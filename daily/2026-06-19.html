RCU 同步：给一个常用 C 函数加上安全外壳

Philipp Stanner 提交了一组补丁，给 C 内核里非常常用的函数 synchronize_rcu() 做了一层安全的 Rust 封装。synchronize_rcu() 的作用是"等所有正在读旧数据的人都读完，再回收旧数据"——它在任何安全场景下调用都没问题，所以非常适合做成一个无需 unsafe 的 Rust 函数。这组补丁分三步走：第一个补丁加封装本身，后面两个补丁分别把封装用到 revocable.rs 和 poll.rs 里，替换掉原来直接调用 C 函数的写法。作者说目前只做了编译测试，但他在自己的 DmaFence 工作里已经用上了第一个补丁、运行良好。

📬 查看补丁系列

同一天，Danilo Krummrich 和 Boqun Feng 修了 Revocable（可撤销资源）的一个并发竞态 bug。问题场景是这样的：当两条代码路径同时想"撤销"同一个资源时会打架。比如用 Devres 管理设备资源时，驱动核心的 devres_release_all() 会通过回调调用 revoke()，而与此同时 Devres::drop() 又在另一个 CPU 上调用 revoke_nosync()——两个"撤销者"撞在一起，谁也没保证安全。这个补丁修复了这个竞态，对内存管理类抽象的健壮性很关键，因为这种"谁先释放"的边界情况一旦出错就是难以复现的崩溃。

️ DMA-buf / dma_fence：Rust 抽象有人接管了

Philipp Stanner 提交了一组关于 dma_fence（一种跨设备的"完成信号"机制，GPU 等高速设备共享缓冲区时大量用到）的补丁。其中最有意义的一条是更新 MAINTAINERS 文件：把新写的 Rust dma_fence 抽象正式纳入现有 dma-buf 子系统的维护范围，由 Philipp 自荐协助维护。理由很实在——这些抽象很复杂，既要懂 C 端又要懂 Rust 端，与其新开一个维护条目，不如挂在现有团队下，由 Sumit Semwal、Christian König 等老维护者一起把关。

📬 查看补丁

同一系列里还有一个小而必要的补丁：往 Rust 的错误码集合里新增 ECANCELED（操作被取消）。原因是 dma_fence 抽象在表达"这个 fence 被取消了"时需要这个标准错误码，否则没法准确把 C 端的语义映射到 Rust 端。这类补丁看着不起眼，但属于"上层抽象要落地，底层基础设施得先补齐"的典型例子。

BINDER（进程间通信）：修正状态检查顺序

Binder（进程间通信）：修正状态检查顺序

Keshav Verma 提交了 rust_binder 的一个 bug 修复（v2 版本）。Binder 是安卓里进程之间互相通信的核心机制。问题在于：现在的 Rust Binder 会先创建 Binder 节点，再去检查是否已经注册了"上下文管理器（context manager）"。如果其实已经有一个管理器存在，那么 set_manager_node() 才返回 -EBUSY 错误——但此时节点状态已经被建好了，留下了一个半成品。这个补丁把检查提前到创建节点之前，让顺序和 C 版 Binder 保持一致，避免出现"先建后悔"的脏状态。审阅者里有 Miguel Ojeda 和 Greg Kroah-Hartman。

模块系统与宏：减少样板代码

模块系统与宏：减少样板代码

Gary Guo 提交了两组配套补丁（都是 v2，各 7 个补丁），目标是让写驱动模块时少敲点重复代码。第一组给 ModuleMetadata trait 加了一个 THIS_MODULE 常量——THIS_MODULE 是 C 内核里"指向当前模块自己"的指针，很多 API 都要传它。第二组更进一步，让 #[vtable] 宏能自动帮你插入 ThisModule，开发者不用再手动写。两组合起来，相当于把以前每个模块都要手抄一遍的样板，交给宏自动生成。

📬 vtable 自动插入

Miguel Ojeda 和 Andreas Hindborg 还提交了 hrtimer（高精度定时器）的一个收紧补丁（v2）：把 expires() 方法限制为只能在安全的上下文里调用。这是为了防止在不该读取定时器到期时间的时机去读它，从源头堵住一类误用。

社区讨论：OPAQUE 在 DROP 之后还会被写吗？

社区讨论：Opaque 在 drop 之后还会被写吗？

在 Zulip 的 #General 频道，Philipp Stanner 抛出了一个很硬核的内存安全问题，引来 Gary Guo、Andreas Hindborg 一起讨论（共 15 条消息）。情况是这样的：他有一个 Opaque<T>（一种"内核里这块内存的内容我不细究、只当黑盒"的包装），这个 Opaque 在某个时刻会被 drop，但支撑它和里面 T 的那块内存在 drop 之后还可能继续存在。Philipp 需要一个保证：除了他自己通过定义好的 API 去改，任何人都不能动这块 T 的哪怕一个字节，哪怕他执行了 unsafe { drop_in_place(...) } 这种操作。

Andreas Hindborg 回应说：编译器不会"凭空造出"写操作，而且因为用了 MaybeUninit，T 的析构函数（Drop）根本不会被运行，所以不必担心。这场讨论本质上是在厘清 Rust 的内存模型在和 C 内核打交道时，到底能给出多强的"不被篡改"保证——对所有写底层抽象的人都很有参考价值。

💬 查看讨论
💡 小白科普
Drop 与 MaybeUninit：Rust 里对象生命周期结束时会自动运行 Drop（类似"善后清理"）；而 MaybeUninit<T> 是"可能还没初始化的 T"，它不会自动帮你跑 Drop，所以适合包装那些由 C 端掌控生死的内存。MaybeUninit 文档 →

代码风格统一：竖排 IMPORT 大扫除

代码风格统一：竖排 import 大扫除

今天有一大批"不改功能、只改格式"的补丁在刷屏，主角是 Andreas Hindborg，集中在 block（块设备）子系统。具体包括：把 block/mq 里的多余 import 删掉并重新格式化（v2，5 个补丁）、把 block/mq 改成竖排 import 风格（v2，5 个补丁）、把 block/rnull（一个用于测试的空块设备驱动）也改成竖排风格（v3，7 个补丁）。所谓"竖排 import 风格"就是每个导入项单独占一行，社区正在统一推这种写法。

为什么大家要花精力做这种"看起来没意义"的改动？因为统一的代码风格能让未来的改动更容易、合并冲突更少、审阅更省心——就像团队约定好所有文件都用同一种排版，新人接手时不用每次都去适应不同人的习惯。这类补丁通常审阅很快、争议小。
