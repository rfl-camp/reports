️ S390 大型机架构：Rust 来了！

补丁 1 — BUG/WARN 支持：

今天最重磅的消息：IBM 的 s390 大型机架构正式开始支持 Rust。开发者 Jan Polensky 提交了一个包含 4 个补丁的系列，目标是让内核中的 Rust 代码能够在 s390 硬件上顺利编译和运行。这意味着 Rust-for-Linux 的硬件覆盖面又扩大了一步——从常见的 x86、ARM，延伸到了企业级大型机。

补丁 1 — BUG/WARN 支持：为 s390 提供了 ARCH_WARN_ASM 宏。在内核中，当代码检测到不应该发生的情况时，会触发 WARN（警告）或 BUG（致命错误）。这个补丁让 Rust 代码也能在 s390 上使用这些机制，就像给新来的 Rust 住户接上了大楼的火警系统。

📬 查看补丁 1 — WARN/BUG 支持
补丁 2 — 静态分支跳转宏：

补丁 2 — 静态分支跳转宏：实现了 ARCH_STATIC_BRANCH_ASM 和 ARCH_STATIC_BRANCH_JUMP_ASM 宏。内核中有一种叫「静态分支」的优化技术：在运行时可以动态开关某些代码路径，而几乎不产生性能开销。之前 s390 的实现把汇编指令嵌在 C 代码里，没法给 Rust 共享使用。这个补丁把汇编序列提取成独立的宏，让 Rust 也能复用。Gary Guo 已经给出了审查意见。

补丁 3 — Bindgen 类型兼容性修复：

补丁 3 — Bindgen 类型兼容性修复：在 s390 上，有些 C 结构体同时使用了 packed（紧凑排列）和 aligned（对齐）属性，这在 C 语言里没问题，但 Rust 编译器不允许一个 #[repr(packed)] 的类型里嵌套包含 #[repr(align)] 的字段（报错 E0588）。解决方法很巧妙：把这些冲突的类型标记为「opaque」（不透明），让 bindgen 不去生成它们的详细布局，而是当作一个黑盒处理。

补丁 4 — 正式启用 Rust 支持：

补丁 4 — 正式启用 Rust 支持：把 s390 正式接入内核的 Rust 基础设施——包括更新架构支持文档、提供 s390 的 Rust 编译目标（target）和必要的编译器标志、设置 bindgen 目标等。Miguel Ojeda（Rust-for-Linux 项目的主要维护者）已参与审查。GitHub 上对应的 issue #106「Support s390」也在同步推进中。

指针格式化安全：防止内核地址泄漏

指针格式化安全：防止内核地址泄漏

补丁 1 — 修复栈地址打印 bug：

开发者 Ke Sun 提交了 v12 版本的安全指针格式化补丁系列（已经迭代了 12 轮！），解决了两个关于 {:p}（指针打印格式）的安全问题。这个系列包含两个补丁，目标是确保内核中通过 Rust 打印指针时，不会意外暴露真实的内存地址——这类信息如果泄漏，攻击者可以利用它绕过 KASLR 等安全防护。

补丁 1 — 修复栈地址打印 bug：之前内核中有一个叫 impl_fmt_adapter_forward! 的宏，在转发 Pointer trait 时会把 self 解构到一个局部变量 t 中。这导致 {:p} 实际上打印的是这个临时栈变量的地址，而不是你真正想打印的那个指针——就好比你想看某栋大楼的地址，结果看到的是快递单的地址。修复方法是移除宏中的 Pointer 转发，改为手动为 Adapter<&T> 实现，确保打印的是正确的指针值。

📬 查看补丁 1 — 修复栈地址
补丁 2 — HashedPtr 防地址泄漏：

补丁 2 — HashedPtr 防地址泄漏：即使指针值是正确的，直接打印原始地址也是不安全的。这个补丁定义了一个新的 kernel::fmt::Pointer trait 和一个 HashedPtr 包装类型，让 {:p} 格式化时走内核的 %p 哈希格式——也就是说，打印出来的不是真实地址，而是一个经过哈希处理的「假地址」，开发者调试时仍然可以区分不同指针，但攻击者无法从中推断出真实的内存布局。Onur Özkan 已给出审查意见。

📬 查看补丁 2 — HashedPtr 📬 查看完整系列
💡 小白科普
KASLR（内核地址空间布局随机化）：内核每次启动时会把自己加载到随机的内存地址，这样攻击者就没法提前知道内核代码在哪，增加了攻击难度。如果代码不小心把真实地址打印到日志里，这道防线就形同虚设了。了解 ASLR

️ 硬件监控（HWMON）：RUST 抽象初探

️ 硬件监控（hwmon）：Rust 抽象初探

开发者 Donjuanplatinum 提交了一个 RFC（征求意见）补丁，为内核的硬件监控（hwmon）子系统添加了最基础的 Rust 抽象层。hwmon 是 Linux 内核中用于读取硬件传感器数据的子系统——比如 CPU 温度、风扇转速、电压等等，你在 Linux 桌面上用 sensors 命令看到的数据就是来自 hwmon。

目前这个抽象层的功能还很精简，属于"最小可用产品"（MVP）阶段：只支持注册一个温度传感器，提供只读的 temp1_input 属性。多通道支持、其他传感器类型（风扇、电压等）、可写属性等功能还没有实现。Guenter Roeck（hwmon 子系统的维护者）已参与讨论。这是一个很好的开端——先把基础框架搭起来，后续再逐步扩展功能。

在 Zulip 聊天中，Donjuanplatinum 还提到了与 Matteo Martelli 关于 hwmon 抽象的之前讨论，以及 MECHREVO WUJIE 系列笔记本在 uniwill-acpi 驱动中添加支持的相关工作，说明社区对硬件监控的 Rust 化有持续的兴趣。

hwmon：Linux 内核的硬件监控子系统，负责从主板、CPU、GPU 等硬件上的传感器芯片读取温度、电压、风扇转速等信息。就像你手机上的"电池健康"功能，但监控的是电脑的各种硬件。了解 hwmon

同步原语与初始化框架

同步原语与初始化框架

SetOnce 新增懒初始化方法：

SetOnce 新增懒初始化方法：Alice Ryhl 提交了一个补丁，为 rust/kernel/sync 模块中的 SetOnce 类型添加了懒初始化方法。SetOnce 是一种同步容器——你可以理解为一个"只能写一次的盒子"：在多线程环境下，多个线程可能都想往里面放东西，但只有第一个成功写入的线程会生效，后面的都会被忽略。新增的懒初始化方法让它能够在第一次被访问时才执行初始化逻辑，既安全又高效。Gary Guo 和 Andreas Hindborg 等 6 位开发者参与了审查，可见社区对这个核心同步原语的重视。

📬 查看补丁
pin-init 宏内部重构（8 个补丁）：

pin-init 宏内部重构（8 个补丁）：Gary Guo 提交了一个大型的重构系列，对 pin-init 基础设施进行内部优化。pin-init 是 Rust-for-Linux 中一套非常重要的宏系统，用于安全地初始化那些"不能移动"的数据结构（pinned types）。在内核中，很多数据结构一旦创建就不能在内存中移动位置（比如被其他地方引用的锁、链表节点等），pin-init 解决的就是"如何安全地初始化这些不能移动的东西"。

这次重构包括：将 pin_data 宏中的字段处理改为使用闭包（closure），新增用于记录字段信息的结构体等。虽然这些是内部实现的改动，不影响对外 API，但它们让代码更清晰、更易维护，也为未来的功能扩展铺平了道路。

impl_flags 添加转换函数：Andreas Hindborg 提交了 2 个补丁，为 impl_flags! 宏生成的标志位类型添加了转换函数。在内核驱动开发中，经常需要用位标志来表示各种状态或选项（比如"只读"、"可写"、"可执行"可以组合在一起），这个补丁让不同标志类型之间的转换更加方便和类型安全。

💡 小白科普
Pin（固定）：Rust 的 Pin 类型保证一个值在内存中的位置不会被移动。这在内核中很重要，因为很多内核数据结构（如互斥锁、等待队列）会被其他地方通过指针引用，一旦移动就会导致"悬垂指针"（指向已失效位置的指针）。了解 Pin

代码风格：统一 "KERNEL VERTICAL" 导入样式

代码风格：统一 "Kernel Vertical" 导入样式

alloc 模块清理（2 组补丁）：

今天有多个补丁在推进导入语句的风格统一工作，把单行的 use 导入改为"kernel vertical"（内核垂直）样式。这是什么意思呢？简单来说：

之前的写法可能是 use kernel::{prelude::*, sync::Arc, types::Flags};——把所有导入挤在一行。"垂直样式"则是每个导入单独一行，像这样：

use kernel::prelude::*; use kernel::sync::Arc; use kernel::types::Flags;

虽然看起来只是格式上的小改动，但对于代码审查（code review）和 git 版本对比来说好处很大：每行只有一个导入，当有人添加或删除一个导入时，git diff 只会显示一行变化，不会"污染"整行，更容易看出改了什么。

alloc 模块清理（2 组补丁）：Gary Guo 和 Eliot Courtney 分别提交了补丁，清理 rust/kernel/alloc 模块（内存分配相关）中的文档测试（doctest）导入和一般导入。Danilo Krummrich 参与了审查。

📬 查看补丁 — doctest 导入清理 📬 查看补丁 — alloc 导入清理

⚡ 抢占与 NMI：内核调度的深水区

⚡ 抢占与 NMI：内核调度的深水区

Boqun Feng 提交了一个包含 11 个补丁的大型系列，用于追踪 NMI（不可屏蔽中断）的嵌套层数，并将其计入独立的 per-CPU 计数器。这是一个相当底层的改动，涉及内核的抢占（preempt）子系统。

简单来说：CPU 在执行代码时可能被各种中断打断。大多数中断可以被暂时"屏蔽"（忽略），但 NMI 不行——它是"不可屏蔽"的，无论 CPU 在干什么都必须立刻响应。当 NMI 嵌套发生时（一个 NMI 处理过程中又来了另一个），内核需要精确知道当前嵌套了几层，否则可能在错误的时机允许任务切换（抢占），导致系统崩溃。这个补丁系列让内核能更精确地追踪这种嵌套，提高了系统的稳定性。Joel Fernandes 和 Steven Rostedt（Linux tracing 子系统的维护者）参与了审查。

📬 查看补丁系列
模块参数初始化顺序修复（v4）：

模块参数初始化顺序修复（v4）：Shashank Balaji 提交了第 4 版补丁（4 个补丁），修复了 module_kset 的初始化时序问题。在内核启动流程中，模块参数（module parameters）需要通过 sysfs 暴露给用户空间，这依赖于 module_kset 这个内核对象集合。但之前它的初始化太晚了——在 do_initcalls()（执行各个子系统的初始化函数）之后才初始化，导致一些早期加载的模块找不到它。这个补丁把初始化提前到 do_initcalls() 之前。Jon Hunter 和 Sumit Gupta 参与了审查，已经迭代到 v4 说明之前几个版本都有反馈需要改进。

📬 查看补丁系列
💡 小白科普
NMI（Non-Maskable Interrupt，不可屏蔽中断）：一种最高优先级的硬件中断，CPU 无法忽略。通常用于硬件故障通知、性能监控、看门狗定时器等场景。想象成你家的烟雾报警器——无论你在干什么都必须立刻响应。了解 NMI
抢占（Preemption）：操作系统强制中断当前正在运行的任务，把 CPU 让给更高优先级的任务。内核需要精确控制什么时候允许抢占，什么时候禁止。了解内核抢占

BINDER 驱动优化

Binder 驱动优化

Alice Ryhl（Google 的 Rust-for-Linux 核心开发者）提交了一个补丁，优化了 Rust 版 Binder 驱动中 shrinker（内存回收器）的实现。具体改动是将 VMA（虚拟内存区域）的查找方式从传统的锁定方式改为使用 lock_vma_under_rcu()——一种基于 RCU（读-复制-更新）机制的更轻量级锁定方式。

这个改动的好处是：在内存压力大、需要回收内存时，shrinker 查找和检查 VMA 的操作会更快、对系统的干扰更小。RCU 允许读操作在几乎零开销的情况下并发进行，只有写操作才需要等待。对于 Binder 这种高频使用的 IPC 机制（Android 系统中几乎所有进程间通信都走 Binder），性能提升意义重大。

📬 查看补丁
💡 小白科普
Binder：Android 系统的核心进程间通信（IPC）机制。手机上每个 App 想和系统服务或其他 App 交互，几乎都要通过 Binder。Rust 版 Binder 驱动是 Rust-for-Linux 最重要的"实战项目"之一。了解 Binder
RCU（Read-Copy-Update）：一种高效的内核同步机制，允许多个读者同时访问数据而不需要加锁，写者则通过"复制-修改-替换"的方式更新数据。特别适合读多写少的场景。了解 RCU

开发工具：RUST-ANALYZER 遇到 BUG

开发工具：rust-analyzer 遇到 Bug

在 Zulip 的 #Help 频道中，DRM/GPU 驱动开发者 Lyude 报告了一个令人头疼的问题：rust-analyzer 突然无法理解 container_of! 宏的类型了。rust-analyzer 是 Rust 社区最常用的 IDE 支持工具（提供代码补全、跳转定义等功能），它对开发效率至关重要。

Lyude 使用的是 rust-analyzer 1.95.0 版本。更糟糕的是，在 rust/kernel/drm/gem/shmem.rs 文件中，只要打开一个未闭合的花括号对，rust-analyzer 就会直接崩溃（panic）。Lyude 已经把复现问题的分支推到了 GitLab 上供社区调查。Tamir Duberstein 正在协助排查，询问了 kconfig 配置和 rust-analyzer 版本等环境信息。

这类工具链问题虽然不影响内核本身的运行，但会严重影响开发者的日常工作效率——想象一下你写代码时 IDE 完全没有智能提示，甚至频繁崩溃，那滋味可不好受。

container_of!：内核中一个经典的宏，给定一个结构体中某个字段的指针，反推出整个结构体的指针。就像你只知道一栋大楼中某个窗户的位置，通过它推算出大楼大门的位置。这个宏在 C 内核中广泛使用，Rust 版内核也提供了对应实现。了解内核 API
rust-analyzer：Rust 语言的 LSP（语言服务协议）实现，为编辑器提供代码补全、错误提示、跳转定义等智能功能。了解 rust-analyzer

Rust 不稳定特性跟踪（GitHub Issue #2）：

Rust 不稳定特性跟踪（GitHub Issue #2）：这是一个长期跟踪的元 issue，记录内核 Rust 代码所依赖的所有 Rust 不稳定特性（unstable features）。Rust 语言有很多还在实验阶段的特性需要用 #![feature(...)] 手动开启，内核代码用到了其中不少。这个 issue 会持续更新，直到这些特性全部稳定化。如果你想了解"内核的 Rust 代码和普通 Rust 程序有什么不同"，这个 issue 是很好的起点。

🔗 GitHub Issue #2
