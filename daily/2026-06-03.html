ZEROCOPY 库支持

zerocopy 库支持

Miguel Ojeda 提交 zerocopy 支持（18 个补丁）

Miguel Ojeda 提交 zerocopy 支持（18 个补丁）

这是今天最重要的基础设施更新之一！Miguel Ojeda 提交了一个包含 18 个补丁的大型系列，为 Linux 内核引入对 zerocopy 库的支持。zerocopy 的口号是："快速、安全、编译报错——三选二"。它提供了一组可派生的 trait（比如 FromBytes、IntoBytes）和宏（比如 transmute!），用来安全地进行内存类型转换。

你可以这样理解：在内核中，经常需要把一块原始的字节数据"解读"成某种结构体（比如把网卡收到的一堆字节解读成一个网络数据包头）。在 C 语言中这通常用强制类型转换，非常容易出错。zerocopy 让你在 Rust 中"零拷贝"地完成这件事——数据不需要复制，类型转换在编译期就经过安全检查。这大幅降低了内存安全 bug 的风险。

内核安全与内存管理

内核安全与内存管理

删除 task_euid() 函数（v4）

删除 task_euid() 函数（v4）

Alice Ryhl 提交了第 4 版补丁，要删除 task_euid() 这个函数。euid 是"有效用户 ID"（effective user ID）的缩写——简单来说，Linux 系统通过 euid 来判断"这个进程现在以谁的身份在运行"。比如当你用 sudo 运行命令时，进程的 euid 会变成 root（0）。删除这个函数可能是因为 Rust 版的内核 API 提供了更安全的替代方式来获取这个信息，或者这个接口的设计存在问题。Paul Moore（Linux 安全子系统的维护者之一）参与了审查，这表明这个改动涉及到安全敏感的代码路径。

RISC-V 内存管理：确保 PROT_WRITE 正确映射（v23，28 个补丁）

RISC-V 内存管理：确保 PROT_WRITE 正确映射（v23，28 个补丁）

Deepak Gupta 提交了一个大型补丁系列的第 23 版（共 28 个补丁！），解决 RISC-V 架构上的一个内存权限问题。问题是：当用户程序请求"可写"（PROT_WRITE）的内存映射时，系统应该同时授予"可读 + 可写"（VM_READ | VM_WRITE）权限。这在其他架构上是默认行为（因为大多数 CPU 硬件上"可写"隐含了"可读"），但 RISC-V 的设计允许"只写不可读"的内存页面。这个补丁确保 RISC-V 上的行为和其他架构一致，避免一些程序因为假设"可写就能读"而崩溃。Eric W. Biederman 参与了审查。迭代到 v23 说明这个问题的处理非常棘手，涉及到多个子系统的协调。

Soundness Issue：ProcessInner::death_delivered 未强制列表所有权不变量
