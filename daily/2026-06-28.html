️ 修复 DRM/misc 驱动的 fops.owner 崩溃问题（v7 大补丁系列）

今天的"重头戏"。作者 Alvin Sun 提交了一整套 10 个补丁，标题是 "Fix missing fops.owner in Rust DRM/misc abstractions"。这件事的来龙去脉很有教育意义：在开发一个叫 tyr 的显卡调试功能时，开发者发现一个真实崩溃——当 gnome-shell（桌面环境）还开着 /dev/card1（显卡设备节点）时，如果你用 rmmod tyr 把驱动卸载掉，内核就会发生空指针解引用而崩溃。

根本原因是：每个设备的"文件操作表"（file_operations，简称 fops）里有一个 owner 字段，它的作用是告诉内核"这个设备正被哪个模块支撑着"。只要还有人开着这个设备，内核就不该允许卸载对应模块。但 Rust 的抽象层之前漏填了这个 owner，导致内核以为"没人用"，于是把模块拆了，留下一个悬空的指针，下一次访问就炸了。

📬 查看补丁系列总览

为了干净地修好它，这套补丁做了不少"搬家"和"重构"工作。第一步是把模块相关的核心类型（Module、InPlaceModule、ModuleMetadata、ThisModule）从大杂烩文件 lib.rs 搬进一个新的专门文件 rust/kernel/module.rs，再从原处重新导出，这样既整理了代码，又不会牵动一大堆其他文件。同时把六个总线驱动里访问内部字段 module.0 的写法，改成用公开方法 ThisModule::as_ptr()，因为那个字段不再公开了。

📬 查看：模块类型搬进 module.rs

第二步是给 ModuleMetadata trait 加上一个 THIS_MODULE 常量。以前 ThisModule 指针只能在运行时拿到，但因为最低支持的 Rust 版本（MSRV）升级后，一个叫 const_refs_to_static 的特性稳定了，现在可以在编译期常量上下文里使用这个指针了。这正是填 file_operations 这种"静态表"所需要的——它必须在编译期就准备好。

📬 查看：ModuleMetadata 新增 THIS_MODULE 常量

️ 修复 DRM/misc 驱动的 fops.owner 崩溃问题（v7 大补丁系列）

第三步是让 #[vtable] 宏更智能：自动在 trait 一侧补上 type OwnerModule: ::kernel::ModuleMetadata; 这个关联类型，并在实现一侧自动填上 type OwnerModule = crate::LocalModule;。这样驱动开发者就不用每次都手动声明和实现 OwnerModule 了，少写很多样板代码。配套地，还在 doctest（文档测试）环境里加了一个带空指针实现的 LocalModule 兜底，避免在没有 module! 宏的测试场景里编译失败。

📬 查看：#[vtable] 自动插入 OwnerModule 📬 查看：doctest 的 LocalModule 兜底

真正的修复落点在 miscdevice（杂项字符设备）和 drm（显卡）这两个抽象层：它们终于把驱动的模块指针正确地填进了 fops.owner。这两个补丁才是直接堵住开头那个崩溃的"补丁眼"。剩下的几个补丁是收尾工作：把 binder 改用 LocalModule、从 module! 宏里彻底移除旧的 THIS_MODULE 静态变量，以及更新 MAINTAINERS 文件让新的 module.rs 有人负责维护。还有一个独立但同源的 v7 补丁，把 configfs 的 configfs_attrs! 宏里的 THIS_MODULE 换成了 this_module::<LocalModule>()，保持整体一致。

📬 查看：miscdevice 设置 fops.owner 📬 查看：drm 设置 fops.owner 📬 查看：从 module! 移除 THIS_MODULE 静态变量 📬 查看：binder 改用 LocalModule 📬 查看：更新 MAINTAINERS 📬 查看：configfs 改用 LocalModule
🎓 小白科普
• fops.owner（文件操作表的 owner 字段）：内核用它记录"某个设备文件归哪个模块管"，从而防止你在设备还被使用时把模块卸载掉——就像还书前图书馆不会拆掉那个书架。漏填它就会留下悬空指针导致崩溃。→ 内核 VFS 与 file_operations 文档
• 空指针解引用（NULL pointer dereference）：程序去访问一个"指向空地址(0)"的指针，CPU 拒绝并报错；在内核里这往往直接导致系统崩溃（kernel panic/oops）。→ 维基百科：悬空指针

RUST BINDER 驱动改进与限速日志打印

Rust Binder 驱动改进与限速日志打印

Google 的 Carlos Llamas 今天连发好几组补丁，主题都围绕 Rust 版 Binder 驱动（Binder 是安卓上进程之间互相通信的核心机制）的日志打印。第一组补丁先在内核 Rust 库里新增了一类 pr_*_ratelimit! 宏。"ratelimit（限速）"的意思是：如果同一条错误日志短时间内疯狂触发，这套宏会自动帮你"压一压"，只打印一部分，避免日志被刷爆、把磁盘和串口塞满。这是给后面的改造打基础。

📬 查看：新增 pr_*_ratelimit! 宏

有了限速宏之后，他又提交了两组针对 Binder 自身的补丁：一组把事务（transaction）失败时分散在各处的打印语句整合到一起，让出错信息更统一、更好排查；另一组则把 Binder 里原来普通的打印统一换成 pr_*_ratelimited! 版本，这样当某个客户端不停触发同一种事务错误时，不至于把内核日志淹没。这对一个像 Binder 这样每秒可能处理大量请求的高频驱动来说很实用。

📬 查看：整合事务失败打印 📬 查看：Binder 改用限速打印

还有一个 v2 小补丁，针对清理 Binder 内部"偏移量数组（offsets array）"的代码。原来清理时用的步长（stride）类型可能不够宽，这个补丁改成用 u64（64 位无符号整数）作为步长，避免在大数据量下出现计算溢出之类的隐患。这是个不起眼但关乎正确性的细节改进。

📬 查看：清理偏移量数组改用 u64 步长 (v2)
🎓 小白科普
• Binder：安卓系统里进程间通信（IPC）的核心机制，App 调系统服务、服务之间互相调用都靠它；现在社区正在用 Rust 重写它的驱动以提升安全性。→ 内核 binderfs 文档
• 日志限速（ratelimit）：当同一条日志在短时间内重复太多次时自动抑制输出，防止刷屏拖垮系统——类似手机通知的"勿扰/合并"功能。→ 内核 printk 基础文档

类型系统与宏工具的基础打磨

类型系统与宏工具的基础打磨

这一类补丁不直接做功能，而是给整个 Rust 内核代码打"地基"。Danilo Krummrich 和 Miguel Ojeda 提交的 v4 补丁引入了一个叫 ForLt 的基础 trait，作为现有 CovariantForLt 的更底层支撑。这听起来很抽象，简单说：它和 Rust 里的"生命周期（lifetime）"以及"型变（variance）"这些高级类型概念有关，目的是让抽象层在处理"带生命周期参数的类型"时更灵活、表达力更强。这种 trait 一般驱动开发者不会直接碰，但库作者写安全抽象时会依赖它。

📬 查看：ForLt 基础 trait (v4)

Antonio Hickey 和 Miguel Ojeda 提交了 v5 补丁，新增一个 overflow_assert! 宏。它的用途是做算术溢出检查的断言——在内核里，整数计算一旦溢出（比如两个很大的数相加超过类型上限）可能导致严重的安全漏洞或崩溃。有了这个宏，开发者可以在关键计算处显式断言"这里不该溢出"，让问题在出现时立刻暴露，而不是悄悄算出一个错误的值。

📬 查看：overflow_assert! 宏 (v5)
🎓 小白科普
• 型变 / 协变（variance / covariance）：描述"如果类型 A 能当作 B 用，那么包含 A 的容器能不能当作包含 B 的容器用"的规则，是 Rust 生命周期安全的底层机制。→ Rust 子类型与型变文档
• 整数溢出（integer overflow）：计算结果超过该整数类型能表示的最大值，会"绕回"成一个错误的小值，在内核里常是漏洞来源。→ Rust checked 运算文档

️ 用 PIN_INIT::ZEROED 替换不安全的"清零"写法

️ 用 pin_init::zeroed 替换不安全的"清零"写法

Alexandre Courbot 今天提交了两个思路一致的补丁，都是把代码里的 core::mem::zeroed 换成 pin_init::zeroed。前者是 Rust 标准库里一个把内存全部填零来"凭空造一个值"的函数，但它是 unsafe 的，而且对某些类型来说"全零"并不是一个合法状态，用错了会引入未定义行为。pin_init 是内核专门用来安全做"原地初始化"的框架，它的 zeroed 更受控、更符合内核对初始化的要求。

具体来说，一个补丁改的是 IOMMU（输入输出内存管理单元，负责管理外设访问内存时的地址翻译）抽象层；另一个改的是 Rust Binder 里 file_operations 的初始化。两处都是把"手动清零"换成框架提供的更安全方式，属于持续提升代码健壮性的清理工作。

📬 查看：iommu 改用 pin_init::zeroed 📬 查看：rust_binder 的 file_operations 改用 pin_init::zeroed
🎓 小白科普
• pin_init：Rust-for-Linux 里专门解决"如何安全地在固定内存位置上原地构造一个对象"的框架，内核很多结构体不能随意移动，所以需要它。→ Rust-for-Linux：pinned-init 介绍
• IOMMU：一个硬件单元，给外设（如显卡、网卡）访问内存时做地址翻译和隔离，相当于内存的"门禁系统"。→ 维基百科：IOMMU

依赖更新与工具链动态

Nicolas Schier 提交了一个补丁，把内核里用到的 zerocopy 这个第三方库更新到了 v0.8.52。zerocopy 的作用是让程序能在不复制数据的情况下，安全地把一块字节内存"看作"某种结构体类型——这对追求性能的内核代码很有价值。跟着上游库版本走，能拿到 bug 修复和新特性，是日常维护的一部分。

📬 查看：zerocopy 更新到 v0.8.52

GitHub 上由 Miguel Ojeda（ojeda）维护的 Issue #355「rustc 想要的特性与 bug 修复」仍然开着。这是一个长期的"愿望清单"式追踪帖，记录 Rust-for-Linux 项目希望 Rust 编译器（rustc）实现或修复的功能。它带着 toolchain 和 meta 标签，本质上是社区和 Rust 编译器团队之间的协作桥梁——很多今天能用上的新写法（比如前面提到的 const_refs_to_static 稳定）正是这类长期推动的成果。

📬 查看：Issue #355 rustc 愿望清单
🎓 小白科普
• MSRV（最低支持的 Rust 版本）：项目能正常编译所需的最老 Rust 编译器版本；一旦 MSRV 提高，就能用上更新的语言特性（今天的 fops 修复正是受益于 MSRV 提升后稳定的特性）。→ Cargo 的 rust-version 文档
• zerocopy：一个让你"不拷贝、零开销"地在字节数据和类型之间转换的 Rust 库，常用于解析二进制数据。→ zerocopy 文档

社区讨论：要不要给 KERNEL::DEVICE 加相等比较？

社区讨论：要不要给 kernel::Device 加相等比较？

在 Zulip 聊天的 General 频道里，有人发起讨论：能不能给 kernel::Device（内核设备类型）实现 PartialEq，也就是让两个设备对象可以用 == 直接比较是否"相等"。Danilo Krummrich 在回复里给出了一段示例代码，演示如何判断当前设备和它的父设备是否是同一个——他建议通过比较两者的底层裸指针（as_raw()）来判断，如果两个指针不一样就返回 EINVAL（参数无效）错误。

这段讨论体现了一个内核 Rust 抽象设计中的常见取舍：设备"相等"到底该怎么定义？是比较内存地址（同一个对象），还是比较某种业务上的标识？Danilo 的写法倾向于用裸指针地址来判断是否是同一个设备实例，这是目前比较务实的做法。讨论目前还比较初步，更多是在打磨写法而非定下结论。

📬 查看：Zulip 讨论
🎓 小白科普
• PartialEq：Rust 的一个 trait，类型实现它之后就能用 == 和 != 做相等比较。→ Rust PartialEq 文档
• 裸指针 as_raw()：Rust 抽象层里拿到底层 C 结构体原始指针的方法，比较两个裸指针地址相等就意味着它们指向同一个对象。→ Rust 指针文档
