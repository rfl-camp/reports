️ GPU / DRM 驱动

️ GPU / DRM 驱动

nova-core：获取并显示显存(VRAM)容量

来自 NVIDIA 的 Alexandre Courbot 提交了一组 4 个补丁，让 nova-core（用 Rust 编写的 NVIDIA GPU 开源驱动）能够查询并显示显卡上有多少显存。这组补丁分工很清晰：第一个补丁把 GSP（GPU 系统处理器）的卸载状态移到了一个 pinned 的 GPU 子对象中，这样在内存中的位置就不会被移动，避免指针失效；第二个补丁把获取 GPU 静态信息的逻辑重构为 GSP 的一个方法，代码结构更清晰；第三个补丁让驱动通过 GSP 固件提取可用的"帧缓冲区"(FB)内存区域；最后一个补丁整合前面的工作，将 VRAM 容量信息暴露出来。

打个比方：这就像给一台新电脑装好驱动后，系统终于能在"设备管理器"里看到你的显卡有多少 GB 显存了——之前驱动连这个基本信息都还读不到。

DRM GpuVM：修复多线程安全性（Send/Sync）

Google 的 Sami Tolvanen 提交了两组 v3 补丁，修复了 DRM 子系统中 GpuVM（GPU 虚拟内存管理）抽象的线程安全问题。问题在于：GpuVm 结构体之前无条件地实现了 Send 和 Sync（意思是"我可以安全地在线程间传递和共享"），但它内部持有的 VmBoData 和 Object 数据并不一定满足这个条件。如果这些数据本身不是线程安全的，多个线程同时操作它们就会出 bug——这在 Rust 的类型系统中被称为"不健全"(unsound)。

修复方法是：给 GpuVm 的 Send/Sync 实现加上了正确的 trait bound，要求内部数据也必须是 Send + Sync。同时，GpuVaAlloc（GPU 虚拟地址分配器）和 GpuVmBo（GPU 虚拟内存的缓冲对象）也获得了合理的 Send/Sync 实现，这样各个 GPU 驱动就不用自己写 unsafe impl Send 了。

zerocopy 库集成

zerocopy 支持 v2：19 个补丁的大系列

Alice Ryhl、Gary Guo 和 Miguel Ojeda 共同提交了一个包含 19 个补丁的大型系列，将 zerocopy 库引入 Linux 内核的 Rust 代码中。zerocopy 是一个用于安全地在字节序列和 Rust 结构体之间转换的库——在内核中，驱动程序经常需要把从硬件或网络收到的一串字节"翻译"成有结构的数据，以前这需要写很多 unsafe 代码，而 zerocopy 可以自动验证数据的有效性并安全地完成转换。这是第二版补丁，已经收到了 5 位审查者的反馈。

上游 zerocopy 库同意添加内核专属 derive 支持

在 Zulip 的 zerocopy 频道中，zerocopy 库的作者 Jack Wrenn 被社区说服了！他宣布将在下个版本中添加 derive(zerocopy_derive::most_traits) 这个宏，通过 --cfg zerocopy_unstable_linux 配置标志启用。这意味着内核开发者只需要写一行 #[derive(...)] 就能自动为结构体实现所有常用的 zerocopy trait，大大减少重复代码。对应的上游 PR 已在 GitHub 上。Miguel Ojeda 也将此链接到了内核项目的 Issue #1239 进行追踪。

BINDER 驱动（ANDROID IPC）

Binder 驱动（Android IPC）

Process::node_refs 从 Mutex 换成 SpinLock

Alice Ryhl 提交了一组 6 个补丁（v2），将 Binder 驱动中 Process::node_refs 的锁从互斥锁（Mutex）换成自旋锁（SpinLock）。原因是实际运行中发现了优先级反转问题：一个高优先级的 UI 线程试图获取 mutex，但持有这把锁的低优先级线程被操作系统调度器换下去了，导致 UI 线程苦等了 22 毫秒才拿到锁——这对用户来说就是明显的界面卡顿！

换成自旋锁后，持锁时间非常短（因为自旋锁的使用规范要求在持锁期间不能做任何可能阻塞或耗时的操作），这样高优先级线程就不会被长时间阻塞了。打个比方：互斥锁像是在门口排队等叫号，如果前面的人去上厕所了你只能干等；自旋锁像是一扇旋转门，每个人只能快速通过，不允许在里面停留。

📬 查看补丁
Binder 驱动安全性问题：Issue #1237 和 #1238

用户 GeorgeAndrou 报告了两个 Binder 驱动的安全性 (soundness) 问题。Issue #1237 指出 Node::add_death 函数中的 unsafe 不变量仅依赖于"隐式调用约定"——也就是说，它假设调用者会以特定方式调用这个函数，但这个假设并没有被类型系统强制保证。Issue #1238 则指出 ProcessInner::death_delivered 没有正确强制"链表所有权"不变量，这意味着在某些极端情况下可能出现内存安全问题。

这类 Issue 体现了 Rust 在内核中的价值：通过严格审视 unsafe 代码的边界条件，社区正在系统性地提高 Binder 驱动的安全性。

I/O 子系统

I/O 子系统

动态大小的 I/O Region 类型（v3，19 个补丁）

Gary Guo 提交了一组大型补丁（19 个），为 Rust 的 I/O 抽象添加了一种"动态大小"的 Region 类型。在内核中，驱动程序需要与硬件寄存器交互，这些寄存器通过内存映射 I/O (MMIO) 暴露给 CPU。之前的 I/O Region 类型在编译期就必须确定大小，但很多设备的 I/O 区域大小只有在运行时才能知道（比如不同型号的网卡可能有不同大小的寄存器空间）。这组补丁让驱动可以在运行时指定 I/O 区域的大小，大大增加了灵活性。

Zulip 讨论：通用 I/O 后端与对齐问题

在 Zulip 上，Gary Guo、Danilo Krummrich、Alice Ryhl 和 Alexandre Courbot 展开了一场 28 条消息的深度讨论，主题是 I/O 区域的对齐（alignment）问题。Sashiko 指出当前的"无类型"I/O 区域存在对齐不正确的情况——对硬件 I/O 来说，如果你用错误的对齐方式读写寄存器，硬件可能不响应甚至崩溃。

Gary Guo 在设备树中搜索后发现，有些 GPIO 驱动使用的 I/O 区域是按 1 字节对齐的，和其他驱动使用的 4 字节对齐不同。这意味着 I/O 抽象可能必须支持自定义对齐，这是一个比较复杂的设计问题。讨论还在进行中，社区正在权衡增加通用性与保持 API 简洁之间的平衡。

内存与类型安全

新增 Align 类型：让对齐也能用泛型参数

Gary Guo 提交了一个新的 Align 类型，解决了 Rust 中一个长期存在的限制：#[repr(align(N))] 属性中的 N 只能是硬编码的整数，不能用泛型参数。新的 Align 类型通过 const generics（常量泛型）实现，允许在编译期通过类型参数指定对齐值。这对于需要针对不同硬件有不同对齐要求的抽象层非常重要——比如前面提到的 I/O Region 就可能用到它。

block: 修复 GenDisk 的 Send bound

由 Yuan Tan 和 Andreas Hindborg 提交（v2），修复了块设备层中 GenDisk<T> 结构体的 Send trait bound。之前的代码要求 T: Send，但这里的 T 是"操作实现"类型（Operations），通常是一个零大小的标记类型（不携带任何数据），所以约束 T: Send 完全是约束错了对象。真正需要约束的是 GenDisk 内部实际持有并跨线程移动的数据。这个补丁是一个包含 83 个补丁的大系列中的一部分。修正了这个 bound，使类型约束更精确地反映了实际的所有权语义。

社区讨论：字段投影与 RCU

社区讨论：字段投影与 RCU

Zulip 上最热烈的讨论之一（38 条消息），Benno Lossin、Andreas Hindborg、Alice Ryhl 和 Miguel Ojeda 一起探讨了如何用"字段投影"(field projections) 这个新设计来改进 RCU（Read-Copy-Update）的 Rust 抽象。

Benno Lossin 分享了一个详细的设计原型，展示了一种将 Driver、DriverData 和共享数据结构组合在一起的方式。核心思想是：当你有一个被 Arc<Mutex<DriverData>> 保护的复杂数据结构，你可能只想访问其中的一个字段而不是整个结构——这就是"字段投影"做的事情。它就像是给一个大保险箱中的某一个抽屉配了一把专用钥匙，你可以只打开那个抽屉而不用打开整个保险箱。

对于 RCU 来说，这个设计意味着读取操作可以更高效：你可以直接"投影"到你需要读取的字段，而写入操作则通过正常的路径完成。Benno 提供了完整的示例代码，包括读写两种访问模式的实现。这是一个非常前沿的探索，可能会深刻影响未来内核 Rust 代码中锁和共享数据的使用方式。

💡 RCU (Read-Copy-Update)：Linux 内核中一种高效的同步机制，特别适合"读多写少"的场景。读操作几乎没有开销，写操作则通过创建数据副本、修改副本、然后原子替换的方式完成。📖 学习更多

统一"内核竖排导入"风格（已合入 rust-next）

Miguel Ojeda 和 Andreas Hindborg 在多个模块中推进了"内核竖排导入"(kernel vertical imports) 代码风格。这种风格要求每个 use 语句导入的模块各占一行，一行一个，而不是用花括号把多个导入挤在一行里。虽然没有功能变化，但统一的代码风格让大型代码库更容易阅读和审查。

已有 4 个提交合入了 rust-next 分支：rust/kernel/str.rs（两个提交——风格转换和清理未使用导入）、rust/kernel/aref.rs 和 rust/kernel/page.rs。
