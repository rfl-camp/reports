UACCESS 用户内存拷贝接口大重构（RFC 系列）

uaccess 用户内存拷贝接口大重构（RFC 系列）

这是今天最值得关注的技术动态。Christophe Leroy 提交了一组共 9 个补丁的 RFC 系列，目标是彻底重构内核中「用户空间内存访问」相关的接口。这些接口，也就是 copy_to_user() / copy_from_user()，是内核向用户程序读写数据的核心通道——可以想象成快递员在内核和用户程序之间送包裹的「标准流程」。

【补丁 2/9】INLINE_COPY 迁移到 Kconfig

当前内核支持 21 种架构，其中 16 种定义了 INLINE_COPY_TO_USER 和 INLINE_COPY_FROM_USER 这两个宏，而另外 5 种一个都没定义。这种用 C 语言 #ifdef 控制的方式容易出错，补丁提议把它们统一成一个叫 CONFIG_ARCH_WANTS_NOINLINE_COPY 的 Kconfig 配置项，让架构差异交给构建系统管理，更清晰也更安全。参与讨论的有 Andrew Cooper、Yury Norov 等人，共 3 条 review 意见。

uaccess 用户内存拷贝接口大重构（RFC 系列）

【补丁 5/9】引入 copy_partial 系列函数

这是重构中最核心也最敏感的一步。计划在后续补丁中修改 copy_to_user() / copy_from_user()，让它们在失败时直接返回错误码 -EFAULT，而不是像现在这样返回「没拷贝完的字节数」。问题在于，在内核 6000 多处调用这两个函数的代码中，大约有 2% 的地方依赖于「部分拷贝」行为——即拷贝失败时仍会告诉你拷了多少。这部分代码需要提前切换到新的 copy_to_user_partial() / copy_from_user_partial() 接口。讨论者包括 Alice Ryhl、Linus Torvalds 和 David Laight，共 4 条 review 意见。

📬 查看补丁

【补丁 7/9】x86 补全 unsafe_copy_from_user()

目前 x86 和 arm64 两大主流架构都缺少 unsafe_copy_from_user() 这个函数。它是 copy_from_user() 的「裸版本」，调用者自行保证地址合法，省去一些安全检查，性能更高但风险也更大。这个补丁为 x86 补上了这个缺失的实现，让两个架构的接口对齐。参与讨论的有 Linus Torvalds、Yury Norov、Christophe Leroy，共 5 条 review 意见——这说明 Linus 本人在密切关注这个 RFC 系列。

RUST PIN-INIT 初始化框架：重要 BUG 修复

Rust pin-init 初始化框架：重要 bug 修复

pin-init 是 Rust-for-Linux 中一个专门处理「在固定内存位置初始化结构体」的框架，在内核中处理需要 Pin 的数据结构时不可或缺。今天这个框架迎来了三个相关补丁，其中最关键的是一个生命周期标注的 bug 修复。

【v3】修复字段引用的错误生命周期标注

Gary Guo 提交第三版修复：当使用 init! 或 pin_init! 宏初始化结构体时，可以在初始化其他字段时引用已经初始化好的字段。然而，代码中这些引用被错误地标注为 &'static 生命周期（意思是「引用永远有效」），而实际上引用只在初始化器的作用域内有效。虽然目前没有用户代码触发了这个漏洞，但它理论上可能允许悬垂引用，是一个必须修复的安全隐患。Alice Ryhl 参与了 review。

社区讨论：UNWRAP 的用法之争 + 自旋锁进展 + 行业动态

社区讨论：unwrap 的用法之争 + 自旋锁进展 + 行业动态

社区今天在 Zulip 上有几个值得关注的讨论。

unwrap() vs. unwrap_unchecked()：该用哪个？

GPU 开发者 Lyude 在 #General 频道发起了这个讨论，起因是她在自己的 shmem 系列补丁的 review 中，审查者 Alexander 建议用 unwrap_unchecked() 替代 unwrap()。unwrap() 在值为 None/Err 时会 panic，而 unwrap_unchecked() 是 unsafe 的，跳过检查直接取值，如果值实际上是 None 会触发未定义行为，非常危险。

Gary Guo 给出了简洁有力的回答：「能不用就都别用」。他建议用 Option::insert 等方法来获取引用，从结构上避免需要 unwrap 的情况。这体现了 Rust-for-Linux 社区的代码风格取向：既不爱用可能 panic 的 unwrap()，更不鼓励用绕过安全检查的 unwrap_unchecked()，而是从设计上消除「不得不解包」的场景。这个讨论对所有写内核 Rust 代码的人都很有参考价值。

📚 小白科普
• unwrap() 与 panic：Rust 中 Option::unwrap() 如果值是 None 会导致程序崩溃（panic）。在内核中 panic 通常会引发系统崩溃，所以内核代码对 unwrap 的使用非常谨慎。
→ doc.rust-lang.org · Option::unwrap
• 自旋锁（Spinlock）：一种「忙等待」的锁，线程拿不到锁时不会睡眠，而是一直循环检查。在中断上下文中只能用自旋锁，不能用普通互斥锁。
→ docs.kernel.org · 自旋锁
