️ PowerPC 架构 Rust 支持（V13 大版本更新）

今天最重磅的消息：来自 IBM 的 Mukesh Kumar Chaurasiya 提交了 PowerPC 架构 Rust 支持的 第 13 版补丁系列，一共包含 7 个补丁。这意味着 PowerPC 这个经典的处理器架构（曾经用在苹果 Mac、IBM 服务器上），离正式支持用 Rust 写内核模块又近了一步。这个系列同时支持两种 PowerPC 变体：32 位大端序（ppc32be）和 64 位小端序（ppc64le）。

整体补丁系列概览：这 7 个补丁像搭积木一样，一层层解决了在 PowerPC 上编译 Rust 内核代码遇到的各种问题。从修复编译器找错依赖库、到链接符号缺失、到内联汇编不兼容，最终实现了完整的架构支持。ppc64le 已经在 Power11 服务器上成功运行了 rust_minimal 示例模块；ppc32 则在任天堂 Wii 上测试通过！

补丁 1 — 修复 "multiple candidates for rmeta dependency core" 错误：在用 LLVM 工具链为 ppc64le 编译 Rust 代码时，rustc 编译器会困惑——它同时看到了系统自带的标准库和内核自己编译的 libcore.rmeta，不知道该用哪个。这个补丁通过调整搜索路径的优先级，确保编译器总是使用内核自己编译的版本。就像你电脑上装了两个版本的 Python，程序不知道该调用哪个，所以需要明确指定路径。

📬 查看补丁

补丁 2 — 修复 dma-resv 未定义符号问题：当内核配置中没有启用 CONFIG_DMA_SHARED_BUFFER（DMA 共享缓冲区）时，链接器会报错说找不到 dma_resv_unlock 等符号。这是因为 Rust 辅助函数文件 helpers.c 里引用了这些函数，但对应的 C 代码根本没有被编译进来。补丁通过条件编译（只在启用了相关配置时才编译这些辅助函数）解决了问题。这是个典型的"跨架构兼容性"问题——x86 上默认开启的功能，在 PowerPC 上可能是关闭的。

📬 查看补丁

补丁 3 — 调整 jump_label 内联汇编：PowerPC 的跳转标签（jump_label）机制需要在 C 和 Rust 之间共享内联汇编代码。为了避免在两种语言中重复编写相同的汇编，这个补丁引入了一个新宏 ARCH_STATIC_BRANCH_ASM，让 C 和 Rust 可以共用同一份汇编定义。这和上游之前在其他架构上做的改进保持一致。

📬 查看补丁

补丁 4 — 设置 PowerPC 最低 rustc 版本为 1.95：PowerPC 需要稳定的内联汇编（inline asm）支持，而这个功能是在 Rust 1.95 才稳定的。所以这个补丁在构建系统里加了一个版本检查——如果你的 rustc 版本低于 1.95，直接告诉你不支持，而不是让你编译到一半报一堆奇怪的错误。

补丁 5 — 让 __udivdi3/__umoddi3 触发 panic：这是由 Link Mauve 贡献的补丁。Rust 的 core 库在格式化 64 位和 128 位整数时会调用软件除法函数 __udivdi3 和 __umoddi3，但内核中不应该使用这些函数（内核有自己的除法方式）。这个补丁让这两个函数在被调用时直接 panic（崩溃并报错），这样如果有代码不小心用了它们，就会立刻被发现，而不是产生难以排查的 bug。

GPU / DRM 图形驱动

GPU / DRM 图形驱动

引入 shmem::SGTable 抽象（v12）：这组由 Red Hat 的 Lyude Paul 和 NVIDIA 的 Alexandre Courbot 共同推进的补丁系列已经迭代到第 12 版，可见其复杂度。它为 DRM 子系统的 GEM（Graphics Execution Manager）共享内存对象引入了 SGTable（散列-聚集表）的 Rust 抽象。

简单来说，GPU 驱动需要管理显存和系统内存之间的数据传输。但内存在物理上可能是碎片化的——就像你的书分散在房间各个角落。SGTable 就是一张"地图"，告诉 GPU："你要的数据分散在这些地方，按这个顺序去拿。"这个 Rust 封装让 GPU 驱动开发者可以用安全的 Rust 代码来操作这个地图，而不用直接和 C 的指针打交道。这是 Nova（NVIDIA 开源 GPU 驱动）和其他 Rust GPU 驱动的重要基础设施。

内存管理与数据结构

内存管理与数据结构

新增零大小 realloc 测试（v1 & v2）：社区新人 Hsiu Che Yu 今天连续提交了两版补丁，为内核的 Rust 内存分配器（Kmalloc、Vmalloc、KVmalloc）添加测试用例。根据 Allocator trait 的约定，当你调用 realloc 但把目标大小设为零时，应该等同于释放内存（free）。但之前没有测试来验证这个行为！Hsiu Che Yu 的补丁补上了这个空白——第一版是功能测试（验证行为正确），第二版改为冒烟测试（只验证不会崩溃或报错），措辞更加精确。

📬 查看 v1 补丁 📬 查看 v2 补丁

XArray 新增 Guard::find() 辅助方法：Alvin Sun 提交了一组 4 个补丁，为内核的 XArray 数据结构的 Rust 封装添加了 Guard::find() 方法。XArray 可以理解为内核中的"超级数组"——它能高效地按索引存取数据，还支持并发访问。新增的 find() 方法允许在持有锁（Guard）的情况下按范围查找元素，由维护者 Andreas Hindborg 进行了代码审阅。

修复 List::remove 的 SAFETY 注释：Philipp Stanner 发现 List::remove 方法中的安全性注释（SAFETY comment）描述不准确。在 Rust-for-Linux 项目中，每个 unsafe 代码块都必须有详细的注释解释为什么它是安全的，这是项目的硬性规定。这个补丁修正了注释中对类型的错误引用，虽然不影响运行，但对代码的可维护性和审阅质量很重要。

初始化框架与宏工具

初始化框架与宏工具

修复 pin-init 访问器引用生命周期（v2）：Gary Guo 提交了对 pin-init 库的修复。pin-init 是 Rust-for-Linux 中一个非常核心的库，用于安全地初始化需要"固定"在内存中不能移动的数据结构（很多内核对象都有这个要求，比如互斥锁、链表节点）。这个 bug 是访问器（accessor）返回的引用生命周期不正确——简单说就是编译器可能允许你在数据已经无效之后还继续使用它。v2 版本已经收到 1 条审阅意见。

📬 查看补丁

Zulip 讨论：init_zeroed + chain 的可失败组合：在 Zulip 的 #pin-init 频道中，Andreas Hindborg 遇到了一个类型系统的小麻烦。他想把 Opaque::init_zeroed()（把内存清零）和 .chain()（链式后续初始化）组合使用，但 init_zeroed() 返回的错误类型是 Infallible（永远不会失败），而 chain 闭包返回的是 Result<_, Error>（可能失败），两个错误类型对不上。Benno Lossin 指出需要使用泛型错误类型 impl Init<Opaque<_>, _> 来解决类型不匹配的问题。这种类型体操在 Rust 中很常见，但也反映了 pin-init API 设计的一些可改进之处。

初始化框架与宏工具

新增 warn_on_err 宏（v2）：Alexandre Courbot（NVIDIA）提交了 warn_on_err 宏的第 2 版。这个宏的作用很直观：当一个返回 Result 的函数出错时，自动打印一条内核警告日志，省得开发者每次都手写 if let Err(e) = ... { pr_warn!(...) } 这样的样板代码。Gary Guo 参与了审阅，提出了改进意见。

📬 查看补丁

按需初始化 module_kset（v3）：Shashank Balaji 提交了一组 4 个补丁，由 Gary Guo 审阅。目前内核中的 module_kset（一个管理所有内核模块在 sysfs 中展示的对象集合）是在启动早期统一初始化的。这组补丁将其改为"按需初始化"——只有当第一个模块真正需要注册到 sysfs 时才创建。这种延迟初始化可以让 Rust 模块更方便地融入现有的模块参数系统。

设备驱动：SYNOLOGY NAS 嵌入式控制器

设备驱动：Synology NAS 嵌入式控制器

Synology Microp 驱动第 10 版：Markus Probst 提交了 Synology NAS 嵌入式控制器（microcontroller，简称 microp）驱动的第 10 版，包含 2 个补丁。Synology 是知名的 NAS（网络附加存储）品牌，它的硬件上有一颗专门的微控制器芯片，负责管理硬盘指示灯、风扇转速、电源按钮等物理硬件。

这组补丁包括两部分：第一个补丁在设备树绑定（dt-bindings）中注册了 Synology microp 设备的描述信息——这就像给这个硬件写一张"身份证"，让内核知道它是什么、在哪里、怎么通信。第二个补丁是用 Rust 编写的实际驱动程序代码，实现了与微控制器的通信协议。能迭代到第 10 版说明这个驱动正在被认真审阅，离合入主线越来越近了。这也是一个很好的"用 Rust 写真实硬件驱动"的范例。

社区讨论与新人指导

社区讨论与新人指导

Zulip：如何正确使用 bindgen 生成的绑定？新人 Johnathan Koppang 在 Zulip 的 #Help 频道提问：Rust-for-Linux 的源码注释里说"不要直接使用 bindings crate"，那应该怎么调用 C 函数呢？Alice Ryhl（Google，Rust-for-Linux 核心开发者）解释说：这条规则只针对驱动程序——驱动应该通过安全的 Rust 抽象层来调用内核功能，而不是直接调用原始的 C 绑定。但在抽象层内部，当然需要使用 bindings crate，不然它存在就没意义了。Miguel Ojeda（项目维护者）也参与了讨论。这是一个很好的"为什么要分层抽象"的例子。

GitHub Issue #1233：WorkItemPointer 安全注释引用了错误的类型：onur-ozkan 报告了一个代码质量问题——在 impl WorkItemPointer for Pin<KBox<T>> 的实现中，安全性注释（SAFETY comment）引用了错误的类型名称。虽然代码本身的逻辑是正确的，但注释的准确性在内核开发中非常重要，因为审阅者和未来的维护者会依赖这些注释来理解为什么 unsafe 代码是安全的。这个 issue 目前处于 open 状态，适合新人来修复！
