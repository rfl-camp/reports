RUST 主线合并：V7.2 PULL REQUEST

Rust 主线合并：v7.2 Pull Request

发生了什么：

发生了什么：Miguel Ojeda（Rust-for-Linux 项目的主要维护者）向 Linus Torvalds 发送了将 Rust 代码合并到 Linux v7.2 内核的拉取请求。这是一个体量很大的更新，最核心的变化是引入了 zerocopy 这个第三方库（以 vendoring 的方式，即把源码直接放进内核树）。

为什么重要：在内核开发中，经常需要把一段原始的字节序列（比如从硬件读回来的数据）解释成某种结构体。以前用 Rust 做这件事，需要写大量的 unsafe（不安全）代码——就像是告诉编译器"相信我，这段代码没问题"，但这样就绕过了 Rust 的安全检查。zerocopy 库提供了安全的方式来做这种转换，相当于给这些操作加上了"安全带"。引入它之后，可以用安全代码替换掉一大批不安全代码，让内核中的 Rust 代码整体更可靠。

打个比方：以前你要把一袋混装的零件（字节）按说明书组装成成品（结构体），得自己保证不会装错，现在有了一个自动化夹具（zerocopy），它会帮你检查每个零件是否放对了位置。

️ PCI 驱动：EDU 教学设备驱动示例

️ PCI 驱动：EDU 教学设备驱动示例

补丁 1：让 Vendor::from_raw() 变成公开方法

今天最具教学价值的一组补丁来自 Maurice Hieronymus，他提交了一整套（共 4 个补丁）针对 QEMU EDU 设备的 Rust PCI 驱动示例。这个系列从底层 API 改进到最终驱动实现，环环相扣。

改了什么：之前 Vendor::from_raw() 的可见性是 pub(super)，也就是只有同一个模块内部才能用它。这意味着驱动代码只能通过内核预定义的 PCI_VENDOR_ID_* 常量来获取厂商 ID。但有些设备（比如 QEMU 的教学设备 "edu"）并没有在内核的 pci_ids.h 头文件里注册常量名。

解决方案：把 from_raw() 改为完全公开（pub），让驱动可以直接用数字厂商 ID 来创建 Vendor 对象。这样就能为没有"名字"的设备编写驱动了。Gary Guo 对此进行了 review。

补丁 2：添加托管式 Device::enable_device()

改了什么：之前 Rust PCI 绑定只有 enable_device_mem()（对应 C 里的 pcim_enable_device()），现在又加了一个 enable_device() 方法，它是"managed"的——意思是当驱动从设备上解绑时，系统会自动调用 pci_disable_device() 来清理资源。

为什么重要：想象一下你在图书馆借了一本书，"managed"模式就像图书馆有自动归还系统：你离开时书会自动还回去，不需要你记着手动还。这避免了驱动开发者忘记关闭设备导致的资源泄漏。使能计数（enable count）会在 unbind/rebind 过程中保持平衡。

内核同步原语：COMPLETION 添加 COMPLETE()

内核同步原语：Completion 添加 complete()

发生了什么：

发生了什么：Gary Guo 和 Maurice Hieronymus 合作为 Rust 的 Completion（完成量）抽象添加了 complete() 方法。之前 Rust 的 Completion 绑定只有 complete_all() 和 wait_for_completion() 两个方法。

问题是什么：complete_all() 会把一个 Completion 永久标记为"已完成"——一旦调用了它，之后所有的 wait_for_completion() 都会立即返回，不会再等待。这意味着你不能用同一个 Completion 对象反复发信号。打个比方：complete_all() 就像把交通灯永远变成绿灯，所有车都直接通过；而新添加的 complete() 则是每次只放行一辆车（唤醒一个等待者），之后灯又变红了。

为什么需要它：EDU 驱动里的中断处理需要反复通知等待者"中断来了"，每次中断只唤醒一个等待者，所以需要 complete() 这种"一次性唤醒一个"的语义。这个补丁收到了 2 个 review，说明社区对它的正确性比较重视。

️ 构建系统与工具链

️ 构建系统与工具链

doctest 函数名裁剪：提升可重复性

改了什么：Gary Guo 提交、David Gow review 的一个小补丁，修复了 Rust doctest（文档测试）在生成测试函数名时的一个问题。之前生成的函数名可能因为路径等因素在不同构建环境下不一致，导致测试结果"不可重复"——同样的代码在不同机器上编译出来的二进制不完全一样。

为什么重要：可重复构建（reproducible build）是安全和调试的基础。如果同一份源码在任何机器上编译的结果都完全相同，你就能确认"这个二进制确实来自这份源码"。这个补丁通过裁剪（trim）掉函数名中多余的部分来确保一致性。虽然改动很小，但对 CI（持续集成）系统和内核安全验证很有意义。

cargo-nok：用纯 Cargo 编译树外内核模块（社区讨论）

发生了什么：Tiago Dinis 在 Zulip 的 #Modules 频道里介绍了他的新项目 cargo-nok（No-Kbuild 的缩写）。这是一个实验性工具，目标是让开发者完全绕过内核的 Kbuild 构建系统，只用 Rust 自己的 Cargo 包管理器来编译树外（out-of-tree）内核模块。

为什么这很有意思：目前要编译一个 Rust 内核模块，你必须用内核的 Kbuild 系统（也就是 make 那一套），配置起来对新手不太友好。如果能直接用 cargo build 就搞定，开发体验会好很多——就像你写普通 Rust 项目一样。

限制和讨论：Tiago 自己也指出，并非所有 crate 都能兼容，因为内核使用的是自定义版本的 core、alloc 等基础库。但很多纯逻辑的 crate 是可以直接用的。他还 fork 了 serde（一个流行的序列化库），移除了浮点数支持后就能在内核模块里使用了——这说明不少用户态的 Rust 生态库离内核可用并不远。
