构建系统：配了 Rust 驱动却没装工具链？以后直接报错！

发生了什么：Sasha Finkelstein 提交了一个补丁，改变了当用户在内核配置中启用了 RUST=y（表示"我要用 Rust"）但系统上实际没有可用的 Rust 工具链时的行为。目前内核的做法是"悄悄地"把所有 Rust 驱动禁用掉——编译照样成功，但用户会困惑地发现自己配置的驱动不见了。这就好比你在手机设置里打开了蓝牙，结果系统偷偷把蓝牙关了还不告诉你。

为什么重要：这个补丁让构建过程在这种情况下直接失败并报错，就像缺少 OpenSSL 时编译会报错一样。这对自己编译内核的用户（比如 Linux 发行版打包者、嵌入式开发者）来说非常友好——你能第一时间知道出了什么问题，而不是装好系统后才发现驱动丢了。该补丁已经有 4 位审阅者参与了讨论。

💡 小白科普：Kconfig / RUST=y —— Linux 内核用一套叫 Kconfig 的配置系统让你选择要编译哪些功能。RUST=y 表示启用 Rust 语言支持。就像安装软件时勾选"安装额外组件"一样。 📖 了解 Kconfig

️ VIRTIO 驱动：用 RUST 写虚拟设备驱动的时代来了

️ Virtio 驱动：用 Rust 写虚拟设备驱动的时代来了

发生了什么：Manos Pitsidianakis 提交了一组共 6 个补丁的系列（v3 版本），为 Linux 内核添加了 Rust 语言的 Virtio 绑定（bindings）。Virtio 是虚拟机和宿主机之间通信的标准协议——如果你用过 QEMU 或云服务器，你的网卡、硬盘很可能就是通过 Virtio 工作的。这组补丁让开发者可以用更安全的 Rust 语言来编写 Virtio 前端驱动（也就是虚拟机里面的驱动）。

这 6 个补丁分别做了什么：

① 生成 Virtio 绑定头文件（rust/bindings）—— 当内核配置中启用了 CONFIG_VIRTIO 时，自动把 C 语言的 Virtio 头文件生成对应的 Rust 绑定，这样 Rust 代码就能调用底层的 C 接口了。

📬 查看补丁 1/6

② 添加 Virtio 辅助函数（rust/helpers/virtio.c）—— 内核中有些 Virtio 的内部 API 是用 C 宏（inline macro）实现的，Rust 没法直接调用宏，所以需要在一个辅助文件里把这些宏"包装"成普通 C 函数，Rust 才能用。

📬 查看补丁 2/6

③ 修复 Device::parent 方法的上下文返回值（rust/kernel/device）—— 这个补丁修复了一个类型系统的问题：调用设备的 parent() 方法获取父设备时，返回值的"上下文"（context）应该和调用者保持一致，但之前默认返回了 Normal 上下文。这就像你在图书馆借的书，还书时应该还到同一个图书馆，而不是默认还到总馆。

④ 添加 Virtio 核心模块（rust/kernel/virtio）—— 这是整个系列的核心，提供了 Rust 对 Virtio API 的封装。包括注册/注销 Virtio 驱动、处理 Virtqueue（虚拟队列——虚拟机和宿主机之间传数据的通道）等功能。有了这个模块，Rust 驱动开发者就有了一套安全的、符合 Rust 习惯的接口来操作 Virtio 设备。

📬 查看补丁 4/6

⑤ 为 Completion 实现可中断等待—— Completion 是内核里一种"等通知"的机制，类似于"快递到了叫我一声"。之前只能死等（不可中断），现在加了"可中断等待"，意味着等待过程中如果收到信号（比如用户按了 Ctrl+C），可以提前退出，而不是卡死在那里。这对 Virtio 驱动的健壮性很重要。

⑥ 示例驱动：virtio-rtc（WIP）（samples/rust）—— 作为概念验证，这个补丁添加了一个 Rust 编写的 Virtio 实时时钟（RTC）示例驱动。它可以通过 Virtqueue 查询时钟的能力（capabilities），但目前还没有真正注册时钟，属于半成品（WIP）。作者标注了还有一些 dead code 和缺失的 SAFETY 注释需要补全。即便如此，它已经展示了用 Rust 写 Virtio 驱动的完整流程。

⚙️ 工作队列：新增"取消同步"功能

⚙️ 工作队列：新增"取消同步"功能

发生了什么：Onur Özkan 提交了一个补丁，为 Rust 的工作队列（workqueue）模块添加了 cancel_sync（取消同步）支持。Alice Ryhl 也参与了审阅。工作队列是内核里一种"待办事项清单"机制——驱动可以把一些不需要立即完成的任务丢到队列里，让内核稍后执行。

为什么需要 cancel_sync：当一个驱动要被卸载（teardown）时，可能队列里还有没做完的任务。cancel_sync 的作用是：取消那些还没开始的任务，同时等待已经在运行的任务完成，然后才安全地释放相关资源。这就像你要退出一个群聊前，先等正在发送的消息发完，再撤回还没发的消息，最后才退群。

一个有趣的设计细节：这个功能没有为 Pin<KBox<T>> 类型实现，因为把一个装箱（boxed）的工作项放入队列时，所有权会转移给队列。既然你已经把东西交出去了，就没有一个"独立的安全持有者"可以去取消它了。

📬 查看补丁
💡 小白科普：工作队列（Workqueue） —— 内核中一种延迟执行机制，允许把不紧急的任务排队等待处理，避免阻塞关键路径。可以理解为"内核版的线程池 + 任务队列"。 📖 了解 Workqueue

PIN-INIT 库：上游同步 V7.2 第一轮

pin-init 库：上游同步 v7.2 第一轮

发生了什么：Gary Guo 提交了一组共 10 个补丁，将 pin-init 库的上游变更同步到内核树中（v7.2 版本，第一轮）。pin-init 是 Rust-for-Linux 项目里一个非常核心的库，它解决了 Rust 里一个棘手的问题：如何安全地初始化那些"不能移动"的数据结构（pinned types）。在内核里，很多数据结构一旦创建就不能挪位置（因为有指针指向它们），这个库就是专门处理这种场景的。

同步意味着什么：pin-init 同时在内核内部和外部（作为独立的 Rust crate）维护。定期把外部的改进同步回内核树，能确保内核里的版本保持最新、修复 bug、获得新特性。

📬 查看补丁系列

附带的小修复：Gary Guo 还提交了一个额外补丁，修复了 pin-init 示例代码中的一个 Clippy 警告（useless_borrows_in_formatting）。Clippy 是 Rust 的代码检查工具，类似于 C 世界的静态分析器。这个警告指出格式化字符串时有不必要的借用，虽然不影响功能，但保持代码整洁是好习惯。

📬 查看 Clippy 修复
💡 小白科普：Pin —— Rust 中的一个概念，表示"钉住"一个值使其不能被移动。内核中很多结构体（如链表节点、互斥锁）需要固定在内存中，因为其他地方持有指向它们的指针。pin-init 库让你可以安全地初始化这些"被钉住"的结构。 📖 了解 Pin

设备模型：辅助设备注册数据改进

设备模型：辅助设备注册数据改进

发生了什么：Danilo Krummrich（Rust-for-Linux 设备模型方面的核心贡献者）提交了 3 个补丁的第 2 版，为 Rust 的辅助设备（auxiliary device）抽象添加了"注册数据"（registration data）支持。

什么是辅助设备：在 Linux 内核中，一个物理设备有时需要暴露多种不同的功能。比如一块网卡可能同时支持网络和 RDMA。辅助设备机制允许一个"主驱动"创建多个"辅助设备"，然后由不同的"辅助驱动"分别管理这些功能。这次的补丁让辅助设备在注册时可以携带额外的数据，使驱动之间的信息传递更加灵活。

版本迭代：这是 v2 版本，说明作者根据上一轮审阅意见做了修改。已经有 1 位审阅者参与了讨论。

📬 查看补丁
💡 小白科普：辅助设备（Auxiliary Device） —— Linux 内核中的一种设备抽象，允许一个硬件设备拆分成多个逻辑子设备，由不同驱动分别管理。就像一台多功能打印机，打印、扫描、传真功能由不同的"子驱动"分别负责。 📖 了解辅助总线

社区讨论：kconfirm 提案引发讨论

发生了什么：Miguel Ojeda（Rust-for-Linux 项目的维护者）和 Jan Engelhardt 正在讨论一个叫 kconfirm 的 RFC（征求意见稿），目前是第 2 版。这是一个关于内核构建/配置流程的提案，旨在为内核配置过程中的某些关键选项增加确认机制。

为什么有意思：RFC（Request for Comments）阶段意味着这个想法还在早期讨论中，社区成员可以自由提出意见和建议。目前有 2 位参与者在讨论中，关于该工具的具体行为和设计细节还在你来我往地交换意见。这类讨论是开源社区决策过程的缩影——一个功能从提出到最终合入内核，往往要经过多轮这样的讨论。

️ 开发工具：RUST-ANALYZER 遇到 CONTAINER_O

️ 开发工具：rust-analyzer 遇到 container_of! 类型识别问题

发生了什么：在 Zulip 的 #Help 频道中，Jesung Yang 反馈了一个 rust-analyzer（Rust 的 IDE 智能补全工具）的问题：它突然无法正确理解 container_of! 宏返回的类型了。container_of! 是内核编程中非常常用的一个宏——当你拿到一个结构体内部某个成员的指针时，这个宏可以帮你"反推"出整个结构体的指针。

问题根因：Jesung Yang 分析认为，这可能是因为 rust-analyzer 对原始指针类型（如 *const T）上的固有方法调用（如 byte_sub、cast）的支持不够完善。好消息是已经有相关的修复补丁，应该很快就能解决。这个问题虽然不影响编译，但会让开发者在编写内核 Rust 代码时失去智能提示，影响开发效率。

📬 查看讨论
💡 小白科普：container_of! —— 一个经典的内核编程技巧。想象你在停车场看到了一辆车的后视镜，通过后视镜的位置你可以推算出整辆车停在哪里。container_of! 做的就是类似的事情：通过一个结构体成员的地址，反推出整个结构体的地址。rust-analyzer 是 Rust 语言的 LSP 服务器，为编辑器提供代码补全、跳转定义等智能功能。 📖 了解 Rust-for-Linux
