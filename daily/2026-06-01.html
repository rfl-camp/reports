串口设备总线抽象（v11，共 3 个补丁）

这组补丁为 Linux 内核的串口（Serial）设备总线提供了基础的 Rust 抽象层。简单来说，串口是电脑和外部设备之间最经典的通信方式之一——想象一下用 USB 转串口线连接单片机、调试嵌入式设备，底层走的就是串口协议。这组补丁做的事情，就是让内核开发者可以用 Rust 来编写串口设备的驱动程序，而不必只能用 C 语言。已经迭代到了第 11 版，说明社区对代码质量要求很高，经过了反复的评审和修改。参与者包括 Markus Probst、Onur Özkan 和内核维护者 Danilo Krummrich，收到了 9 条审查意见，讨论相当热烈。

LED 多色灯控制器抽象（v18，共 3 个补丁）

你手机上的呼吸灯、键盘背光灯、RGB 灯条——这些"可以变颜色的灯"在内核里由一个叫 multicolor LED classdev 的子系统管理。这组补丁就是为这个子系统编写 Rust 语言的封装接口，让驱动开发者可以用 Rust 安全地控制多色 LED 设备。这个补丁已经迭代到惊人的第 18 版，作者 Onur Özkan 非常有耐心地根据社区反馈持续改进。能坚持迭代 18 次，也说明 Rust 进入内核的门槛确实不低，但社区对代码质量的追求值得敬佩。

I2C 适配器引用计数双重递增修复（v3）

这是一个 bug 修复补丁，作者 Nicolás Antinori 发现了 Rust I2C 驱动封装中的一个引用计数（refcount）问题。问题出在 I2cAdapter::get 这个函数：当它调用 C 函数 i2c_get_adapter() 时，引用计数已经加了 1；但随后代码把裸指针转换成 Rust 的 ARef 智能指针时，又会自动再加 1——这就导致引用计数被多加了一次。这就好比你借了一本书，图书馆登记了一次，结果你的借书卡上又自动登记了一次，导致你得还两次才能注销。虽然这不会让系统崩溃，但会导致资源永远不会被正确释放（内存泄漏）。修复方法是避免这次多余的引用计数递增。

同步与并发

SRCU 同步机制的 Rust 抽象（v7，共 4 个补丁）

SRCU（Sleepable Read-Copy-Update）是 Linux 内核中一种高级的同步机制。普通的锁就像一扇门——你进去了别人就得等；而 RCU 更像是"大家都可以看报纸（读），但换报纸（写）时要巧妙地先准备好新报纸再替换"，读操作几乎没有开销。SRCU 是 RCU 的一种变体，允许在等待的过程中"睡觉"（阻塞），这在某些场景下是必须的。这组补丁由 Onur Özkan 编写，RCU 子系统的权威维护者 Paul E. McKenney 和 Rust-for-Linux 项目负责人 Miguel Ojeda 都参与了评审，说明这个抽象的重要性很高。能在 Rust 中安全地使用 SRCU，意味着用 Rust 写的内核模块可以享受到这种高性能的无锁并发保护。

构建系统与工具链

构建系统与工具链

kbuild：将长类型名文件纳入清理目标（v3）

Rust 编译器有时会生成一些文件名很长的临时文件（*.long-type-*.txt），这些文件是用来记录 Rust 那些"超级长的类型签名"的——Rust 的泛型嵌套起来类型名可以长到令人发指。这些文件在编译后其实就没用了，但之前执行 make clean（清理编译产物）时，这些文件不会被自动删除，日积月累就会占用空间、干扰开发。Miguel Ojeda 提交的这个补丁把这类文件加入了 kbuild（内核构建系统）的清理规则，这样一运行 make clean 就会自动打扫干净，保持源码目录整洁。虽然是个小改动，但对日常开发体验很重要。

x86 架构：支持 Rust 1.98.0 及更高版本的目标规范

Rust 编译器会不定期更新它的"目标规范"（target spec），也就是告诉编译器"我要生成的代码是给什么样的 CPU/平台用的"这份配置。Rust 1.98.0 版本对 x86 架构的目标规范做了一些修改，而内核编译需要使用自定义的目标规范，所以这个补丁就是让内核的构建系统兼容新版 Rust 编译器的变化。Miguel Ojeda 提交了补丁，确保使用 Rust 1.98.0 或更新版本时，内核仍然能正确编译。这类补丁虽然不涉及功能变化，但对于"跟上 Rust 上游"至关重要——毕竟你不希望更新了 Rust 编译器之后内核就编译不了了。

ANDROID BINDER 驱动

Android Binder 驱动

rust_binder：修复 offsets 数组的遍历步长问题（v2）

Android 系统的核心进程间通信（IPC）机制叫做 Binder——所有 App 之间的数据传递都要经过它，可以说是 Android 的"神经系统"。Rust-for-Linux 社区正在用 Rust 重写 Binder 驱动（即 rust_binder）。Hyunwoo Kim 发现了一个关于内存遍历步长的 bug：在 Binder 清理资源时，需要遍历一个 offsets 数组，数组中每个元素是 binder_size_t 类型（固定 8 字节 / u64）。但代码用了 usize（与平台相关的大小）作为步长。在 64 位系统上 usize 刚好也是 8 字节，没有问题；但在 32 位系统上，usize 只有 4 字节，这意味着每次只跨 4 字节去读一个 8 字节的条目——就像你看日历每次翻半页，内容全都错位了。修复方法很直接：把步长和读取类型都改为 u64，保证在所有平台上行为一致。

RUST 宏与语言特性

Rust 宏与语言特性

用 const expect 替换 match + panic 模式

Daniel del Castillo 提交了一个代码改进补丁，针对的是内核 Rust 代码中过程宏（proc macro）的写法。在某些需要在编译期（const context）做计算的地方，以前用的是 match 加 panic! 的写法——也就是"如果结果不对就直接崩溃"。这种写法虽然能用，但不够简洁优雅。新补丁改用 Rust 较新提供的 const expect 特性，代码更简洁、意图更清晰：直接说"我期望这个值存在，不存在就报错"。就好比从"如果钥匙不在门口，就大喊一声然后倒下"变成了"期望钥匙在门口"——含义一样，但表达简洁多了。这类改动虽然不影响功能，但能让内核 Rust 代码更地道、更易读。

GitHub Issue #2：内核需要的 Rust 不稳定特性清单

这是一个由项目负责人 Miguel Ojeda（ojeda）维护的长期追踪 Issue，列出了 Linux 内核中使用到的所有 Rust 不稳定特性（unstable features）。Rust 语言分为稳定版和 nightly 版，很多实验性功能只有 nightly 才有（比如内联汇编的高级用法、自定义内存分配器等）。内核开发天然需要很多底层能力，所以不可避免地会用到一些还没有"转正"的 Rust 特性。这个 Issue 的意义在于：它帮助 Rust 语言团队了解哪些特性对内核开发最重要、应该优先稳定化，同时也让内核开发者清楚地知道自己依赖了哪些"不稳定的地基"。如果你想了解 Rust 进入内核的最大技术障碍之一，这个 Issue 是必读材料。
