️ GPU / DRM 驱动（Nova Core 系列）

Blackwell: 修正系统内存刷新寄存器

今天 GPU 驱动方向是当之无愧的主角。nova-core 是社区正在用 Rust 为 NVIDIA GPU 编写的全新开源驱动，目标是替代现有的 C 语言 nouveau 驱动。今天一口气推进了多个 v11 版本的补丁，涵盖了 Hopper（H100 系列）和 Blackwell（B 系列）两代 GPU 架构。

Alexandre Courbot 和 John Hubbard 提交的这组补丁（共 22 个）修正了 Blackwell 架构 GPU 使用的 sysmem flush register（系统内存刷新寄存器）。简单来说，GPU 和 CPU 共享系统内存时，需要通过特定的硬件寄存器来保证数据一致性——就像两个人同时编辑一个文档，需要有个"同步按钮"来保证看到的是最新版本。这个补丁确保 Blackwell 架构使用了正确的寄存器地址，避免数据不一致导致的渲染错误或系统崩溃。这已经是第 11 版，经过了 5 轮审查，说明社区对硬件寄存器操作的正确性要求非常高。

📬 查看补丁
Blackwell: 计算 PMU 预留显存大小

同一系列中的另一组补丁处理的是 PMU（Performance Monitoring Unit，性能监控单元）预留显存的计算问题。GPU 的显存并不是全部给用户程序使用的，有一部分需要留给固件和监控单元。这个补丁确保 Blackwell 架构能正确计算出 PMU 需要保留多少显存，类似于你买了 8GB 内存的手机，但系统本身要占掉 1-2GB——驱动需要精确知道这个"系统占用"有多大，才不会把显存分配得超出实际可用范围。

Hopper/Blackwell: FSP 安全启动完成等待

现代 GPU 启动时有一个安全启动流程，由 FSP（Falcon Security Processor） 负责——可以把它想象成 GPU 里面的一个"安全卫士"，在 GPU 正式工作之前先检查固件是否被篡改。这个补丁为驱动添加了等待 FSP 安全启动完成的逻辑：驱动需要耐心等 FSP 说"OK，一切安全"之后才能继续初始化 GPU，否则可能在不安全的状态下运行。

Hopper/Blackwell: FMC 签名提取

继续安全启动的话题。FMC（First Microcontroller） 是 GPU 启动时第一个运行的微控制器，它的固件带有数字签名。这个补丁让驱动能够从硬件中提取 FMC 的签名信息，用于验证固件的真实性。这就好比你下载一个软件后，系统会检查它的数字签名来确认"这确实是官方发布的，没有被人偷偷改过"。

📬 查看补丁
Hopper/Blackwell: 扩大 non-WPR 堆

GPU 的固件在显存中有一块叫做 WPR（Write-Protected Region） 的受保护区域，普通程序不能写入。但在这块区域之外，还需要一些"非保护堆内存"（non-WPR heap）给固件做临时数据存储。这个补丁把这块区域的大小调大了，因为新一代 GPU 固件更复杂，需要更多的临时工作空间——就像搬到更大的办公室，因为团队人多了，需要更多桌子。

Timur Tabi 参与的这个补丁为 FSP 的 Falcon 引擎添加了一个"存根"（stub）实现。Falcon 是 NVIDIA GPU 内部的一种专用微处理器，负责执行各种管理任务。现阶段先放一个最基本的框架进去，后续再逐步填充完整的功能——就像盖房子先把框架搭好，再慢慢装修。这种渐进式开发方式让代码更容易被审查和合并。

内存管理与同步原语

内存管理与同步原语

DMA Fence Rust 抽象（4 个补丁）

Boris Brezillon、Alice Ryhl 和 Philipp Stanner 等人提交的这组补丁为内核的 DMA fence 机制添加了 Rust 抽象。DMA fence 是 GPU 编程中极其重要的概念——当 CPU 让 GPU 去做一件事（比如渲染一帧画面），CPU 怎么知道 GPU 做完了？答案就是 DMA fence，它就像一个"完成信号"，GPU 做完任务后会"发射"这个信号，CPU 收到后才知道可以继续下一步。这组补丁收到了 13 条审查意见，可见社区对这个核心抽象非常重视。用 Rust 来实现可以借助类型系统和生命周期检查，避免 C 代码中常见的"忘记等信号就继续执行"之类的 bug。

📬 查看补丁
RCU: 添加 RcuBox 类型（4 个补丁）

Philipp Stanner 和 Boqun Feng 提交了一组补丁，为 Rust 内核代码引入了 RcuBox 类型。RCU（Read-Copy-Update）是 Linux 内核中一种非常巧妙的并发读写机制：当很多线程需要读取同一份数据时，RCU 允许它们无锁地自由读取；当有人要修改数据时，先复制一份新的，改完后再替换旧的。RcuBox 就是把这种机制封装成一个安全易用的 Rust 类型，就像你用智能指针（如 Arc）一样自然地使用 RCU 保护的数据。

Sync: 引入 LazyInit v2（2 个补丁）

Alice Ryhl 提交的 LazyInit 是一个延迟初始化类型。有些内核对象在创建时还不知道该初始化成什么值，需要到后面某个时刻才能确定——比如一个驱动对象，可能在注册阶段才能获得硬件信息来完成初始化。LazyInit 提供了一个安全的容器来处理这种"先创建、后初始化"的场景，同时保证你不会在初始化之前就去使用它（Rust 编译器会帮你检查这一点）。这已经是第 2 版，说明社区在接口设计上正在反复打磨。

设备驱动与子系统抽象（I2C / IIO）

[RFC] I2C: 为 I2cClient 实现 Io trait

Jonathan Cameron 和 Muchamad Coirul Anwar 正在为 Linux 的 I2C 子系统编写 Rust 抽象。I2C 是硬件世界中最常见的通信协议之一——你的手机里，触摸屏和主芯片之间、传感器和处理器之间，很多都是用 I2C 通信的。这个 RFC 补丁为 I2cClient（代表一个 I2C 设备）实现了 kernel::io::Io trait，让 Rust 驱动可以用统一的 I/O 接口来读写 I2C 设备的寄存器，而不用每次都写底层通信代码。目前还在 RFC（征求意见稿）阶段，已经是第 3 版，社区正在审查 API 设计是否合理。

[RFC] IIO 子系统最小 Rust 抽象

同一组作者还在推进 IIO（Industrial I/O，工业 I/O） 子系统的 Rust 抽象。IIO 是 Linux 中专门用来管理各种传感器（加速度计、温度传感器、光线传感器等）的框架。这个补丁提供了最小可用的 Rust IIO 抽象，让 Rust 驱动开发者能够注册 IIO 设备、定义通道和读取传感器数据。这为将来用 Rust 写更多传感器驱动打下了基础。

⚙️ 内核模块与参数

⚙️ 内核模块与参数

module_param: 参数值改为按值返回 v2

Gary Guo 和 Andreas Hindborg 提交的这个补丁改进了 Rust 内核模块获取参数值的方式。当一个模块参数的类型实现了 Copy（比如 i32、bool 这些简单类型），之前调用 value() 返回的是一个引用（&T），但对于这种可以直接复制的小数据，按值返回（直接给你一份副本）更方便、更符合 Rust 的使用习惯。新版本把原来的方法改名为 value_ref()，新的 value() 直接返回值的副本。这是一个提升 API 人体工学（ergonomics）的改进——让代码写起来更自然。

📬 查看补丁
kernel: param: 在 pure_initcall 中初始化 module_kset v6

Shashank Balaji 提交的这个补丁修改了 module_kset 的初始化时机。module_kset 是内核中管理所有模块的容器，之前的初始化时机可能在某些场景下太晚了，导致依赖它的代码出问题。补丁把初始化移到 pure_initcall 阶段——这是内核启动过程中非常早期的一个阶段。就像你开店之前得先把货架摆好，这个补丁确保"模块管理架"在大家需要用之前就已经就位了。这已经是第 6 版，说明初始化顺序在内核中是个非常敏感的问题，稍有不慎就会影响启动流程。

kbuild: 清理 *.long-type-*.txt 文件 v3

Joel Kamminga 提交、经 Miguel Ojeda 和 Nathan Chancellor 审查的这个补丁改进了 Rust 内核构建系统（kbuild）的清理机制。Rust 编译器在编译过程中会生成一些 *.long-type-*.txt 文件——这些是当 Rust 类型名过长时编译器自动创建的辅助文件（Rust 的泛型类型名可以变得非常非常长！）。之前执行 make clean 时这些文件不会被清理掉，日积月累就会占用空间。这个补丁把它们加入了清理目标列表，让 make clean 能正确删除它们——就像给打扫卫生的阿姨多加了一个"别忘了擦窗台"的提醒。

在 zerocopy 频道中，Jack Wrenn（zerocopy 库的维护者）问 Alice Ryhl：要支持"静默失败的 derive"（即 derive 宏如果条件不满足就静默跳过而不报错），需要依赖 Rust nightly 的 trivial_bounds 特性。Alice 提出了一个聪明的替代方案：使用 for<'a>（高阶 trait bound）的 workaround 来绕过 trivial bounds 的限制——即使 where 子句中没有出现任何生命周期参数，加上 for<'a> 也能避免编译器报 trivial bounds 错误。这种技巧性的解决方案避免了对 nightly 特性的依赖，对内核的稳定性很重要。

RISC-V 内存管理：修复 PROT_WRITE 权限设置 v23

Andreas Schwab 和 Deepak Gupta 提交的这个补丁修复了 RISC-V 架构上的一个内存权限问题。在 Linux 中，当一个程序申请一块"可写"的内存（PROT_WRITE），内核应该同时授予读和写权限（VM_READ | VM_WRITE）——因为你几乎不可能"只写不读"一块内存（想想看，你怎么往一个地方写数据却不能读它？）。但在 RISC-V 架构上这个行为之前不太对，这个补丁进行了修正。这是一个庞大的系列，共 28 个补丁，已经到了第 23 版，说明跨架构的内存管理修复确实复杂。虽然这个补丁本身是 C 代码的修复，但它出现在 Rust-for-Linux 邮件列表上，可能是因为它影响了 Rust 代码依赖的内存映射行为。
