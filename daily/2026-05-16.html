GPU 驱动 · NOVA-CORE 卸载流程大重构

GPU 驱动 · Nova-core 卸载流程大重构

补丁 1：移除多余的代理函数

今天 Nova 驱动（NVIDIA 开源 GPU 驱动的 Rust 实现）迎来了一组非常重要的补丁——驱动卸载（unload）流程。这组补丁共 7 个，已经迭代到第五版，由 NVIDIA 的 Alexandre Courbot 主导开发。

先说背景：当你在 Linux 里"卸载"一个驱动时（比如用 rmmod 命令），理想情况下驱动应该把自己占用的所有资源都清理干净。但之前 Nova 驱动卸载时，GPU 上的一个叫 GSP（GPU System Processor） 的小处理器还在继续运行，而且 GPU 固件用的一块受保护内存（WPR2 区域）也没有被释放。这就好比你关了电脑上的应用程序，但应用程序的后台进程还在偷偷跑着、还占着你的内存——不仅浪费资源，而且重新加载驱动时会出问题（因为那块内存还被占着，没法重新初始化）。更严重的是，如果系统没有 IOMMU 保护，GSP 可能会继续访问已经被内核回收的共享内存区域，造成安全隐患。

第一个补丁做了一点代码整理：删掉了一个叫 get_gsp_info 的"中间人"函数。这个函数在早期开发中有用，但自从通用的命令队列发送方法合并之后，它就变成了多余的样板代码。现在直接用正确的方式把 GetGspStaticInfo 命令放进队列即可。这就像把一个不再需要的"转接头"拆掉，让数据直接流通。

补丁 2：固件命令不再全量导入

之前 GSP 命令模块会把所有固件命令（fw commands）全部导入，导致你看代码时分不清一个命令到底是固件层的还是 GSP 层的。而且如果两层恰好有同名命令，就会冲突。这个补丁停止了"一股脑全导入"的做法，让代码层次更清晰。这是一个很好的软件工程实践——命名空间隔离，就像你整理书架时把教科书和小说分开放一样。

📬 查看补丁
补丁 3：卸载时发送 UNLOADING_GUEST_DRIVER 命令

这是整组补丁的核心之一。驱动卸载时，现在会向 GSP 发送一条 UNLOADING_GUEST_DRIVER 命令，告诉 GSP "我（驱动）要走了，你别再访问我们之间共享的内存了"。如果没有这一步，GSP 可能继续读写已被内核回收的内存，就像你搬走了但没告诉室友，室友还往你房间里放东西一样，特别是在没有 IOMMU（一种硬件内存隔离机制）的系统上会很危险。

补丁 4：重构 SEC2 引导加载流程

这个补丁由 John Hubbard（同样来自 NVIDIA）编写，把 SEC2（一种安全引擎）的 reset/load/boot 三步操作封装进了一个 BooterFirmware::run() 方法。这主要是重构（代码行为不变，但结构更好），目的是为后续添加 FSP（Falcon Security Processor）引导路径做准备。就像先把厨房整理干净，再开始做新菜。

📬 查看补丁
补丁 5 & 6：启动代码分层——引入硬件抽象层（HAL）

GSP 的启动过程中，有些步骤对所有 NVIDIA GPU 都一样（比如发送启动后的初始化消息），但有些步骤因芯片架构不同而不同。补丁 5 先把"跟芯片相关的代码"挪到一起，补丁 6 则正式把它们抽到一个 HAL（硬件抽象层）里。目前 Turing 和 Ampere 两代架构差异不大，但未来要支持 FSP 引导时差异会很大，提前做好抽象是明智之举。这就好比你造一辆车，把发动机接口标准化，以后换发动机就方便了。

补丁 7：卸载时运行 Booter Unloader 和 FWSEC-SB

最后一个补丁完成了卸载流程的最后一环。加载驱动时，FWSEC-FRTS 固件会在显存中创建一个叫 WPR2 的安全区域来存放 GSP 固件，Booter Loader 会把固件加载进去。卸载时就要做反向操作：先运行 Booter Unloader 让 GSP 退出 RISC-V 运行模式，再运行 FWSEC-SB 清除 WPR2 区域。这样下次加载驱动时就能干净地重新初始化了。整个流程形成了完整的"加载-运行-卸载"生命周期。

寄存器定义该放哪？

DMA 同步机制 · DMA_FENCE RUST 抽象

DMA 同步机制 · dma_fence Rust 抽象

Philipp Stanner 和 Onur Özkan 提交了 dma_fence 的 Rust 安全抽象的第三版 RFC（征求意见稿）。dma_fence 是 Linux 内核中非常重要的一个同步原语——你可以把它想象成一个"承诺"：GPU 上的某个操作完成后，这个 fence 就会被"触发"（signalled），其他等待这个操作结果的代码就知道可以继续了。

这套框架有几条严格的规则：fence 只能触发一次；所有 fence 最终都必须被触发（不能永远挂着不完成）；错误码必须在触发之前设置好。这些规则在 C 语言里全靠开发者自觉遵守，稍有不慎就会导致 GPU 死锁或者内核崩溃。用 Rust 的类型系统来包装后，这些规则就变成了编译期的检查——你违反规则，代码就编译不过。这对所有 Rust GPU 驱动都至关重要，因为 GPU 渲染、视频解码、显示输出都依赖这个同步机制。

目前这还处于 RFC 阶段，也就是说社区还在讨论接口设计是否合理，欢迎有兴趣的同学参与评审。

内核安全 · 指针隐藏与权限检查

内核安全 · 指针隐藏与权限检查

防止内核地址泄漏：指针格式化改进

开发者 Ke Sun 提交了一个很有安全意义的补丁：在 Rust 内核代码中，当你用 {:p} 格式化输出一个指针时，默认会打印出真实的内存地址。这个地址如果被攻击者看到，就能用来绕过 KASLR（内核地址空间布局随机化，一种重要的安全防护机制）。

这个补丁定义了一个自定义的 kernel::fmt::Pointer trait 和一个 HashedPtr 包装类型，让 {:p} 自动走内核的 %p 哈希格式——也就是说打印出来的是一个经过哈希处理的假地址，人类看起来像个地址但实际上无法被利用。这就像把你家的门牌号加密了，快递员能送到，但小偷看不出你家在哪。

📬 查看补丁
不可信数据抽象

Alistair Francis 提交了一组共 18 个补丁，为内核引入了"不可信数据"（untrusted data）的 Rust 抽象。这是什么意思呢？在内核中，有些数据来自用户空间或者外部设备，是"不可信"的——你不能假设它们的值是合理的，必须先验证才能使用。这个抽象用 Rust 的类型系统把"可信"和"不可信"的数据区分开来：一个 Untrusted<T> 类型的数据，你必须先对它做验证（检查范围、格式等），才能拿到里面真正的值。这就像快递到了先要拆开检查，确认没问题才能签收。这种做法能在编译期就防止开发者忘记做输入验证。

📬 查看补丁
capable() 和 ns_capable() 安全抽象

Miguel Ojeda（Rust-for-Linux 项目的核心维护者）参与审查了一组为 capable() 和 ns_capable() 添加 Rust 安全抽象的补丁。这两个函数是内核中检查"当前进程有没有某种特权"的核心接口——比如检查一个进程是否有权限加载内核模块、修改网络配置等。为它们写 Rust 绑定意味着 Rust 驱动可以安全地做权限检查了，不需要直接调用 C 函数。

️ 架构支持 · ARM 与 RUST 的兼容性

️ 架构支持 · ARM 与 Rust 的兼容性

ARM 架构：KASAN 启用时禁用 Rust

Miguel Ojeda 提交了一个补丁，当 ARM（32 位）架构上启用了 KASAN（内核地址消毒器）时，不再允许同时启用 Rust 支持。KASAN 是一个强大的内存错误检测工具，能帮你找到越界访问、使用已释放内存等 bug。但问题是，KASAN 的实现方式跟 Rust 的编译工具链在 32 位 ARM 上还不兼容——两者同时开启会导致编译失败或运行时出问题。所以目前的解决方案是"二选一"：要么用 KASAN 调试 C 代码，要么用 Rust 写驱动，暂时不能同时用。这个限制只影响 32 位 ARM，64 位的 ARM64（aarch64）不受影响。

📬 查看补丁
64 位除法在 32 位平台上的难题

Zulip 的 General 频道里，Demi Obenour 讨论了一个底层问题：在 32 位 ARM 上执行 64 位整数除法（比如两个 u64 相除）需要调用一个叫 __aeabi_uldivmod 的辅助函数。问题是 Rust 编译器生成的代码可能会隐式调用这个函数，但内核环境中它可能没有被正确提供。Demi 的提议是干脆让这个符号保持未定义，这样如果有代码试图做 64 位除法就会在链接阶段直接报错，而不是运行时出神秘 bug。这是一个很"底层"的问题，但对保证 Rust 代码在嵌入式 ARM 设备上正确运行很重要。

类型系统改进 · PHYSADDR 新类型

类型系统改进 · PhysAddr 新类型

kernel test robot 报告了一个关于 PhysAddr（物理地址）类型转换的补丁的测试结果。这个补丁将 PhysAddr 从一个简单的类型别名（type PhysAddr = u64）转换为一个新类型（newtype）包装（struct PhysAddr(u64)）。

为什么要这么改？类型别名只是给现有类型起了个新名字，编译器不会区分它和原类型——你可以把一个普通的 u64 数字（比如文件大小）直接当物理地址用，编译器不会报错。但如果用 newtype，编译器就知道"物理地址"和"普通数字"是不同的东西，你不能混着用。这就像把"人民币"和"美元"区分开来——虽然都是数字，但你不能直接把 100 人民币当 100 美元花。这种改进能在编译期就防止一大类"地址搞混"的 bug。

DRM 图形栈 · Asahi（Apple Silicon）进展

在 Zulip 的 DRM 频道，Lyude（Red Hat 的图形栈开发者）提到她将在周五发出关于 Asahi GEM SHMEM 修改的补丁。Asahi 是为 Apple Silicon（M1/M2 等芯片）开发的 Linux GPU 驱动，也是用 Rust 编写的。GEM SHMEM 是 DRM 子系统中管理 GPU 内存的一种机制，使用共享内存（shmem）作为后端。这意味着 Asahi 驱动的内存管理即将有新的改进。虽然今天只是一个简短的状态更新，但值得关注——Apple GPU 的 Rust 驱动和 NVIDIA GPU 的 Rust 驱动是目前社区最活跃的两个前沿项目。
