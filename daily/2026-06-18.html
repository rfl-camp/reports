GPU / 显卡驱动（nova-core）

nova-core 是社区正在用 Rust 重写的 NVIDIA 开源显卡驱动。今天的核心人物是 Alexandre Courbot，他提交了一大组围绕"开机和显存"的补丁，标题统一叫 obtain and display VRAM amount v2（获取并显示显存容量，第 2 版）。这组补丁拆成了好几块循序渐进地做。

第一块是把"如何向 GSP 询问显卡静态信息"这件事，从原来藏在 Gsp::boot 里、拿到结果却没法优雅地传回去的写法，单独抽成 Gsp 的一个专门方法，只要 GSP 一启动就能随时调用。这是典型的重构：功能不变，但代码结构更清爽，方便后面复用。

第二块把"卸载 GSP 所需的状态"从 Gpu 结构体里搬出来，做成一个独立的、固定在内存里的子对象（pinned subobject）。为什么要这么做？原来的写法要求"卸载用的字段"必须最后一个初始化——一旦 GSP 启动成功但后面某步又失败了，Gpu 就处于"半初始化"的尴尬状态，负责清理的 PinnedDrop 析构逻辑还跑不起来，等于该清理的没清理。把它独立出来就解决了这个先后顺序的坑，让出错时也能正确收尾。

第三块（由 Joel Fernandes 贡献）给 GspStaticConfigInfo 加了个 usable_fb_regions() 方法，专门从 GSP 返回的 fbRegionInfoParams 里挑出"真正可用的显存区域"——也就是那些没有被系统保留、也没被保护起来的部分。提取出来的区域会被存好并暴露给驱动其他地方使用。简单说，就是让驱动搞清楚"这块显卡上到底有多少显存是我能随便用的"，这个信息开机时会打印出来，将来还可能作为参数用。

📬 可用显存区域补丁

另一条线由 Eliot Courtney 主导，是一组 13 个补丁的"健壮性加固"工作，主要针对 FSP（Falcon 安全处理器）通道和 GSP 启动过程。具体包括：尝试强制对 FSP 通道的独占访问（避免多方同时乱用同一个通道）、捕捉"队列指针出错"这类异常情况（指针指错地方时能及时发现而不是默默出事），以及在出错时也要保住 FMC 启动参数所在的那块 DMA 内存别被提前释放。这些都是在打磨开机流程的边角，让显卡在异常情况下不至于直接翻车。

📬 提取可用 FB 区域
💡 小白科普
· GSP（GPU System Processor）：现代 NVIDIA 显卡里的一颗小处理器，跑着自己的固件，主机驱动很多操作（比如查询硬件信息）其实是"发命令给 GSP，让它代办"。
· VRAM（显存）：显卡上专用的内存，用来放纹理、画面缓冲等数据，和你电脑的普通内存是分开的。维基百科：VRAM

️ DRM / 显示子系统（新提议）

️ DRM / 显示子系统（新提议）

Mike Lothian 发了一组 RFC（征求意见稿）：rust: drm: minimal KMS bindings, EDID read, rotation, HDCP defs。意思是给 Rust 驱动提供"刚好够用"的一套 KMS（内核模式设置）接口，让一个 Rust 写的显示驱动能真正点亮屏幕、跑通一条最简单的显示流水线。

具体来说，它借助内核现成的 drm_simple_display_pipe 辅助工具，搭出"一个 CRTC + 主图层 + 编码器"这样最小的原子模式设置管线（atomic mode-setting），并且能从显示器自己的传输通道真正读取 EDID（显示器自报家门的信息，比如分辨率、刷新率）。系列里还带了显示器旋转和 HDCP（内容保护）相关的定义。因为是 RFC，目前还处在"大家先看看思路对不对"的阶段，已有 2 位 reviewer 参与。

📬 查看 DRM RFC
💡 小白科普
· KMS（Kernel Mode Setting）：由内核负责设置屏幕分辨率、刷新率、画面输出的机制；"原子（atomic）"指一次性把所有显示参数一起改好，要么全成功要么全不变，避免画面闪烁撕裂。维基百科：KMS
· EDID：显示器通过线缆告诉电脑"我是谁、支持哪些分辨率"的一小段数据。

⚙️ 工作队列与并发

⚙️ 工作队列与并发

Onur Özkan 今天在 workqueue（工作队列）上连推两项功能。第一项是 ScopedQueue：支持"生命周期受限"的任务项，已到 v2。普通的工作队列要求你提交的任务在内存里活得足够久，而 ScopedQueue 允许提交那些只在某个作用域内有效的任务，由 Rust 的生命周期机制来保证安全。相比 v1，这一版去掉了原来 *with_lt 这类命名，在 ScopedQueue::enqueue 里补了详细的安全注释，还加上了 Suggested-by 致谢标签——可以看出是在 reviewer 建议下逐步打磨的，目前已有 5 条评审意见，Danilo Krummrich、Gary Guo 等核心成员都参与了。

📬 ScopedQueue v2

第二项是 cancel_sync 支持，已到 v3，也就是"同步地取消一个已排队的工作项"。这一版把原来的 trait 名字从 SupportsCancelling 改成更简洁的 SupportsCancel，改进了 from_raw_work 的文档注释，并去掉了 addr_of_mut! 的用法。往前追溯，v1 引入了 SupportsCancelling trait 给 from_raw_work 函数用、并把 from_raw_work 从 WorkItemPointer 里移了出来。这类"取消任务"的能力对驱动很关键——比如设备拔出时，得能干净地把还没执行的回调取消掉。

📬 cancel_sync v3

在 Zulip 的 #General 频道，Andreas Hindborg 和 Boqun Feng 讨论了 "带中断的自旋锁（Spinlocks with IRQs）"。Andreas 想动手实验，连着问了几个很实在的问题：要测试是不是先打上那个 C 的补丁系列、再打 Rust 的？Boqun 手上有没有把全部补丁都合好的代码树？或者有没有人已经把它们 rebase 到 v7.1 分支上、可以直接拿来测？这其实反映了新人参与内核测试常遇到的门槛——补丁散落在不同系列里，光是"把环境搭起来"就是一道坎。

💬 查看讨论
💡 小白科普
· 工作队列（workqueue）：内核里"稍后再做"的机制——把不急着立刻干、或不能在中断里干的活儿丢进队列，由后台线程慢慢执行。内核文档：workqueue
· 自旋锁（spinlock）：一种"忙等"的锁，拿不到锁就原地空转反复尝试，适合极短的临界区；"带 IRQ"的版本会同时关掉中断，防止中断处理程序和它抢同一把锁造成死锁。

加密支持（新提议）

加密支持（新提议）

Mike Lothian 还发了一组加密相关的 RFC：rust: crypto: library AES-128 / SHA-256 / HMAC + RSA。目标是搞一个小而可复用的 kernel::crypto 模块，让内核里的 Rust 代码能直接做哈希、加密单个数据块、以及 RSA 公钥加密。

系列分两个补丁：第 1 个绑定内核现成的加密库，提供 sha256()、hmac_sha256() 和 Aes128（单块 ECB 模式加密）；第 2 个通过 crypto_akcipher 接口提供 Akcipher 和 rsa_pubkey_encrypt()（RSA 公钥加密）。值得注意的是，内核加密领域的资深维护者 Eric Biggers 出现在了 reviewer 名单里——这类涉及密码学的代码通常审得很严，因为一旦实现有误就是安全隐患。Miguel Ojeda 也参与了讨论。

📬 RSA 公钥加密
💡 小白科普
· SHA-256 / HMAC：SHA-256 是把任意数据压成固定长度"指纹"的哈希算法，用于校验数据是否被篡改；HMAC 则在哈希里掺入一把密钥，用来验证消息"确实是知道密钥的人发的"。维基百科：HMAC
· 绑定（bindings）：让 Rust 能调用内核已有 C 代码的一层"翻译接口"，这样不用重写算法，直接复用内核成熟的加密库。

USB 设备驱动

USB 设备驱动

USB 这块有两条动态。一条是 Alice Ryhl 的 把 Device 和 Interface 的方法标记为 inline（内联）。这是个性能/代码体积的微优化：告诉编译器把这些小函数直接"展开"到调用处，省去函数调用开销。这种补丁看着小，但参与评审的人不少——Danilo Krummrich、Greg Kroah-Hartman（USB 子系统的大佬）等共 6 位都看了。

📬 USB inline 补丁

另一条是 Mike Lothian 的 RFC：rust: usb: add synchronous bulk transfer support（同步批量传输支持），这是一个 9 个补丁组成的大系列里的第一部分。批量传输（bulk transfer）是 USB 用来传大块数据的方式，比如 U 盘读写、打印机传文件。"同步"意味着调用后会一直等到传输完成才返回，写起来直观。Danilo Krummrich 参与了讨论。这同样处于早期 RFC 阶段。

📬 USB 批量传输 RFC
💡 小白科普
· 批量传输（bulk transfer）：USB 四种传输模式之一，专门用来可靠地传大量数据（不保证实时，但保证不出错），U 盘、移动硬盘都靠它。维基百科：USB 传输类型
· inline（内联）：编译器优化手段，把短小函数的代码直接塞进调用点，减少调用开销。

内存管理

内存管理

Alice Ryhl 的 rust: page: convert to Ownable 已经迭代到了惊人的 第 17 版（10 个补丁），堪称今天的"长跑选手"。它把内核里的"内存页（page）"抽象改造成实现 Ownable 这个所有权 trait 的形式。简单说，就是用 Rust 的所有权模型来更安全地管理"这一页内存归谁、谁负责释放"，避免出现重复释放或忘记释放的内存 bug。能反复打磨到 17 版，说明这是块涉及面广、必须极其谨慎的基础设施，社区在反复推敲细节。

📬 page → Ownable v17
💡 小白科普
· 内存页（page）：操作系统管理内存的最小单位，通常 4KB 一块，内核分配、回收内存都是以页为单位进行的。维基百科：内存页
· 所有权（Ownership）：Rust 的招牌特性，每块资源都有唯一的"主人"，主人离开作用域时资源自动释放，从根上杜绝内存泄漏和悬空指针。Rust Book：所有权

构建系统与宏

构建系统与宏

Nicolas Schier 的 kbuild: Replace and dissolve procmacro-extension variable，已到 v2 是一个构建脚本的小清理。它改用 make 的 $(basename) 函数和"替换引用"语法，来从过程宏目标里提取 crate（Rust 包）名称，替代原来的 $(patsubst) 写法。由于 procmacro-extension 这个变量全工程只有一处用到，干脆就地把提取逻辑写进去、再把这个变量删掉。属于"减少一个不必要的中间变量、让 Makefile 更直白"的整理活儿，Miguel Ojeda 参与评审。

📬 kbuild 清理 v2

Malte Wechter 的 rust: add procedural macro for declaring configfs attributes，已到 v3 引入了一个过程宏，用来更方便地声明 configfs 属性。configfs 是内核里一种"用文件/目录来配置内核对象"的机制。有了这个宏，开发者就不用手写一堆样板代码，写几行声明就能自动生成对应的属性处理逻辑——就像用注解（annotation）省去重复劳动。Miguel Ojeda 参与评审。

📬 configfs 宏 v3
💡 小白科普
· 过程宏（procedural macro）：Rust 里能在编译期"自动生成代码"的工具，你写一行声明，它帮你展开成几十行重复代码。Rust 文档：过程宏
· configfs：内核提供的一套用"创建目录、写文件"方式从用户空间配置内核对象的虚拟文件系统。内核文档：configfs

⏱️ 时间与延迟

⏱️ 时间与延迟

Andreas Hindborg 的 rust: time: warn and assert out-of-range input in fsleep() and udelay()，已到 v2。这个补丁给两个"延时函数"加了输入检查：当传进 fsleep()（灵活睡眠）和 udelay()（微秒级忙等延时）的数值超出合理范围时，会发出警告并触发断言。这是防御性编程——与其让一个离谱的延时值悄悄导致诡异行为，不如在调试阶段就大声报错，帮开发者尽早发现自己传错了参数。Sang-Heon Jeon 参与评审。

📬 fsleep/udelay 检查 v2
💡 小白科普
· udelay 与 fsleep：内核里两种等待方式。udelay 是"忙等"——CPU 原地空转数微秒，精确但浪费算力，只适合极短延时；fsleep 会根据时长智能选择睡眠方式。内核文档：延时与睡眠函数

社区讨论与协作

社区讨论与协作

在 #General 频道，Philipp Stanner 抛出一个小却实际的问题：rust 目录下的文件名，分隔符到底该用下划线 _ 还是连字符 -？ 比如该写 dma_fence.rs 还是 dma-fence.rs。Onur Özkan 给出了明确答复：用 dma_fence.rs（下划线），并援引了 Rust API 命名指南中"模块（modules）"那一节作为依据。讨论共 9 条消息，最后被标记为已解决（✔）。对新人来说这是个很有用的小结论——Rust 文件名跟随 Rust 的惯例，用下划线。

💬 命名约定讨论

在 #Nova 频道，新人贡献者 Nanonej 发了一组 RFC：把寄存器定义挪到真正使用它们的模块里。这是他在研究代码时顺手发现的一批"低垂的果实"（容易改进的小问题），并按 Alexandre Courbot 的建议用了 b4 工具来发补丁。Alexandre 回应说虽然还没细看，但"这个粒度看起来是对的，保持模块内聚对评审更友好"。Nanonej 也坦言，邮件补丁流程比他习惯的"合并请求（Merge Request）"感觉更重一些——这正是很多从 GitHub 转到内核邮件流程的新人的共同心声。

💬 寄存器定义讨论

在 #Tyr 频道（Tyr 是另一个 Rust GPU 驱动项目），关于 SysMem 实现的讨论（Tyr MR #67）被 Laura Nao 标记为已解决。具体细节不多，但说明该合并请求里关于系统内存处理的那段讨论已经收尾。

💬 Tyr SysMem 讨论
💡 小白科普
· 邮件补丁流程 vs Merge Request：Linux 内核传统上靠"发邮件提交补丁"协作，而不是 GitHub 那种网页点"合并请求"。b4 就是帮你管理这套邮件补丁流程的命令行工具。如何为 Rust-for-Linux 贡献
· 寄存器定义（register definitions）：硬件驱动里描述芯片各个控制寄存器地址和含义的代码，放在"用它的模块"附近能让代码更聚拢、更好维护。

️ 工具链与平台支持（GITHUB 跟踪）

️ 工具链与平台支持（GitHub 跟踪）

GitHub 上几个长期跟踪用的"清单型" issue 今天仍处于开放状态，都由 Miguel Ojeda 维护。它们不是当天才出现的新事，而是社区持续记录"还差什么"的看板：

· #355 rustc 想要的特性与待修 bug 和 #2 内核需要的 Rust 不稳定特性（均带 toolchain/meta 标签）：记录内核要正式用上 Rust，还依赖哪些尚未稳定的编译器特性。这关系到"内核什么时候能脱离 nightly 特性"这个大目标。

· #350 rustdoc 想要的特性与待修 bug：跟踪文档工具的需求。

· #106 支持 s390 架构（arch 标签）：让 Rust 内核代码能在 IBM 的 s390 大型机架构上跑起来，属于扩大硬件覆盖面的工作。

🐙 #106 s390
💡 小白科普
· 不稳定特性（unstable features）：Rust 编译器里还在试验、尚未正式定稿的功能，只能在 nightly 版用。内核用到不少，因此社区一直在推动它们尽快稳定。Rust Unstable Book
· 架构（arch）：指 CPU 指令集类型，如 x86、ARM、s390。每支持一种新架构，都要让底层代码适配它的特性。
