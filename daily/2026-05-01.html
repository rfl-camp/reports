️ GPU / Nova 驱动

Nova 驱动模块重命名：从 nova_core 到 nova-core
Joel Fernandes 提交了一个看起来很小但其实很关键的改动：把内核构建系统（Kbuild）里 Nova 驱动的模块目标从 nova_core.o 改名为 nova-core.o。为什么要改？因为 Rust 编译器在编译 nova_core.rs 这个源文件时，也会生成一个叫 nova_core.o 的中间文件，两个同名文件撞在一起会导致构建失败。改用连字符命名后，模块目标和 Rust crate 的中间产物就不会冲突了，Nova 驱动就能作为一个"复合模块"（composite module）正常编译。这个补丁是让 nova-core 和 nova-drm 协同工作的 7 个补丁系列的一部分。

📬 查看补丁

导出 Rust 符号，让 nova-drm 能调用 nova-core
同样来自 Joel Fernandes 的补丁。Nova 驱动被拆分成了两个模块：nova-core（负责底层 GPU 硬件交互）和 nova-drm（负责与 Linux 图形子系统 DRM 对接）。问题是 nova-drm 作为一个独立的可加载模块，在运行时需要能找到 nova-core 里的函数。这个补丁的做法是：用 nm 工具扫描 nova-core 编译出来的 Rust 全局符号，自动生成 C 语言的 EXPORT_SYMBOL_GPL() 声明，然后编译进模块。这样 nova-drm 加载时就能正确"链接"到 nova-core 的功能了。这是让 Rust 内核模块之间能互相调用的重要基础设施工作。

Nova DRM 前端：打通调用 nova-core 的通路
Alexandre Courbot 提交的这个 7 补丁系列是上面两个补丁的"总工程"。它的目标是让 nova-drm（用户空间图形程序最终打交道的模块）能够真正调用到 nova-core 的功能。打个比方：nova-core 就像汽车的发动机，nova-drm 就像方向盘和仪表盘，这个补丁系列就是把发动机和驾驶舱之间的线路接好。这是 Nova 驱动走向可用的关键一步。

️ GPU / Nova 驱动

Hopper/Blackwell 架构固件支持（v10，28 个补丁）
Alexandre Courbot 持续推进 Nova 驱动对 NVIDIA 最新 GPU 架构的支持，这已经迭代到第 10 个版本了！Hopper 是 NVIDIA H100 系列 GPU 使用的架构（目前 AI 训练的主力），Blackwell 则是更新一代的架构（B100/B200 系列）。这 28 个补丁为 Nova 驱动增加了加载和管理这两代 GPU 固件（firmware）的能力。固件就像 GPU 的"操作系统"，驱动需要在初始化时把正确的固件加载到 GPU 上，GPU 才能正常工作。这个系列已经迭代了 10 个版本，说明社区对代码质量要求非常严格。

📬 查看补丁

WPR 堆大小计算改为可失败操作（v9，31 个补丁）
同样来自 Alexandre Courbot 的大型系列补丁。WPR（Write Protected Region）是 GPU 内存中一块受保护的区域，用于存放安全敏感的固件数据。之前计算这块区域大小的代码假设"一定能成功"，但在内核编程中，内存分配和大小计算是可能失败的（比如内存不够）。这个补丁把相关操作改成了"可失败"（fallible）的——也就是说，如果出了问题会返回一个错误码，而不是直接崩溃（panic）。这是 Rust 在内核中的一个核心理念：显式处理错误，不要假装错误不存在。31 个补丁、第 9 个版本，可见这是一项细致的重构工作。

⚙️ 设备驱动框架

⚙️ 设备驱动框架

高阶生命周期类型（Higher-Ranked Lifetime Types）用于设备驱动（24 个补丁）
Alice Ryhl 和 Danilo Krummrich 联手提交了一个重量级的 24 补丁系列，为 Rust 设备驱动框架引入了"高阶生命周期类型"。这是什么意思呢？在 Linux 内核里，一个设备驱动在运行过程中会经历"探测"（probe）、"运行"、"移除"（remove）等阶段，不同阶段能访问的资源是不同的。Rust 的生命周期系统本来就是用来追踪"谁能在什么时候访问什么"的，但普通的生命周期标注不够灵活，无法表达"这个函数要能处理任意生命周期"的需求。高阶生命周期（用 for<'a> 语法）可以解决这个问题，让驱动框架在编译时就确保不同阶段的资源访问是安全的。这对驱动开发者来说意味着：编译器会帮你检查更多潜在的内存安全问题，而不需要你手动写 unsafe 代码。

📬 查看补丁

驱动数据在设备资源释放前先释放（24 个补丁）
Alice Ryhl 和 Danilo Krummrich 的另一个大型系列。这个补丁修改了驱动数据（drvdata）和设备资源（devres）的释放顺序。在内核驱动中，设备被移除时需要按正确顺序清理资源——就像拆房子要先把家具搬走再拆墙一样。之前的实现中，驱动自己存储的数据可能在设备资源释放之后才被释放，这会导致悬垂指针（dangling pointer）的风险。这个补丁确保 drvdata 先被释放，然后才释放 devres 注册的资源，从根本上消除了这种时序错误的可能性。这是一个典型的"用 Rust 的所有权系统来保证内核代码正确性"的案例。

内存与类型安全

内存与类型安全

扩展安全的 AsBytes/FromBytes 用法（v3，4 个补丁）
Matthew Maurer 提交的第三版补丁，让更多地方可以安全地使用 AsBytes 和 FromBytes 这两个 trait。这两个 trait 是做什么的？在内核中，经常需要把一个结构体"当作一串字节来读写"——比如把数据发送给硬件、写入磁盘、或者从网络接收。AsBytes 表示"这个类型可以安全地被解读为字节序列"，FromBytes 表示"任意字节序列都能安全地被解读为这个类型"。之前很多地方用的是 unsafe 的手动转换，这个补丁让编译器来保证这些转换是安全的。Miguel Ojeda 和 Alexandre Courbot 参与了审查，共有 4 条评审意见。

📬 查看补丁

为指针投影添加 panic 版本的索引操作（5 个补丁）
Gary Guo 和 Alexandre Courbot 合作的补丁，为 Rust 内核的指针操作（rust/kernel/ptr.rs）添加了一种新的索引投影（index projection）变体。"投影"是指从一个复合类型（比如数组或结构体）中取出某个字段或元素的操作。新增的变体会在索引越界时触发 panic（程序中止），而不是返回一个 Option/Result。为什么需要这个？因为在某些场景下，越界访问意味着代码逻辑有严重 bug，直接 panic 比默默返回错误更容易发现问题。这就像数组访问用 arr[i]（越界 panic）还是 arr.get(i)（越界返回 None）——两种都有用武之地。

工作队列（Workqueue）

为 WorkItemPointer 实现补充安全性文档
Sagar Taunk 提交了一个文档性质的补丁，给 Pin<KBox<T>> 上的 WorkItemPointer 实现补充了完整的安全性论证（SAFETY 注释）。之前这里只有一个 SAFETY: TODO——也就是说原作者知道需要解释为什么这段 unsafe 代码是安全的，但还没写。Sagar 的补丁补上了这个空缺：安全性论证依赖三个保证——__enqueue 通过 Pin::into_inner 剥离 Pin 包装来获取裸指针，KBox 保证指针指向的内存是稳定的（不会被移动），以及工作队列的回调机制保证了内存生命周期的正确性。Alice Ryhl、Onur Özkan 等 3 人参与了审查。这虽然"只是"写注释，但在内核开发中，SAFETY 注释的重要性不亚于代码本身——它是向所有人解释"为什么这段 unsafe 代码不会出错"的承诺。

️ 宏与日志工具

新增 warn_on_err 宏（v3，6 个补丁）
Danilo Krummrich 和 Alexandre Courbot 合作的补丁，为内核 Rust 代码添加了一个叫 warn_on_err! 的新宏。这个宏的作用是：当一个返回 Result 的操作失败时，自动打印一条内核警告日志（相当于 C 语言中的 WARN_ON），然后把错误继续传递出去。想象一下，你在做饭时发现盐放多了——warn_on_err! 就像是先喊一声"盐多了！"（打印警告），然后再决定接下来怎么办（传递错误）。这个宏减少了手动写日志代码的样板，让错误处理更简洁。已经迭代到第 3 版，说明社区对宏的具体行为和 API 设计进行了充分讨论。

📬 查看补丁

模块参数空指针警告改用 pr_warn_once!
Aaron Tomlin 提交的小改进。在内核模块的参数处理代码中，如果遇到空指针（null pointer）的情况，之前可能每次都会打印警告，现在改用 pr_warn_once!——也就是说，同样的警告只会打印一次。这避免了当同一个问题反复触发时，内核日志被大量重复的警告信息"淹没"。这是一个很小但很实用的改动，体现了"日志信息要有意义、不要刷屏"的工程原则。
