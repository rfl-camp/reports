GPU / 显卡驱动（NOVA-CORE）

GPU / 显卡驱动（nova-core）

① 引入 zerocopy 库改造数据绑定。

nova-core 是社区正在用 Rust 编写的 NVIDIA 新一代显卡驱动，今天它贡献了今天最大的一批补丁。主线只有一条：把显卡和驱动之间「对话」用的数据结构，从手写的危险代码换成更安全的方式。

① 引入 zerocopy 库改造数据绑定。显卡里有一颗叫 GSP 的小处理器，驱动要和它通信就得来回读写一大堆二进制数据结构。以前 nova-core 是靠程序员手写 unsafe 的 AsBytes / FromBytes 实现，来声明「这块内存可以安全地当作字节流来读写」——实践中一般没问题，但没有任何机制真正去检查它对不对，全凭人靠谱。这次的补丁改用 zerocopy 这个专门为此设计的库，由编译器自动、安全地推导这些转换，从根上消除了手写 unsafe 的隐患。改动覆盖了自动生成的 bindings 以及固件命令相关的类型。

📬 查看补丁（bindings 转 zerocopy）
② 在 DMA 层架一座「转换桥」。

② 在 DMA 层架一座「转换桥」。光让 nova-core 用 zerocopy 还不够——内核的 DMA 子系统（设备直接读写内存的通道）有自己一套「这块内存按字节安全吗」的判断标准（叫 transmute 字节安全约束）。这组 4 个补丁把 zerocopy 推导出来的类型「桥接」进 DMA 的安全体系里，让两套机制能互认，这样 GSP 那块内存（GspMem）也能顺利转用 zerocopy。可以理解成：先各自把安全标准定好，再修一座桥让它们互通，避免重复造轮子。

GPU / 显卡驱动（nova-core）

③ 整理 GSP 启动流程，理顺各部件的「生命周期」。

③ 整理 GSP 启动流程，理顺各部件的「生命周期」。Alexandre Courbot 提交了两组各 12 个补丁的重构。一组把 Fsp（GPU 的一个子设备）实例正式存进 Gpu 结构里：以前它只在新架构（Hopper 及以上）开机时临时创建、用完即扔，但既然它是 GPU 的一个长期部件，生命周期就该跟着 GPU 走，而不是只活在一次开机过程里。另一组则把刚引入的 GspBootContext 推广复用，让 Gsp::boot（启动）和 Gsp::unload（卸载）的代码结构对称起来，更好读也更好维护。此外还有一个补丁把 bar 和 dev 存进 falcon（GPU 上另一个微控制器）里，思路一脉相承——让每个部件自己持有需要的东西。

📬 falcon 保存 bar 和 dev
④ 为 vGPU 引入 fwctl 抽象。

④ 为 vGPU 引入 fwctl 抽象。在 NVIDIA 的虚拟 GPU（vGPU，把一张物理显卡切给多台虚拟机用）方案里，必须先把「vGPU 类型描述数据」喂给 GSP，用户态才能列出可用的 vGPU 类型并创建实例。原本设计是借用「固件加载接口」来传这些数据，但作者发现 fwctl（一个专门用于在用户态和设备固件之间上传/下发数据的内核接口）更契合这个场景。这版补丁为 fwctl 写了一套 Rust 抽象，铺路给后续的 vGPU 支持。

内核核心抽象 & 驱动模型

内核核心抽象 & 驱动模型

① 设备识别改用指针而非索引。

这一类补丁不针对某个具体硬件，而是改进所有 Rust 驱动共用的「底层框架」，影响面很广。

① 设备识别改用指针而非索引。驱动要认出「我能驱动哪些硬件」，靠的是一张设备 ID 表，每条记录可以挂一份「附加信息」（driver_data）。C 语言驱动习惯直接用一个指针指向这份信息；而目前 Rust 代码用的是索引（数字下标），然后还得靠一张额外的「对照表」把数字翻译成真正的 &IdInfo。Gary Guo 这组 12 个补丁让 Rust 也直接用指针，去掉那张多余的对照表，也消除了在 ACPI / OF（两种设备枚举机制）里到处手写的重复代码。

📬 ID info 改用指针 v2
② I/O 类型的泛化与投影。

② I/O 类型的泛化与投影。Danilo Krummrich 和 Gary Guo 合作的一组 20 个补丁（已到 v5），目标是让访问硬件寄存器、I/O 内存的那套类型更通用、更灵活，支持「投影」（从一个大的 I/O 区域里安全地取出某个子区域来操作）。这是设备驱动天天要用的基础能力，做得好能让上层驱动写起来更省心、更不容易出错。

📬 I/O 类型泛化与投影 v5
③ 引用计数 API 微调。

③ 引用计数 API 微调。Gary Guo 的补丁（已到 v7）把 AlwaysRefCounted::inc_ref（增加引用计数）从一个「方法」改成「关联函数」。差别在于调用方式和语义更清晰，避免某些容易误用的写法。这种改动看着小，但因为它是被无数地方调用的核心 trait，得反复打磨、谨慎合入，所以才迭代到第 7 版。

📬 inc_ref 改为关联函数 v7

引用计数（Reference Counting）：一种内存管理方法——给一个对象记一个「现在有几个人在用我」的数字，加一个使用者就 +1，用完就 -1，归零时自动释放。内核里大量共享对象靠它来安全回收。了解引用计数 →

️ 构建系统 & 语言基础设施

️ 构建系统 & 语言基础设施

① 新增 cfg_select! 宏。

这组改动关乎「内核 Rust 代码用什么编译器、怎么写条件编译」，是整个项目的地基。

① 新增 cfg_select! 宏。内核里经常要根据配置开关（比如 CONFIG_FOO 开没开）在两份实现之间二选一。以前的写法是一对 #[cfg(CONFIG_FOO)] / #[cfg(not(CONFIG_FOO))] 配对标注——又啰嗦，又容易改了一边忘了另一边导致两者「不同步」。Rust 标准库新出了 core::cfg_select! 正好解决这个问题（类似 match 那样列出各种情况选一个）。Miguel Ojeda 等人把它「反向移植」（backport）进内核 Rust 并开始使用，让条件编译写得更简洁、更不易出错。

📬 cfg_select! 宏
② 为 PowerPC 设定最低 rustc 版本。

② 为 PowerPC 设定最低 rustc 版本。Mukesh Kumar Chaurasiya 的补丁（已到 V16！可见 PowerPC 上让 Rust 跑起来有多曲折）为 PowerPC 架构明确规定了能编译内核 Rust 代码的最低编译器版本。每个 CPU 架构对 Rust 的支持进度不一样，定好门槛能避免「用太老的编译器编出问题」。

📬 PowerPC 最低 rustc 版本 V16
③ 放行一条编译器警告。

③ 放行一条编译器警告。Miguel Ojeda 的小补丁：对 Rust ≥ 1.98，允许（即不报错地放过）一条名为 suspicious_runtime_symbol_definitions 的 lint 检查。新版编译器引入的新检查有时会对内核这种特殊环境「误报」，这类补丁就是告诉编译器「这种情况我们清楚，别拦着」，保证内核在新编译器上还能顺利编过。

📬 放行 lint 警告

条件编译（cfg）：让同一份源码根据开关编出不同结果——比如「开了某功能就编进这段代码，没开就不编」。这样一套代码能适配各种配置。Rust 条件编译参考 →

设备驱动：LED 灯抽象

设备驱动：LED 灯抽象

Markus Probst 持续在推进「用 Rust 写 LED 灯驱动」的基础抽象，今天一口气发到了 第 20 版（v20），分成 4 个补丁。这套抽象封装的是内核的 LED classdev 框架——也就是让驱动能统一地控制各种 LED 灯（亮度、闪烁模式等），就像给系统装上一个标准的「灯控接口」，之后任何带 LED 的设备驱动都能复用它。

这次的 4 个补丁分别覆盖：整套 led classdev 抽象的总入口、最基础的 classdev 抽象、一个表示「灯的工作模式」的 Mode trait，以及支持多色 LED（multicolor，比如 RGB 灯）的抽象。能迭代到第 20 版，说明 API 设计被社区反复审视、力求把接口打磨到既安全又好用——这正是内核接受新抽象的常态：慢工出细活。

代码风格统一：竖排 IMPORT

代码风格统一：竖排 import

今天有两组补丁在做同一件「美化」工作：把 use 导入语句改成竖排（vertical）风格——也就是每个被导入的东西单独占一行，而不是几个挤在一行里。这样做的好处是 diff 更清晰（加删某个 import 时改动只影响一行）、读起来更顺、合并冲突也更少。

Guru Das Srinagesh 牵头，配合 Andrew Lunn、Zhongqiu Han 等人，把这个风格应用到 rcpufreq_dt（基于设备树的 CPU 调频驱动）以及其他多个 Rust 驱动里。两组都明确标注「无功能改动」（no functional changes），纯粹是可读性和可维护性的清理。它的起因是有人注意到最近一个提交 bc58905eb07 把某个示例驱动改成了竖排风格，于是顺手把其他几处也统一了。这种「看到一处好做法，就推广到全项目」正是内核社区保持代码整洁的日常。

📬 cpufreq 竖排 import
💡 小白科普
diff：「差异」的意思，指代码改动前后的对比。内核靠邮件发送 diff 来评审补丁，diff 越干净、改动行数越聚焦，越方便别人 review。竖排 import 正是为了让 diff 更友好。了解 diff →

② 补全错误码。Timur Tabi 在 General 频道提到，他已经发出补丁，把剩余还没纳入的错误码全部补进 rust/kernel/error.rs。内核函数出错时会返回一个错误码（比如 ENOMEM 表示内存不足），Rust 侧需要把这些 C 的错误码一一封装成 Rust 类型，驱动才能优雅地处理错误。把它们补齐，意味着 Rust 驱动遇到任何标准错误都能对得上号。
