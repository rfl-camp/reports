️ 设备驱动生命周期大重构（24 补丁系列 v5）

① Device Core/CoreInternal 加入生命周期参数

今天最重磅的动态：Danilo Krummrich 提交了一个包含 24 个补丁的大型系列，目前已经迭代到第 5 版。这个系列做的事情用一句话概括就是——让 Rust 编译器帮你检查「硬件资源有没有用错」。

在内核驱动中，你经常需要"映射"硬件的内存区域（比如显卡的寄存器），然后通过这个映射去读写硬件。但这里有个关键问题：这个映射只在设备处于"绑定"状态时才有效。如果设备被卸载了，你还拿着那个映射去读写，就会出大问题（内核崩溃甚至硬件损坏）。以前在 C 语言里，这完全靠程序员自觉。现在通过 Rust 的生命周期参数，编译器可以在编译时就发现这类错误。

这个系列涉及以下多个子系统的改造：

① Device Core/CoreInternal 加入生命周期参数
改了 Device<Core> 的类型定义，给 Core 和 CoreInternal 加上生命周期参数。在驱动的 probe() 回调中拿到的设备引用，其作用域被精确限定为回调函数本身，而不是整个绑定周期。这样，如果你试图把 probe 阶段的临时引用保存到长期数据结构里，编译器会直接报错。Alexandre Courbot、Eliot Courtney 等参与了 review。

📬 查看补丁
② PCI BAR 映射绑定到设备生命周期

② PCI BAR 映射绑定到设备生命周期
把 pci::Bar<SIZE> 改成了 pci::Bar<'a, SIZE>，内部存储一个 &'a Device<Bound> 引用。这意味着 BAR 映射（就是 PCI 设备上的一段内存地址空间）的生存期被绑定到了设备的"已绑定"状态。同时简化了 iomap_region_sized() 的返回类型，从复杂的 impl PinInit<Devres<Bar>> 变成了更直观的 Result<Bar<'a, SIZE>>。Gary Guo、Alexandre Courbot 等 5 人参与 review。

📬 查看补丁
③ IoMem / ExclusiveIoMem 加入生命周期参数

③ IoMem / ExclusiveIoMem 加入生命周期参数
同样的思路也应用到了 I/O 内存映射上。IoMem<SIZE> 变成 IoMem<'a, SIZE>，驱动可以直接在自己的 HRT（Hardware Resource Table）私有数据里持有 I/O 映射的引用，而不需要再套一层 Devres 包装。这样代码更简洁，安全性也由编译器保证。

📬 查看补丁
④ USB Driver trait 加入生命周期参数

④ USB Driver trait 加入生命周期参数
USB 驱动的 Driver trait 里的关联类型 Data 从固定类型变成了 Data<'bound>。有了这个改变，驱动的私有数据可以直接存储对设备的引用，而不用通过 Devres（设备资源管理器）间接持有。probe() 和 disconnect() 回调也相应调整。Eliot Courtney 参与 review。

⑤ 新增 ForLt trait：高阶生命周期支持

⑤ 新增 ForLt trait：高阶生命周期支持
这个补丁由 Gary Guo 编写，添加了一个 ForLt trait，用来处理"泛型生命周期"的场景。打个比方：你有一个函数，它接收一个带生命周期的参数，返回一个也带生命周期的结果——你怎么告诉编译器"这两个生命周期是同一个"？ForLt 就是解决这个问题的。它利用了 Rust 的 for<'a> 语法和协变性（covariance）保证，让存储的 'static 生命周期可以安全地缩短为实际的借用生命周期。

⑥ Auxiliary 注册机制泛化

⑥ Auxiliary 注册机制泛化
基于上面的 ForLt trait，把 auxiliary 子系统的 Registration<T> 泛化为 Registration<F: ForLt>。Device::registration_data() 方法现在返回 Pin<&F::Of<'_>>，通过 ForLt::cast_ref 把存储时的 'static 缩短为借用时的实际生命周期。这是整个系列中最"类型体操"的部分。

⑦ Nova Core 驱动类型分离

⑧ 示例驱动更新

GPU 驱动：Nova Core VBIOS 加固（22 补丁系列 v5）

使用第一个 PCI-AT 镜像

Nova Core 是社区正在用 Rust 从头编写的 NVIDIA 开源 GPU 驱动。今天 Eliot Courtney 提交了一个包含 22 个补丁的系列（v5），主要目标是加固 VBIOS 解析代码。

VBIOS（Video BIOS）是 GPU 上的一段固件，包含了 GPU 的配置信息。驱动启动时需要解析这些数据来正确初始化硬件。问题在于，VBIOS 里的数据来自固件，理论上可能包含不合法的值（比如一个数组索引越界）。在 C 语言驱动中，这类错误很容易导致内核崩溃或安全漏洞。这个补丁系列把所有基于固件值的数组访问都加上了安全检查。

主要改动包括：

使用第一个 PCI-AT 镜像
之前的代码在遇到多个 PCI-AT 镜像时会使用最后一个，但 nouveau（现有的 NVIDIA 开源驱动）使用的是第一个。这个补丁修正了这个行为，保持与 nouveau 一致。这种一致性很重要——如果两个驱动对同一硬件有不同行为，可能会导致意想不到的 bug。

直接构造 FwSecBiosImage

直接构造 FwSecBiosImage
原来的代码有一个中间结构体 FwSecBiosBuilder，但里面只剩下一个字段 falcon_ucode_offset，完全可以直接传给 FwSecBiosImage。这个补丁删掉了这个多余的中间层，简化了代码路径。虽然是小改动，但减少不必要的抽象层能让代码更容易理解和维护。

PMU 查询表改用 KVVec 存储
之前 PMU（电源管理单元）的查找条目是把原始数据复制到 KVec 里，每次需要时再解析。现在改为直接存储解析好的条目到 KVVec 中。这就像是把"每次打开文件都重新解码"变成了"打开时就解码好，以后直接用"——更高效也更清晰。

整体加固策略

整体加固策略
整个系列的核心思想是：所有基于固件数据的数组访问，如果不能通过局部的不变量（invariant）保证安全的，都要加上显式的边界检查。已经有前置检查保护的访问则保持不动，避免多余的防御性代码。Danilo Krummrich 参与了 review。

️ DRM 驱动：Tyr 新增 debugfs 支持

Alvin Sun 提交了一个 13 个补丁的系列，为 DRM Tyr 驱动添加 debugfs 基础设施。debugfs 是 Linux 内核提供的一个调试用虚拟文件系统——你可以把它想象成一个"调试窗口"，让开发者在运行时查看驱动内部的状态信息。

⚡ PWM 驱动简化：TH1520

⚡ PWM 驱动简化：TH1520

Maurice Hieronymus 提交了一个针对 TH1520 芯片 PWM 驱动的补丁。TH1520 是平头哥（T-Head）出品的一款 RISC-V 芯片，PWM（脉冲宽度调制）是一种常用的硬件功能，常用于控制 LED 亮度、电机转速等。

这个补丁的核心改动很精巧：由于 TH1520 的 cycle（周期）寄存器实际上是 32 位的，所以 cycles_to_ns() 函数可以接收 u32 而不是 u64。这样一来，cycles × NSEC_PER_SEC 的最大值约为 4.3×10¹⁸，完全在 u64 范围内，不会溢出。因此，之前使用的饱和算术运算（saturating arithmetic）和专门的 mul_u64_u64_div_u64_roundup 函数就不需要了。

这个改动的好处是减少了对特殊数学辅助函数的依赖，让代码更简单，也更容易移植。Gary Guo 和 Michal Wilczynski 等 4 人参与了 review。

I2C 驱动 BUG 修复：引用计数双重递增

I2C 驱动 Bug 修复：引用计数双重递增

Onur Özkan 发现并修复了 Rust I2C 适配器（I2cAdapter）中的一个引用计数 bug。引用计数是内核中管理对象生命周期的重要机制——每多一个使用者就加 1，每少一个就减 1，减到 0 就释放。

这个 bug 是引用计数被多加了一次（double increment）。后果是什么呢？即使所有使用者都释放了引用，计数器也不会归零，导致对象永远不会被释放——这就是内存泄漏。虽然不会导致崩溃，但在长时间运行的系统中，内存泄漏会慢慢积累，最终可能耗尽系统资源。

这个 bug 的发现也说明了在 Rust 内核驱动中，即使语言本身提供了内存安全保证，与 C 内核交互的边界处仍然需要格外小心——引用计数逻辑涉及 FFI（外部函数接口）调用，是 Rust 安全保证覆盖不到的地方。

💡 引用计数（Reference Counting）：一种内存管理技术。每个对象有一个计数器，被引用时加 1，引用释放时减 1，归零时释放对象。类似于共享单车——最后一个人还车后才能回收。 📖 了解引用计数

内存分配器：7.2-RC1 ALLOC 改动合并

内存分配器：7.2-rc1 Alloc 改动合并

Danilo Krummrich 发出了一个 GIT PULL 请求，要求将 Alloc（内存分配器）相关的改动合并到 Linux 7.2-rc1 中。GIT PULL 是内核开发中子系统维护者向 Linus Torvalds（或上级维护者）请求合并代码的标准流程。

能走到 GIT PULL 这一步，说明这些分配器改动已经经过了充分的审查和测试，准备进入正式的内核发布周期。Rust 内核的内存分配器是所有 Rust 驱动的基石——没有它，你连最基本的 Vec（动态数组）都用不了。每一次分配器的改进都会惠及所有 Rust 内核代码。
