GPU / DRM 显卡驱动

1. 给显卡命令加一把"父设备还在不在"的安全锁（19 连发大系列 v5）

1. 给显卡命令加一把"父设备还在不在"的安全锁（19 连发大系列 v5）

Danilo Krummrich 提交了今天分量最重的一组补丁。问题的背景是这样的：当用户程序通过 ioctl（用户态向驱动下命令的一种方式）操作显卡时，这段代码是在普通的进程上下文里跑的，内核并不保证此时显卡背后的总线设备还连着——想象你正在用打印机打文件，结果有人偷偷把打印机的 USB 线拔了，程序还傻乎乎地往那个地址写数据，就会崩溃。

Danilo 的解法是引入一个叫 RegistrationGuard 的"守卫"对象。它本质上是把内核的 drm_dev_enter/exit 这对函数（基于 SRCU 这种特殊的读写保护机制）包成一个 Rust 守卫：只要这个守卫还活着，编译器就能保证"父设备在这段时间内一定是绑定状态的"。这样就把一个运行时才会爆的 bug，变成了编译期就能挡住的类型错误。

2. nova-core：修复 GSP 共享内存的"内存对不齐"隐患（4 连发）

2. nova-core：修复 GSP 共享内存的"内存对不齐"隐患（4 连发）

SeungJong Ha 提交了一组补丁，针对 nova-core（社区正在用 Rust 重写的英伟达 GPU 驱动）里和 GSP 通信的内存结构 GspMem。GSP 是英伟达显卡上的一颗小处理器，主机和它之间通过一块 DMA 共享内存来交换消息。原来的代码手写了一个 unsafe impl transmute::{AsBytes, FromBytes}，意思是"我保证这块内存可以原封不动地当字节数组来读写"——但实际上它并不满足"无填充字节"的要求：里面的 Msgq 在两个小头部之后塞了一个按页对齐的 MsgqData，中间会有编译器自动插入的空隙（padding）。

这种"手工保证"一旦哪天结构改了就可能出错，是典型的 unsafe 雷区。补丁通过 transmute 桥接到更严谨的 zerocopy 库来重新实现这个转换，让"能不能安全地当字节看"这件事由库和编译器来把关，而不是靠人肉审查。

初始化安全大扫除（pin_init / zerocopy）

1. iommu：把 core::mem::zeroed 换成 pin_init::zeroed

今天有一条很清晰的支线：把内核里各处"手动清零初始化"的老写法，统一替换成更现代、更安全的方式。背景是 Rust 标准库里的 core::mem::zeroed() 是个 unsafe 函数——它直接把一块内存全填成 0 然后当作某个类型来用，但万一这个类型并不允许"全 0"是合法值，就是未定义行为。社区更推荐用 pin_init::zeroed，它会在类型层面要求"这个类型确实可以安全地全 0 初始化"。

1. iommu：把 core::mem::zeroed 换成 pin_init::zeroed

由 Gary Guo 等人推动，针对 IOMMU（内存管理单元，负责给设备做地址翻译和隔离）相关代码。改动把不安全的清零调用换成更受约束的版本，已经有两个 reviewer 看过。这是这条"扫除线"里最核心的一笔。

引用计数 API 改进

引用计数 API 改进

把 AlwaysRefCounted::inc_ref 改成"关联函数"（v5）

把 AlwaysRefCounted::inc_ref 改成"关联函数"（v5）

Trevor Chan 提交了一个看着小、但设计意味很足的改动。AlwaysRefCounted 是内核里描述"这种对象永远带引用计数"的 trait，inc_ref 就是"给引用计数 +1"的操作。问题在于：增加引用计数是个不该随手乱调的危险动作——调多了对象就永远释放不掉（内存泄漏），调错了甚至可能引发安全问题。

原来 inc_ref 是个普通方法，可以像 obj.inc_ref() 这样很顺手地点出来，太容易手滑误调。补丁把它改成关联函数，调用时必须写成 AlwaysRefCounted::inc_ref(&obj) 这种更显眼、更"郑重其事"的形式，相当于给这个危险操作加了一道"你确定要这么做吗"的视觉提醒。当然，这个改动要求把内核里所有实现了 AlwaysRefCounted 的类型都跟着改一遍，所以已经迭代到第 5 版了。
