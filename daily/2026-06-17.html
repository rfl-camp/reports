1. 给 Rust 加上 dma_fence（栅栏）抽象 —— 今天的重头戏

1. 给 Rust 加上 dma_fence（栅栏）抽象 —— 今天的重头戏

Danilo Krummrich、Gary Guo、Philipp Stanner 等人提交了第 2 版、一共 6 个补丁的系列，目标是把 C 语言里的 dma_fence 机制"翻译"成 Rust 能安全使用的接口。你可以把 dma_fence 想象成一张"叫号小票"：CPU 给显卡派了个活儿，但活儿什么时候干完不知道，于是显卡干完后就"撕掉小票"（signal）通知大家。这套机制有几条铁律：每张票只能撕一次、所有票最终都必须被撕掉、错误码只能在撕票前设置。

之所以重要，是因为未来每一个 Rust 写的 GPU 驱动都要靠它来协调 CPU 和 GPU 之间的等待。这一版相比上一版做了不少打磨：去掉了不必要的可变引用、把过于笼统的 unsafe 安全注释拆细、并按 Boris 的建议用 FenceCtx trait 替换掉了 PhantomData。系列里还顺带加了配套零件：让 C 代码能持有 Rust 的 ARef<T>（实现 ForeignOwnable）、新增 ECANCELED 错误码、以及更新 MAINTAINERS 文件登记新的 Rust dma-buf 子系统维护信息。

2. Zulip 热议：dma_fence 在"原子上下文里销毁"的麻烦

2. Zulip 热议：dma_fence 在"原子上下文里销毁"的麻烦

在 #DRM 频道，Philipp Stanner 和 Boris Brezillon 接着深挖了一个棘手问题：当用 call_rcu() 来延迟销毁 DriverFenceData 时，"在原子上下文（不允许睡眠的代码段）里销毁对象"这个老问题比想象中"还要再深几厘米"。Boris 提出疑问：为什么 DriverFenceData::fctx 一定要用 Arc<FenceCtx>？他建议能不能改用生命周期（lifetime）来保证 FenceCtx 一定活得比所有用到它的数据更久，从而把开销更大的引用计数 Arc 换成普通借用引用 &FenceCtx。这是典型的 Rust 内核编程难题——既要内存安全，又不能在错误的时机做销毁动作。讨论还没有定论，属于设计阶段的来回推敲。

3. Zulip 讨论：DRM 设备"注册顺序"该怎么设计

Lyude 和 Danilo Krummrich 在头脑风暴 DRM 设备的注册时序问题。核心争论是：要不要给 drm::Device 设计一个"未初始化（Uninit）"的类型状态。Danilo 认为只需要给已正常注册的 drm::Device<Normal> 提供 ARef 实现就够了——如果一个设备还没满足"已注册"这个前提，那它的处境本来就完全不同，不必单独搞个 Uninit 状态。Lyude 则倾向于尽早动手提交，因为这样能避免以后还得把 DeviceContext 一路传给 Crtc（显示控制器对象）之类的东西，"让 rebase（变基/同步代码）更快"。这是用 Rust 类型系统在编译期就堵住"用错时机"的典型思路。

4. nova-core（NVIDIA 实验驱动）的 FSP 固件通信修补

4. nova-core（NVIDIA 实验驱动）的 FSP 固件通信修补

Alistair Popple 和 Gary Guo 围绕 nova-core 这个新一代 NVIDIA 显卡驱动提交了多组补丁，集中在和 FSP（一种芯片上的安全固件/协处理器）打交道的可靠性上。具体改了三件事：一是抓住非法的队列指针——如果固件返回的消息队列指针是个鬼值，提前发现并报错而不是默默崩溃；二是限制 FSP 接收消息的分配大小，防止固件汇报一个超大长度导致内核申请过多内存；三是把 GSP（GPU 系统处理器）里 falcon 引擎用到的 "PRIV target mask" 常量挪到更合适的位置整理代码。这些都属于"和不太可信的固件打交道时要处处设防"的防御性编程，是让驱动从能跑变成稳定可用的必经之路。

1. KBox::into_non_null —— 已经迭代到第 17 版

Alice Ryhl 和 Gary Guo 维护的这个 10 补丁系列，给内核里的 KBox（内核版的智能指针 Box，负责堆内存的分配和自动释放）增加了一个 into_non_null 方法，用来把一个 KBox 转成保证非空的裸指针，同时把所有权"交出去"。这通常用在需要把 Rust 对象的所有权移交给 C 代码的场景。值得注意的是它已经迭代到 v17——这种打磨次数说明它涉及的所有权语义非常微妙，社区在反复确认每个细节都安全无误。

2. 给 RCU 加上 Rust 封装：rcu_barrier() 与 synchronize_rcu()

2. 给 RCU 加上 Rust 封装：rcu_barrier() 与 synchronize_rcu()

作为 dma_fence 系列的配套，Philipp Stanner 还提交了两个 RCU 相关的抽象。RCU（读-拷贝-更新）是内核里一种非常高效的并发机制：读操作几乎不用加锁，更新时则"先复制一份改完再替换，等所有老读者都离开后再回收旧数据"。synchronize_rcu() 用来等待所有正在进行的读者都读完，rcu_barrier() 则用来等待所有挂起的 RCU 回收回调都执行完。把它们封装成安全的 Rust 接口，正是前面 DmaFence 讨论里"延迟销毁对象"所需要的基础工具。

📬 synchronize_rcu

3. 把 IntoBytes 加进 prelude（已合入 rust-next）

Gary Guo 的一个提交已经合并进 rust-next 分支：把 zerocopy 库的 IntoBytes trait 和它的派生宏 zerocopy_derive::IntoBytes 一起加进 prelude（预导入清单，相当于"开箱即用、不用每次手动 import 的常用工具集"）。IntoBytes 的作用是安全地把一个结构体当成字节数组来看待，这在和硬件、固件交换二进制数据时极其常用。放进 prelude 后，以后的驱动代码会写得更简洁。

1. 修复帧指针（frame pointer）的模块标记问题

1. 修复帧指针（frame pointer）的模块标记问题

Miguel Ojeda 和 Alice Ryhl 提交补丁，给开启了 CONFIG_FRAME_POINTER 的内核设置正确的 LLVM 模块标记。背景是一个 rustc 编译器的 bug：-Cforce-frame-pointers=y 这个开关只给"函数"加上了帧指针标注，却没给整个"模块"加。结果像 asan.module_ctor 这种由 LLVM 后端自动生成的函数就没有帧指针标注，这很可能导致崩溃时打印出的调用栈（backtrace）是错乱的。调用栈错乱会让调试变得非常痛苦——所以这个补丁虽然小，对开发者排错却很关键。

1. 让 kunit_assert! 直接用 line!() 取行号

1. 让 kunit_assert! 直接用 line!() 取行号

Gary Guo 的 3 补丁系列简化了 KUnit（内核单元测试框架）的断言宏。原本 kunit_assert! 需要一个 diff 参数来手动指定行号，因为文档测试（doctest）有时要覆盖默认行号。新方案改成直接用 Rust 内置的 line!() 宏取当前行号，而让文档测试通过"重定义 line!() 宏"的方式来实现原有的覆盖行为。这样断言宏的接口更干净。不过作者也指出，有些现存的文档测试要求 line!() 展开成字面量整数，所以需要小心处理这部分兼容性。

2. 给 bitfield 的 Debug 实现加 #[inline]（已合入 rust-next）

2. 给 bitfield 的 Debug 实现加 #[inline]（已合入 rust-next）

Gary Guo 的另一个已合并提交，给 bitfield（位域）的 Debug 实现加上了 #[inline] 标记。原因是：Debug 实现主要用于调试，正常运行时通常用不到，理想情况下"没用到就不该生成对应代码"。但 Rust 没办法预知下游 crate 会不会用到这个 trait，于是加上 #[inline] 提示，让编译器在没人用时尽量不生成多余代码，给最终内核瘦身。

进程间通信：RUST_BINDER

进程间通信：rust_binder

给 Node::add_death 加上所有权断言 —— 第 3 版

给 Node::add_death 加上所有权断言 —— 第 3 版

Alice Ryhl 和 Georgios Androutsopoulos 在修复 Rust 版 Binder（安卓的进程间通信核心机制）里的一个安全隐患。问题出在 NodeDeath::set_cleared 的 // SAFETY: 安全注释假设：一个 NodeDeath（用于在某个 Binder 节点死亡时通知关注者的对象）永远只会被插进它自己所属节点的"死亡通知列表"里。但实际上，安全函数 Node::add_death 并没有强制检查这一点——它直接把 NodeDeath 插进列表，却没验证 death 确实属于这个节点。这个补丁补上了所有权断言，把"注释里默认的假设"变成"代码里真正强制的不变量"，堵住潜在的逻辑漏洞。这正体现了 Rust 内核开发的严谨：连注释里的假设都要在代码里兑现。

📬 查看补丁
🔰 小白科普：
• Binder：安卓系统里负责"App 之间、App 与系统服务之间"高效通信的核心机制，安卓几乎一切跨进程调用都靠它。📖 维基百科
• 不变量（invariant）：一段代码始终必须成立的约定条件，把它从"注释里的假设"变成"代码里的强制检查"能避免被误用。📖 维基百科
