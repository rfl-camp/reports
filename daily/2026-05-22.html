️ GPU / DRM 驱动

Nova-Core：GPU 驱动卸载时的安全内存清理（v6）

NVIDIA 开源 GPU 驱动 nova-core 提交了第 6 版补丁系列（共 7 个补丁），由 Alexandre Courbot 和 Eliot Courtney 编写，已有 2 位审阅者参与审查。这组补丁解决的问题是：当驱动加载（probe）时，一个叫 FWSEC-FRTS 的固件会在显存中创建一块受保护的安全区域（WPR2），用来存放 GSP 固件，然后 Booter Loader 会把 GSP 固件加载到这块区域并启动它。问题在于，当驱动被卸载时，这些操作需要被"撤销"——特别是 WPR2 安全区域需要被释放，GSP 也需要被停止运行。

你可以把它想象成这样：你在电脑上安装了一个 GPU 驱动，驱动启动时会在显卡内存里"圈一块地"放自己的专用程序。当你卸载驱动的时候，这块地必须被归还，否则下次再装驱动就可能出问题。这组补丁就是在做这个"归还"的工作——运行 Booter Unloader 和 FWSEC-SB 来逆向清理启动时做的所有事情。

这是 Nova 驱动走向成熟的重要一步，因为"能正确卸载"是一个生产级驱动的基本要求。经过 6 轮迭代，说明社区对代码质量要求非常严格。

Asahi DRM：GEM SHMEM 抽象改进

Lyude（Red Hat 的 DRM 开发者）在 Zulip 的 #DRM 频道分享了她对 Asahi（Apple Silicon GPU）驱动中 GEM SHMEM（图形执行管理器·共享内存）抽象的改进工作。她在 freedesktop.org 的 GitLab 上推送了新的提交，包含了更多单元测试，并计划在下周二回来后清理代码并正式发送补丁。

GEM 是 Linux DRM 子系统管理 GPU 内存的框架，而 SHMEM 后端允许 GPU 内存对象通过系统共享内存来分配。这项改进意味着 Apple Silicon 芯片的 GPU 驱动（Asahi）在内存管理方面会更加可靠，同时有更多测试覆盖来保证质量。

️ 构建系统与新架构支持

Rust 工具链缺失时让构建直接报错（v2）

Neal Gompa 和 Sasha Finkelstein 提交了一个重要的构建系统改进补丁（第 2 版，已有 1 位审阅者）。当前的问题是：如果你在内核配置中开启了 RUST=y（意思是"我要启用 Rust 驱动"），但系统上实际没有 Rust 编译器，内核构建系统会悄悄地把所有 Rust 驱动跳过，最终给你一个"成功"的构建。然后你就会疑惑：明明选了 Rust 驱动，为什么编译出来的内核里找不到？

这就好比你去餐厅点了牛排，服务员说"好的"，结果上菜时只有沙拉——因为厨房没有牛排但没告诉你。这个补丁的做法是：如果你点了牛排（RUST=y）但厨房没有牛排（RUST_IS_AVAILABLE=n），就直接告诉你"做不了"（构建失败），而不是假装一切正常。作者指出，这与 OpenSSL 缺失时的行为一致——缺了就报错，不会默默跳过。

内核抽象与 API

内核抽象与 API

RCU：为 call_rcu() 添加 Rust 抽象（v1）

Philipp Stanner 提交了 call_rcu() 的 Rust 抽象（第 1 版，已有 1 位审阅者）。RCU（Read-Copy-Update）是 Linux 内核中一种非常重要的同步机制，专门为"读多写少"的场景设计。它允许多个 CPU 同时读取共享数据而不需要加锁，只有写入时才需要特殊处理。

call_rcu() 是 RCU 机制中"延迟释放"的核心函数——当你想删除一个被 RCU 保护的数据结构时，你不能立即释放它（因为可能还有其他 CPU 正在读），而是通过 call_rcu() 注册一个回调函数，等所有读取者都完成后再执行释放。这就像图书馆要下架一本书，不能在有人正在读的时候直接抢走，而是等所有人读完再收回。

为这个函数提供 Rust 抽象，意味着 Rust 驱动开发者可以用安全的 Rust API 来使用 RCU 的延迟回调功能，而不需要直接调用不安全的 C 绑定。

configfs 属性声明过程宏

Gary Guo 提交了一个新的过程宏（procedural macro）补丁（已有 1 位审阅者），用于声明 configfs 属性。configfs 是 Linux 内核中的一个特殊文件系统，允许用户空间通过创建目录和文件来配置内核对象——比如你可以通过 configfs 来配置 USB gadget 设备，就像在文件管理器里操作文件夹一样来配置硬件。

之前在 Rust 中声明 configfs 属性需要大量样板代码（boilerplate）。这个过程宏让你可以用简洁的声明式语法来定义属性，编译器会自动帮你生成底层的绑定代码。这降低了用 Rust 编写 configfs 驱动的门槛。

Zulip 讨论：如何在 Rust 中使用 WARN_ON

Philipp Stanner 在 Zulip 的 #Help 频道提问：能不能直接用 unsafe { bindings::WARN_ON(true) } 来调用内核的 WARN_ON 宏？Manos Pitsidianakis 回复指出，应该去看 rust/kernel/bug.rs 里已有的封装函数，而不是直接调用底层绑定。这个问题很快就解决了，Philipp 标记了话题为已解决。

这个小讨论反映了 Rust-for-Linux 的一个重要理念：尽量使用已有的安全抽象，而不是到处写 unsafe 直接调用 C 绑定。如果你刚开始写 Rust 内核代码，记得先看看 rust/kernel/ 目录下是否已经有你需要的封装。

VIRTIO 子系统

Virtio 子系统

Virtio Rust 抽象 RFC 系列

Manos Pitsidianakis 在 Zulip 的 #General 频道宣布，他已经发布了一组 RFC（征求意见稿）补丁系列，为 Virtio 子系统引入 Rust 抽象。Virtio 是虚拟化环境中最重要的设备接口标准——当你在虚拟机（如 QEMU/KVM）中使用网络、磁盘、随机数生成器等设备时，底层大概率用的就是 Virtio。

Manos 提到，这组补丁在不断演进：他最初使用了一个 virtio-rtc（实时时钟）样例驱动来演示 API，但后来替换为了一个 virtio-rng（随机数生成器）参考驱动。virtio-rng 更简单，更适合作为教学和参考实现。这表明社区在认真考虑 API 的易用性和可理解性。

Virtio 的 Rust 抽象一旦完成，将为在虚拟化环境中使用 Rust 编写高性能设备驱动打开大门，这对云计算场景意义重大。

代码风格与导入整理

代码风格与导入整理

统一采用竖排导入风格 & 清理冗余导入（v3，共 7 补丁）

Alvin Sun 提交了另一组 7 补丁系列（第 3 版），对内核 Rust 代码的 use 导入语句进行统一整理。这组补丁做了两件事：

第一，统一导入风格。把类似 use kernel::{error::Error, prelude::Result}; 的"横排"写法改成每个导入项单独一行的"竖排"写法。这样做的好处是：git diff 更清晰（改一个导入只影响一行）、代码审查更容易、合并冲突更少。

第二，删除冗余导入。kernel::prelude 已经重新导出（re-export）了 Error、Result、Pin、c_int 等常用类型，所以各个模块中单独导入这些类型是多余的。补丁删除了 miscdevice、block/mq、rnull、samples、doctest 等模块中的冗余导入。

受影响的文件/模块包括：rust/kernel/miscdevice.rs、samples/rust/rust_misc_device.rs、rust/kernel/block/mq.rs、drivers/block/rnull.rs、以及 doctest 基础设施。虽然这类"代码清理"看起来不起眼，但对于一个快速成长中的代码库来说，尽早统一风格可以避免后续更大的技术债务。
