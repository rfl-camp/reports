I2C 总线子系统 BUG 修复

I2C 总线子系统 Bug 修复

修复 I2cAdapter 引用计数重复递增问题

开发者 Nicolás Antinori 发现了 I2C 适配器 Rust 封装中一个引用计数（refcount）的 Bug。

问题出在 I2cAdapter::get() 函数里：当它调用 C 函数 i2c_get_adapter() 时，引用计数已经加了 1。但随后代码又通过 .into() 将原始指针转换成了 ARef（自动引用计数的智能指针），而 From<&T> for ARef<T> 的实现里会再加一次引用计数。这样就导致引用计数多加了一次。

打个比方：就像你去图书馆借书，管理员在借书卡上记了一笔「借出」，但你走到门口时保安又记了一笔，结果系统以为你借了两本，还书时只还了一本，系统永远觉得你还欠一本——这本书就永远不会被释放回书架了。在内核里，这意味着 I2C 适配器的内存永远不会被正确释放，造成内存泄漏。

💡 小白科普
引用计数（Reference Counting）：内核用来追踪一个对象「有多少人正在使用」的机制。每当有新的使用者，计数加 1；使用者释放时，计数减 1；当计数归零，对象才会被真正释放。计数不正确会导致要么提前释放（崩溃）、要么永远不释放（内存泄漏）。 📖 内核引用计数文档

块设备子系统 BUG 修复

块设备子系统 Bug 修复

修复 GenDiskBuilder 构建失败时的资源清理问题

开发者 Haoze Xie（由 Ren Wei 提交）发现了 Rust 块设备层中 GenDiskBuilder::build() 的一个资源泄漏问题。

GenDiskBuilder 是用来创建「通用磁盘」（gendisk）对象的构建器——可以把它想象成一个「组装磁盘的工厂」。问题在于：如果 build() 在调用 C 函数 __blk_mq_alloc_disk()（分配磁盘对象）之后的步骤失败了，那个已经分配好的磁盘对象就被「遗弃」在内存里了。它会一直待到调用者释放最后一个 tagset（标签集，管理 I/O 请求的数据结构）引用时才被清理——但如果调用者不知道这件事，这个磁盘对象就成了内存里的「孤儿」。

修复方法是：在失败路径中，先主动释放那个临时创建的 gendisk 对象，再把外来的队列数据转换回原来的格式归还给调用者。这样就确保了「谁创建、谁清理」的原则，不会在失败时留下悬挂资源。

⚡ 编译优化

⚡ 编译优化

为 OPP 模块方法添加 inline 标记

同样来自 Nicolás Antinori 的补丁。他在使用 LLVM 19.1.7 + Rust 1.85.0 编译内核时发现，OPP（Operating Performance Points，工作性能节点）模块的一些 Rust 方法——比如 OPP::freq()（获取频率）和引用计数的 dec_ref()（减少引用）——被编译器生成为独立的函数符号，出现在了 vmlinux（内核二进制文件）的符号表里。

问题是什么？这些方法本身非常简短，通常只是对 C 函数的一层薄薄的包装，它们本应被「内联」到调用处（就像把一个很短的函数的代码直接「复制粘贴」到每个调用它的地方），而不是作为独立函数存在。作为独立函数意味着每次调用都有额外的函数调用开销（跳转、保存寄存器等），对于这种频繁调用的热路径代码来说是不划算的。

修复方法很简单：给这些方法加上 #[inline] 属性，提示编译器「请把这些方法内联掉」。这样生成的内核二进制会稍微紧凑一些，运行时性能也会略有提升。

💡 小白科普
OPP（Operating Performance Points）：内核中描述设备「在某个电压下能跑多快频率」的配置。CPU、GPU 等硬件通常有多个 OPP，内核的功耗管理模块会根据负载在不同 OPP 之间切换，实现「忙时加速、闲时省电」。 📖 OPP 文档
内联（inline）：编译器把函数体直接「嵌入」到调用点，省去函数调用的跳转开销。特别适合短小精悍的函数。 📖 Rust inline 属性
