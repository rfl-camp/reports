️ GPU / DRM 驱动

Tyr 驱动：将驱动类型和驱动数据分离

Danilo Krummrich 提交了一组两个补丁，对 Tyr GPU 驱动的内部架构进行了重构。之前驱动的"类型定义"和"私有数据"混在一个结构体里，这次把它们拆成了两个：TyrPlatformDriver（一个空的"单元结构体"，只用来实现 platform::Driver trait）和 TyrPlatformDriverData（存放驱动实际需要的私有数据）。这样做的好处是职责更清晰——类型定义负责告诉内核"我是谁"，数据结构负责存"我需要什么"。这是一种在 Rust 驱动开发中逐渐形成的设计模式，让代码更容易维护和理解。Boris Brezillon 和 Eliot Courtney 参与了代码审查。

Tyr 驱动：直接使用 IoMem 代替 Devres 包装

同样来自 Danilo Krummrich 的另一组补丁。之前 Tyr 驱动在探测（probe）阶段访问 I/O 内存时，会把 IoMem（代表一段内存映射区域的类型）包在 Devres（设备资源管理器）和 Arc（引用计数指针）里。但实际上，这段 I/O 内存映射只在 probe 阶段使用，并不需要存到驱动数据里长期持有。现在 IoMem 已经支持了生命周期参数，可以直接使用，不需要额外的 Devres 包装了。这不仅简化了代码，还去掉了 Devres access(dev) 这个模式在 issue_soft_reset 流程中的使用，减少了不必要的间接层。打个比方：以前你要通过一个保险箱（Devres）来拿钥匙（IoMem），现在钥匙直接放口袋里就行了。

nova-core：为 Bar 映射引入生命周期参数

Alexandre Courbot 和 Eliot Courtney 在讨论和审查一组 5 个补丁，目标是给 nova-core 驱动（这是一个正在开发中的用 Rust 编写的 NVIDIA GPU 驱动）的 Bar 类型加上生命周期参数。PCI BAR（Base Address Register）是 GPU 和 CPU 之间通信的"窗口"，驱动通过它来读写 GPU 的寄存器。之前 Bar 的生命周期管理不够精确，现在通过 Rust 的生命周期系统，可以在编译期就保证你不会在 BAR 映射已经被释放后还去访问它——这是 C 语言驱动中常见的 bug 来源。这组补丁是 PCI BAR 资源名称 'static 生命周期系列（共 24 个补丁）的一部分。

PCI BAR 资源名称使用 'static 生命周期（v5，24 个补丁）

这是一个相当大的补丁系列，已经迭代到第 5 版了。核心目标是让 PCI BAR 的资源名称（resource name）使用 'static 生命周期，也就是说这些名称字符串在整个程序运行期间都有效。这解决了之前资源名称可能在运行时被释放而导致悬垂引用的风险。24 个补丁逐步重构了相关的类型和接口，涉及 PCI 子系统的多个层面。Eliot Courtney 和 Alexandre Courbot 正在审查这些改动。

Zulip 热议：DMA Fence 的生命周期管理难题

在 Zulip 的 #DRM 频道，Philipp Stanner、Gary Guo、Boris Brezillon、Danilo Krummrich 等人展开了一场长达 66 条消息的深入讨论，话题是 DMA Fence 在 Rust 中如何安全地管理。DMA Fence 是 GPU 驱动中非常核心的同步机制——当 GPU 在后台执行一个任务时，fence 就像一个"完成标志"，CPU 可以通过它来等待 GPU 任务完成。Philipp 提出了一个关键观察：在释放（drop）一个 DriverFence 之前，必须等待一个宽限期（grace period），否则可能会有其他代码还在引用这个 fence。他还提出了一个有趣的类比：DMA Fence 的"已信号"（signalled）标志本质上就像 Rust 内核中 Revocable 类型的"已撤销"（revoked）标志——两者都是用来标记一个资源是否还有效的。这场讨论目前还在进行中，大家在探索如何用 Rust 的类型系统来安全地表达这些复杂的并发约束。

Binder 驱动（Android IPC）

使用严格来源追踪（Strict Provenance）API 替代裸指针转换

Tamir Duberstein 提交了一组 5 个补丁（v2 版本），这是今天 Binder 驱动最重要的改动。之前代码中存在一些"指针转整数"的操作（比如把一个内存地址转成数字来做计算），这在 Rust 中是合法的但不够安全——编译器很难追踪这个整数到底代表什么内存地址，可能引入未定义行为。严格来源追踪（Strict Provenance）是 Rust 1.84.0 稳定的一套新 API，它让指针操作更加明确：每个指针都清楚地知道自己"来自哪里"、"能访问哪些内存"。由于 Rust-for-Linux 项目当前最低支持 Rust 1.85.0（Debian Trixie），所以可以放心使用这些新 API。Alice Ryhl 参与了审查。

设备资源管理（DEVRES）

设备资源管理（Devres）

为 Devres<T> 添加 'static 约束——修复内存泄漏导致的安全隐患

Danilo Krummrich 提交了一个重要的安全修复补丁。Devres 是 Rust 内核中对 C 语言 devres（设备资源管理）子系统的封装，它的作用是在设备被移除时自动清理相关资源——就像你拔掉 USB 设备时系统自动释放相关内存一样。问题出在哪呢？如果有人用 core::mem::forget()（这在 Rust 中是安全操作！）"忘记"了一个 Devres 对象，它的 Drop（析构函数）就不会运行。但 C 端的 devres 回调仍然会在设备解绑时触发，去释放内部的 Revocable，进而在原地 drop 类型 T。如果 T 中包含非 'static 的引用，这就可能导致 use-after-free（释放后使用）——一种严重的内存安全漏洞。修复方法很直接：给 Devres::new() 的类型参数 T 加上 'static 约束，确保 T 不包含任何短生命周期的引用。Eliot Courtney 和 Alexandre Courbot 参与了审查。

📬 查看补丁
优化类型名称分配并修复截断问题（v2）

这个补丁解决了两个问题。第一个是空间浪费：之前每个不同的 Devres<T> 实例都会在只读数据段（.rodata）中分配一个 128 字节的固定数组来存储类型名称（用于调试时识别"这是什么类型的资源"）。在生产构建中，这些名称占了不少无用空间。第二个是静默截断：如果类型名称超过 127 字节（对于泛型嵌套很深的类型很常见），名称会被悄悄截断，调试日志里看到的是残缺的名字，完全没有任何警告。补丁的解决方案是：把 TYPE_NAME、TYPE_NAME_BUF 和 TYPE_NAME_CSTR 这些常量改为按需分配，只在开启调试时才生成，并在截断时输出提示信息。David Laight、Miguel Ojeda、Greg KH 参与了审查。

debugfs：修复 FileOps 的 transmute 未定义行为

Tamir Duberstein 发现并修复了 debugfs（调试文件系统）模块中的一个潜在未定义行为。之前的 FileOps::adapt() 函数会把 &FileOps<T> 直接 transmute（强制转型）成 &FileOps<T::Inner>。问题在于 FileOps 使用的是 Rust 默认的内存布局（不是 #[repr(C)]），而 Rust 的默认布局不保证不同泛型实例有相同的内存排列方式。也就是说，FileOps<A> 和 FileOps<B> 的字段在内存中的位置可能不同，强制转型就会读到错误的数据。这就像你按照 A 公寓的房间布局去找 B 公寓的卧室，结果走进了厨房。Matthew Maurer 参与了审查。

⚡ 中断与同步机制

中断与自旋锁：引入计数式中断禁用/启用（v2，12 个补丁）

Boqun Feng 提交了一组 12 个补丁，为 Rust 内核代码引入计数式中断禁用/启用机制。什么意思呢？在内核中，有时候需要暂时"关闭"中断（比如在操作关键数据时不想被打断），用完后再"打开"。但如果有嵌套调用——函数 A 关了中断，然后调用函数 B，B 也关了中断，B 返回时开了中断，此时函数 A 还以为中断是关着的，但实际上已经开了！计数式方法解决了这个问题：每次关中断时计数器加 1，开中断时减 1，只有计数器回到 0 时才真正开启中断。这就像一个会议室的门——只有最后一个人离开时才需要关灯，中间有人出去不需要动开关。这组补丁同时涉及 IRQ（中断请求）和 spin_lock（自旋锁）两个子系统。BPF CI bot 已经参与了自动化测试。

Zulip：私有 trait 边界的编译警告怎么处理？

在 Zulip 的 #Help 频道，Philipp Stanner 遇到了一个问题：他定义了一个私有 trait，用在公开 API 的类型约束中，编译器报出了"private bounds"（私有边界）警告。他的 trait 用于在编译期检查用户传入的数据是否实现了 Copy，或者是否被包装在特定类型中。Manos Pitsidianakis 建议使用 Sealed 模式：把 trait 设为公开的，但把它放在一个私有模块里，这样外部代码虽然能看到这个 trait，但无法实现它（因为实现需要访问私有模块中的父 trait）。Philipp 追问："为什么 Rust 不允许 trait 是私有的呢？"——这其实是 Rust 类型系统的一个有趣设计决策：公开 API 的约束必须是公开的，否则使用者无法理解 API 的要求。内核代码库中已经有多处使用 Sealed 模式的例子，搜索 trait Sealed 即可找到。

Rust-for-Linux 项目在 GitHub 上维护着一个长期 issue（#355），用于追踪社区希望 Rust 编译器（rustc）增加的特性和修复的 Bug。这是一个标记为 "toolchain" 和 "meta" 的元议题，由项目维护者 ojeda 创建。它就像一个"许愿清单"，记录了内核开发者在使用 Rust 时遇到的编译器限制和痛点。比如前面提到的高阶生命周期支持、更好的 const 泛型等需求，都可能出现在这个列表上。如果你对 Rust 编译器的开发感兴趣，这个 issue 是了解"内核开发者需要什么"的好窗口。

💡 小白科普
Sealed 模式：一种 Rust 设计模式，让 trait 对外可见但不可被外部实现。做法是让 trait 继承一个定义在私有模块中的父 trait，外部代码因为看不到父 trait 而无法提供实现。常用于库 API 设计中防止用户"误实现"。📖 学习更多
