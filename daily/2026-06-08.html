️ GPU/DRM 图形驱动

️ GPU/DRM 图形驱动

GEM shmem Rust 绑定 v18（总览）

这是今天最重要的一组补丁。GEM shmem 是 Linux 内核中图形驱动管理显存的核心模块——你可以把它想象成"GPU 的内存管家"。Alexandre Courbot（来自 NVIDIA）正在给这个模块编写 Rust 语言的"接口封装"（binding），让未来用 Rust 写 GPU 驱动的开发者能安全地调用这些底层功能。这组补丁已经迭代到第 18 版了，说明社区对代码质量要求非常高，每一版都在根据审核意见不断打磨。参与审核的有 Gary Guo、Miguel Ojeda 等核心维护者，共收到 4 条 review 意见。

新增 DmaResvGuard 辅助结构

Gary Guo 提交了一个 DmaResvGuard（DMA 预留守卫）辅助结构。这是什么意思呢？当 GPU 要使用一块内存时，需要先"预订"它（就像餐厅订位），防止别人同时修改。DmaResvGuard 就是一个 Rust 风格的"锁"，确保当你拿到这个守卫对象时，对应的内存预留一定是有效的；当守卫被释放时，锁也自动解除。这种设计利用了 Rust 的所有权系统来防止"忘记解锁"这类 bug——在 C 代码中这类问题曾导致过死锁和数据竞争。

📬 查看补丁
新增 vmap 映射函数

Alexandre Courbot 还为 GEM shmem 绑定添加了 vmap（虚拟内存映射）函数。简单来说，GPU 使用的显存在物理上可能是分散的碎片，而 vmap 的作用是把这些碎片"拼"成一块连续的虚拟地址空间，这样 CPU 就能像访问一整块内存一样访问它们。这对于 CPU 需要读写 GPU buffer 的场景（比如上传纹理数据）非常关键。Rust 绑定确保了这个映射/解映射过程的生命周期安全——映射不会在底层 buffer 被释放后还存活。

基础设施与工具宏

基础设施与工具宏

bitfield 宏新增 KUnit 测试（v5）

Alexandre Courbot 为 Rust 内核中的 bitfield（位域）宏 添加了 KUnit 测试。位域是什么？硬件寄存器常常把多个开关/配置"打包"在一个整数的不同 bit 位上（比如第 0-3 位控制速度，第 4 位是开关）。bitfield 宏帮助开发者安全地读写这些位，不用手动做位运算。这次提交的 KUnit 测试用来验证这些宏在各种边界情况下是否正确工作——这是第 5 版了，说明测试覆盖在逐步完善。KUnit 是内核内置的单元测试框架，类似于应用开发中的 pytest 或 JUnit。

📬 查看补丁
impl_flags! 宏增加获取底层整数值的方法（v2）

Miguel Ojeda（Rust-for-Linux 项目的主要维护者）提交了对 impl_flags! 宏的增强。这个宏用来定义"标志位集合"——想象一下文件权限 rwx，每一种权限就是一个标志位，它们可以自由组合。这次的改动新增了一个方法，让你能把标志位集合转换回原始整数值。为什么需要这个？因为和 C 代码交互时（比如调用内核的 C 函数），经常需要传递原始整数值。这是第 2 版，Miguel 根据 review 反馈做了改进。

内核版本发布

Linux 7.1 第二轮 Rust 修复已合入主线

pr-tracker-bot 确认了 Rust fixes for 7.1（第 2 轮） 的 GIT PULL 请求已经被处理。这意味着这批针对 Linux 7.1 版本的 Rust 相关 bug 修复已经进入了 Linus 的主线代码树。通常在内核发布候选（RC）阶段，各子系统维护者会陆续提交修复补丁。这是第二轮说明之前还有一些遗留问题需要修补。对于 Rust-for-Linux 来说，这表明 Rust 代码已经是正式发布流程的一部分，和 C 代码享受同等待遇——每个版本都有专门的修复窗口。

社区协作

Zulip：寻找 Rust 工具链 bug 分诊帮手

在 Zulip 的 #Help 频道中，Lyude（知名 DRM/Nouveau 驱动开发者，Red Hat 工程师）发起了一个话题，询问社区是否有人能帮忙分诊（triage）Rust 工具链相关的 bug。所谓"分诊"，就是对收到的 bug 报告进行分类、确认优先级、复现和打标签——就像医院急诊的"预检分诊"一样，决定哪些问题最紧急需要先处理。从回复来看，Lyude 得到了积极的帮助回应（"Yes this helps tremendously, thank you!"），说明社区在工具链维护方面正在建立更好的协作机制。这对于 Rust-for-Linux 的长期健康发展很重要，因为 Rust 编译器本身的 bug 有时会阻碍内核开发。
