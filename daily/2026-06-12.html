GPUVM 抽象层适配 DeviceContext 新架构

GPUVM 抽象层适配 DeviceContext 新架构

这个补丁由 Deborah Brouwer 提交，Alice Ryhl 和 Danilo Krummrich 等人参与审查。背景是这样的：内核最近引入了一个叫 DeviceContext 的新概念，用来管理 GPU 设备的上下文信息。但原来的 GPUVM（GPU 虚拟内存管理器）代码里有一个设计假设——认为"驱动对象类型"和"GPUVM 对象类型"必须完全一样。现在有了 DeviceContext 之后，这个假设就不成立了。这个补丁的做法是：不再强制要求这两个类型相同，而是放宽了类型约束，让 GPUVM 更灵活。简单来说，就像原来规定"钥匙和锁必须是同一个品牌"，现在改成了"只要钥匙能开锁就行"。

GPUVM 新增 SmContext 生命周期约束

GPUVM 新增 SmContext 生命周期约束

这个补丁来自 Boris Brezillon（由 Deborah Brouwer 提交），解决了一个关于 Rust 生命周期的微妙问题。在 Rust 中，"生命周期"是一种确保引用不会变成"野指针"的机制。如果一个 DriverGpuVm 的实现本身带有生命周期参数，那它内部的 SmContext 类型可能依赖于这些生命周期。补丁的做法是添加一个 Self: 'ctx 约束，确保驱动实现的生命周期一定比 SmContext 的生命周期更长。就像你借了别人的工具来做事，你得保证工具的主人在你做完事之前不会把工具收走。

DRM GEM SHMEM 添加 vmap 函数（第 20 版！）

DRM GEM SHMEM 添加 vmap 函数（第 20 版！）

这个补丁系列已经迭代到了第 20 版，由 Deborah Brouwer 提交，Alice Ryhl 参与审查。GEM SHMEM 是 DRM 子系统中用来管理 GPU 共享内存的模块，vmap 函数的作用是把 GPU 使用的内存映射到 CPU 可以访问的虚拟地址空间——就像在两个不同城市之间搭一座桥，让 CPU 也能"看到"GPU 的内存。这个系列经过了漫长的审查和修改，说明社区对于 Rust 抽象层的安全性和正确性要求非常高。在 Zulip 的讨论中，Alice Ryhl 提到她一直在快速响应来自自动化审查工具 sashiko 的反馈并发送新版本，同时也在等待人类审查者的反馈。

I/O 复制方法大规模补丁系列（v4，共 20 个补丁）

I/O 复制方法大规模补丁系列（v4，共 20 个补丁）

Gary Guo 提交了一个包含 20 个补丁的大系列，为 Rust 的 I/O 抽象层添加了"复制方法"。之前的 dma_read! 和 dma_write! 宏在升级为 io_read! 和 io_write! 之后，丢失了一个功能——无法一次性读写大的数据结构体。但这个功能本身就存在语义不清的问题：即使结构体足够小，也无法保证读写是"原子的"（即一次性完成、中间不被打断）。这次的补丁系列重新设计了这个功能，用更安全、更清晰的方式实现了大结构体的 I/O 操作。

I/O 投影宏和方法（v4）

I/O 投影宏和方法（v4）

同样来自 Gary Guo 的补丁系列中的一部分，引入了一个 io_project!() 宏。这个宏的作用是：让你可以从一个大的 I/O 区域中"投影"出一个子视图。想象一下你有一面大墙（整个 I/O 区域），你可以用这个宏在墙上框出一个小窗口（子视图），只操作你需要的部分。它使用指针投影机制来在编译期做检查，确保你框的窗口不会超出墙的范围。对于需要类型转换的情况，还提供了 try_cast() 函数在运行时检查大小和对齐。

BINDER 驱动（ANDROID IPC）

Binder 驱动（Android IPC）

为 Node::add_death 添加所有权断言（v2）

为 Node::add_death 添加所有权断言（v2）

George Androutsopoulos 提交了这个补丁，Miguel Ojeda 和 Alice Ryhl 参与了审查，共有 4 位审查者。Binder 是 Android 系统中进程之间通信（IPC）的核心机制——就像 Android 上不同 App 之间的"邮局"。这个补丁在 Node::add_death 方法中添加了一个"所有权断言"，确保在给某个 Binder 节点注册"死亡通知"时，调用者确实拥有对该节点的正确引用。这是一种防御性编程，防止在复杂的并发场景下出现"你以为你管着这个节点，其实你已经管不了了"的情况。邮件列表上还有对此补丁的进一步讨论。

优化 Binder 线程退出时的 RCU 同步（v5，共 2 个补丁）

优化 Binder 线程退出时的 RCU 同步（v5，共 2 个补丁）

Alice Ryhl 提交了这个两部分的优化补丁系列。在之前的实现中，每当 Binder 中的一个线程被销毁时，都会调用 synchronize_rcu()——这是一个代价很高的操作，它会等待所有 CPU 都经过一个"静止状态"后才能继续。想象一下，每次有人离开办公室，所有人都必须放下手上的工作等一下才能继续，这显然很浪费时间。

优化分为两个补丁：第一个补丁让 PollCondVar（轮询条件变量）使用 kfree_rcu() 代替同步的 RCU 等待——这就像"你把辞职信放在桌上就行了，不用等所有人签字"，内存会在下一个 RCU 宽限期自动释放。第二个补丁把 poll 等待队列从每个线程移到了 Process 对象上，减少了需要清理的资源数量。

修复 GenDisk 的 Send trait 约束（v3）

修复 GenDisk 的 Send trait 约束（v3）

Yuan Tan 提交了这个修复补丁，Miguel Ojeda 参与了审查。问题出在 GenDisk<T>（通用磁盘，代表一个块设备，比如你的硬盘或 SSD）的 Send 实现上。原来的代码要求 T: Send，但这里的 T 是一个 Operations 实现——通常只是一个零大小的标记类型（就像一个"标签"，不实际存储数据）。所以检查 T 是否能安全地跨线程发送，完全没有意义。真正需要检查的是 GenDisk 内部实际持有的数据是否可以安全地跨线程传递。这个补丁修正了约束条件，让它检查正确的类型。这是一个类型系统层面的 bug 修复——虽然实际影响不大（因为标记类型几乎总是 Send 的），但它让代码在语义上更正确。

在 mrproper 中清理 zerocopy-derive 构建产物

在 mrproper 中清理 zerocopy-derive 构建产物

Miguel Ojeda 提交并已合并到 rust-next 分支。make mrproper 是内核构建系统中的一个清理命令——它比 make clean 更彻底，会把所有生成的文件都删干净（就像"恢复出厂设置"）。之前的提交引入了 zerocopy-derive（一个 Rust 过程宏）的构建支持，但忘了把它加到 mrproper 的清理列表里，导致"出厂设置"后还会残留一些 zerocopy-derive 的编译产物。这个补丁补上了这个遗漏。

Rust 模式下默认关闭 randstruct 以改善 allmodconfig 构建

Rust 模式下默认关闭 randstruct 以改善 allmodconfig 构建

Mark Brown 提交了这个补丁。randstruct 是一个安全加固特性，它会随机化内核结构体中字段的顺序，让攻击者更难通过猜测结构体布局来利用漏洞。但这个特性和 Rust 驱动不太兼容——因为 Rust 代码中绑定的 C 结构体布局必须和 C 端保持一致。allmodconfig 是一种"把所有模块都编译"的内核配置（常用于测试），如果 randstruct 开着且有 Rust 模块，编译就会出问题。这个补丁的解决方案很务实：当启用 Rust 时默认关闭 randstruct。

重构 build_assert 宏模块（v4）

将 zerocopy 的 IntoBytes 加入 prelude

将 zerocopy 的 IntoBytes 加入 prelude

Gary Guo 提交了这个简单但实用的补丁。IntoBytes 是 zerocopy 库提供的一个特征，表示"这个类型可以安全地转换为字节序列"。在内核 Rust 代码中，经常需要把结构体转换成字节流来进行 I/O 操作。把 IntoBytes（包括它的 derive 宏）加入 prelude（预导入模块）之后，所有 Rust 内核代码就不用每次都手动写 use zerocopy::IntoBytes 了——自动就能用。这是一个"生活质量改善"类型的修改。
