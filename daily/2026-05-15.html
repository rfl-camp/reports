️ GPU / DRM 驱动

DRM 子系统引入「高阶生命周期」私有数据机制（6 个补丁）

作者：Deborah Brouwer  |  审阅：Danilo Krummrich

这组补丁解决的是 DRM 驱动中一个比较棘手的「数据所有权」问题。简单来说，当 GPU 驱动需要在内核对象（比如一个 GEM 对象或文件描述符）里存放自己的私有数据时，Rust 的编译器需要确切知道这块数据能活多久——也就是"生命周期"。之前的方案在某些复杂场景下会碰壁，因为生命周期参数不够灵活。Deborah 的解决办法是引入 Rust 中的「高阶 trait 约束」（Higher-Ranked Trait Bounds, HRTB）技术，让私有数据的类型可以适配任意生命周期，就像给这个数据穿上了一件"万能尺码的衣服"。Danilo Krummrich 对这组补丁给出了积极反馈，双方正在讨论具体的 API 细节。

GEM 对象 debugfs 查询助手（13 个补丁）

作者：Danilo Krummrich

这是一组较大的补丁集，目的是为 Rust 编写的 DRM 驱动添加 debugfs 查询功能。debugfs 是 Linux 内核的一个调试用虚拟文件系统——你可以把它想象成一个"内核状态监控面板"，开发者可以通过读取里面的文件来查看内核内部正在发生什么。这组补丁让 Rust 驱动可以把 GEM（Graphics Execution Manager）对象的状态信息暴露到 debugfs 中，这样驱动开发者就能方便地检查 GPU 内存对象的状态、大小、引用计数等信息，对调试 GPU 驱动非常有帮助。13 个补丁分步实现了查询接口的 Rust 抽象层。

参与者：Lyude、Gary Guo  |  Zulip #DRM 频道

Lyude（来自 Red Hat，Asahi/Nova 项目核心开发者）在 Zulip 上分享了她为 Asahi GPU 驱动编写的一个新的容器类型。这个容器用于管理 GEM SHMEM 对象——也就是 GPU 通过共享内存（shared memory）方式管理的显存缓冲区。她特别提到这个设计用到了 Gary Guo 之前实现的 SetOnce 原语，并 @了 Gary 来审阅。Lyude 表示下周会正式将补丁发送到邮件列表。这个工作对 Apple Silicon 设备上的开源 GPU 驱动意义重大。

运行时电源管理（RUNTIME PM）

运行时电源管理（Runtime PM）

[RFC] 为 Rust 驱动添加运行时电源管理支持（3 个补丁）

作者：Beata Michalska（ARM）

这是今天最值得关注的新 RFC 系列之一！Beata Michalska 来自 ARM 公司，她提交了一套共 3 个补丁的系列，目标是让 Rust 编写的设备驱动能够使用 Linux 的运行时电源管理（Runtime PM）机制。这是什么意思呢？想象一下你手机里的各种硬件——摄像头、GPS、蓝牙——当你不用它们的时候，系统会自动让它们"睡觉"来省电，用的时候再"叫醒"它们。Runtime PM 就是内核中实现这个功能的框架。

补丁 1/3：核心抽象层

引入了一个名为 PMContext 的 Rust 结构体，它持有一个设备引用并建模整个运行时 PM 生命周期。这个上下文初始化时是"非活跃"状态，当 Runtime PM 被启用后转为"活跃"状态。驱动可以选择在初始化时配置设备的电源状态（活跃或挂起），并且能够携带自定义状态在挂起/恢复周期之间传递。核心设计是通过 Rust 的 trait 系统为每个驱动自动生成 dev_pm_ops 回调函数。

补丁 2/3：平台驱动集成

这个补丁将 PM 回调接入 platform_driver 的注册流程，这样 Rust 编写的平台设备驱动就能自动将自己的挂起/恢复回调暴露给内核的 PM 核心。此外还为 platform::Device 实现了 TryFrom 转换，使得 PM 回调能从通用的 Device 指针恢复出具体的平台设备类型——这在类型安全方面非常重要。

补丁 3/3：DRM Tyr 驱动演示（标记为 DO NOT MERGE）

第三个补丁是一个"示范性质"的实现——将 Runtime PM 接入实验性的 DRM Tyr 驱动，添加了基本的挂起/恢复钩子，为未来的电源门控（power-gating）做准备。这个补丁标记了"请勿合并"，纯粹是为了展示前两个补丁的 API 该怎么用。这是一种很常见的做法，帮助审阅者理解 API 的实际使用场景。

内核基础设施与宏系统

seq_print! 宏优化：绕过 C 格式化函数直接写入

作者：Donjuanplatinum  |  审阅：Greg KH

这个补丁是一个性能优化。之前 seq_print! 宏在输出内容时走了一条"弯路"：先用 Rust 构造一个 fmt::Arguments 对象，然后跨越 FFI 边界传给 C 的 seq_printf 函数，C 再用 vsnprintf 解析格式字符串 %pA，最后又回调到 Rust 来实际写入缓冲区。这相当于从北京寄一封信给隔壁邻居，却要经过上海中转站。现在这个补丁让 seq_print! 直接调用 seq_write，跳过了中间所有 C 层的格式化处理，路径更短、开销更小。Greg KH（Linux 稳定版维护者，内核核心人物之一）已经参与了审阅。

pin-init 模块内部重构（8 个补丁）

作者：Gary Guo

Gary Guo 提交了一组针对 pin-init 模块的内部重构补丁。pin-init 是 Rust-for-Linux 中非常重要的基础库，用于安全地初始化被"固定"（pinned）在内存中的数据结构。这组补丁的核心改动是「使用完整 slot 进行投影」——具体来说，在初始化过程中，之前的实现在处理结构体字段投影时可能只操作部分内存区域，改进后使用完整的内存槽位来进行投影操作，使得内部实现更加正确和一致。这属于纯内部重构，不影响外部 API，但提高了代码的健壮性。部分补丁已被选入子集进行推进。

dev_xx! 宏是否需要 println! 风格变体？

参与者：Hsiu Che Yu、Miguel Ojeda  |  Zulip #General 频道

Hsiu Che Yu 在 Zulip 上提出了一个问题：他发现代码中很多地方使用 dev_info!、dev_err! 等宏时，都要手动在末尾加 \n 换行符，这样写起来有点麻烦。他问是否值得像 println! 那样提供自动加换行的版本。Miguel Ojeda（Rust-for-Linux 项目负责人）回复说这是有意为之的设计——C 侧的 dev_info() 等函数也需要手动加 \n，Rust 侧故意保持一致，特别是当函数名完全相同时，保持行为一致能减少混淆。这个话题已被标记为已解决（✔）。

内存管理

内存管理

Binder 驱动 shrinker 改用 lock_vma_under_rcu()

作者：Lorenzo Stoakes

这个补丁优化了 Rust 版 Binder 驱动中的内存回收（shrinker）路径。Binder 是 Android 系统中进程间通信的核心机制——你手机上的 App 互相传递数据基本上都在用它。当系统内存紧张时，shrinker 会被触发来回收可以释放的内存。这个补丁将 shrinker 中查找 VMA（Virtual Memory Area，虚拟内存区域）的方式从传统的锁机制改为使用 lock_vma_under_rcu()。这是一种更轻量级的加锁方式，利用了 RCU（Read-Copy-Update）机制，在读多写少的场景下性能更好。简单来说，就像从"排队进门"变成了"门口看一眼就知道能不能进"，减少了不必要的等待。

️ 平台支持与构建系统

ARM 平台：KASAN 开启时禁用 Rust 支持

作者：Nathan Chancellor  |  审阅：Miguel Ojeda

Nathan Chancellor（知名内核构建维护者）提交了一个针对 ARM（32 位）平台的补丁。问题是这样的：KASAN（Kernel Address SANitizer）是内核的一个内存错误检测工具，用来抓越界访问、use-after-free 之类的 bug，非常好用。但当前在 32 位 ARM 平台上，KASAN 和 Rust 不能同时开启，两者一起编译会出问题。这个补丁的做法很直接——在 Kconfig 配置中加了一条规则：如果你打开了 KASAN，就自动不勾选 HAVE_RUST，从而避免用户踩坑。Miguel Ojeda 参与了审阅。这不是修复 bug，而是先把已知冲突标注清楚，未来再想办法让两者兼容。
