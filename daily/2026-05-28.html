️ S390 大型机架构：Rust 支持正式推进

今天 s390 架构（IBM 大型机使用的处理器架构）的 Rust 支持取得了重大进展。Heiko Carstens 提交的补丁系列已经迭代到 第三版（v3），共包含 4 个补丁，获得了 9 位开发者的审阅。这个补丁做的事情可以类比为：你买了一台新电脑（s390 大型机），现在要让它能"说" Rust 语言。具体来说，需要为这个架构提供一些"胶水代码"（arch glue），让 Rust 编译器生成的代码能正确地在 s390 硬件上运行。Miguel Ojeda 和 Alice Ryhl 等核心维护者都参与了审阅，说明这个系列已经比较成熟了。

📬 查看补丁：启用 Rust 支持 📬 查看补丁：启用 Rust v3

与此配套的还有 Gary Guo 和 Jan Polensky 提交的 jump_label 静态分支宏补丁。Jump label 是内核里一种非常精巧的优化技术——它可以在运行时动态修改代码中的跳转指令，把"几乎不走"的分支直接用 NOP（空指令）替换掉，从而加速热路径。这个补丁为 s390 实现了 ARCH_STATIC_BRANCH_JUMP_ASM 和 ARCH_STATIC_BRANCH_ASM 两个宏，让 Rust 代码也能使用这一优化。Alice Ryhl 参与了审阅。

同步原语：SRCU 封装与 RCU 新接口

同步原语：SRCU 封装与 RCU 新接口

Onur Özkan 提交的 SRCU（Sleepable RCU，可睡眠 RCU）Rust 抽象已经迭代到了第五版，包含 4 个补丁。SRCU 是一种特殊的读-拷贝-更新机制，和普通 RCU 不同的是，它允许在读侧临界区中睡眠（即可以执行可能阻塞的操作）。这个 Rust 封装提供了一个基于 Guard 模式的安全 API：你进入 SRCU 读取区时会得到一个"守卫"对象，当守卫被丢弃时自动退出临界区，不会忘记解锁。清理工作通过 PinnedDrop 处理，确保所有待处理的宽限期和回调都被妥善排空（通过 synchronize_srcu）。这个系列的直接动机是 Tyr 驱动的 reset 基础设施需要用 SRCU 来序列化硬件访问。

📬 查看补丁：SRCU 抽象 📬 查看补丁：SRCU 辅助函数

配套的还有两个补丁：一个是把 srcu_readers_active() 函数从 kernel/rcu/srcutree.c 移动到头文件 include/linux/srcu.h 中，这样 Rust 的 FFI 辅助函数就能直接调用它了（否则 Rust 那边看不到这个函数）。同时还为 CONFIG_TINY_SRCU 提供了头文件实现，确保不管选哪种 SRCU 后端都能用。另一个补丁更新了 MAINTAINERS 文件，把 Rust SRCU 相关的文件加入到 SRCU 维护者条目中。Boqun Feng 参与了审阅。

同步原语：SRCU 封装与 RCU 新接口

Boqun Feng 和 Philipp Stanner 等人还提交了 call_rcu() 的 Rust 抽象。call_rcu() 是 RCU 机制中的一个关键函数，它的作用是"等所有人都读完了，再执行回调来释放旧数据"——就像图书馆要下架一本书，得等所有正在看这本书的人都还回来之后才能真正销毁它。这个抽象让 Rust 驱动可以安全地使用这种延迟释放模式。Alvin Sun 也参与了讨论，目前收到了 4 条审阅意见。

📬 查看补丁：call_rcu() 抽象

在 Zulip 的 #General 频道，Manos Pitsidianakis 和 Boqun Feng 讨论了 带中断禁用的自旋锁（Spinlocks with IRQs）的进展。这个话题涉及到一个很长的讨论线程。Boqun Feng 指出，Rust 部分的实现可以在 Lyude Paul 的补丁系列中找到，目前的重点是先把 C 语言那边的基础设施合入上游。Manos 表示会去审阅。自旋锁是内核中最基本的同步原语之一，在中断上下文中使用时需要特别小心（必须禁用中断，否则可能死锁），所以这个工作对驱动开发者来说非常重要。

GPU / DRM 驱动子系统

GPU / DRM 驱动子系统

Alistair Popple 提交了一个包含 6 个补丁的系列，为 DRM 子系统引入了 UnbindGuard 抽象。这解决的是一个很实际的问题：当 GPU 驱动正在做某些操作（比如提交渲染命令）的时候，如果用户突然拔掉了显卡（热插拔）或者卸载了驱动，就可能导致驱动访问到已经无效的硬件资源，造成崩溃。在 C 语言中，内核用 drm_dev_enter() 和 drm_dev_exit() 这对函数来保护这样的关键区段——进入时检查设备是否还活着，退出时告诉内核"我用完了"。UnbindGuard 把这个模式封装成 Rust 的 RAII 守卫：只要你持有这个守卫，设备就不会被解绑；守卫被丢弃时自动调用 exit。这样就不可能忘记调用 exit 了。Gary Guo 参与了审阅。

📬 查看补丁：UnbindGuard

在 Zulip 的 #General 频道，Alvin Sun 分享了 Tyr 驱动 debugfs 抽象的重新设计。根据 Danilo Krummrich 在 v1 审阅中的反馈，Tyr 驱动不应该自己创建 debugfs 目录，而应该挂载到 DRM 子系统为每个设备自动创建的 debugfs 根目录下。重新设计后的方案引入了一个 SeqShow trait，驱动通过 &SeqFile 来输出调试信息。这是一种更符合内核规范的做法——就像你不应该在公司里自己建一个文件柜，而应该把文件放到部门统一的文件柜里。

💬 查看讨论

Philipp Stanner 在 #DRM 频道发起了关于 DmaFence 的讨论。DMA Fence 是 GPU 驱动中用来同步不同操作的机制——比如"等这个渲染命令完成后，再把结果显示到屏幕上"。Philipp 提出了一个有趣的设计困境：如果禁止在 DMA fence 中使用任何需要 Drop 的类型，那驱动甚至不能在 fence 里存一个调试用的字符串（因为 String 需要 Drop 来释放内存）。他觉得这个限制可能过于严格了。这反映了 Rust 的所有权系统和内核的特殊需求之间的张力——有时候内核的使用模式不完全符合 Rust 的标准模式。

设备资源管理（DEVRES）

设备资源管理（Devres）

Gary Guo 提交了一个补丁，为 Devres<T> 添加了 'static 生命周期约束。Devres 是内核中"设备管理资源"的 Rust 封装——当设备被移除时，所有与它关联的资源会被自动清理（就像你退租时，房东自动帮你把你租期内添置的家具都处理掉）。添加 'static 约束意味着存储在 Devres 中的类型不能包含非静态的引用，这是为了确保资源在设备卸载时的延迟清理不会导致悬垂引用（引用了已经不存在的数据）。Danilo Krummrich 参与了审阅，共收到 6 条反馈。

📬 查看补丁：'static 约束

Gary Guo 还提交了另一个改进：使用编译时的 type_name 来提供调试信息。之前 Devres 的调试输出可能使用运行时获取的类型名称，而改为编译时常量后，不仅性能更好（省去了运行时的开销），而且类型名称在编译时就确定了，更加可靠。Miguel Ojeda 参与了审阅。这种改动虽然小，但体现了 Rust 的一个优势：很多工作可以在编译时完成，而不是推迟到运行时。

📬 查看补丁：编译时 type_name
💡 小白科普
Devres（Device-managed Resources）：内核的一种资源管理机制。用 devres 分配的资源会在设备解绑时自动释放，省去手动清理的麻烦，也避免了资源泄漏。类比：像智能指针，但管理的是设备生命周期内的资源。 📖 了解 Devres
'static 生命周期：Rust 中表示"至少活到程序结束"的生命周期标记。加了这个约束，就确保数据不会在还被使用时就被销毁。 📖 了解 'static

块设备驱动

块设备驱动

Alice Ryhl 提交了一个修复补丁，将 Rust 侧的 块设备多队列（blk-mq）回调签名与 C 侧对齐。具体来说，之前有一个 C 提交 b040a1a4523d 把 blk_mq_ops::init_request 回调中的 numa_node 参数类型从 unsigned int 改成了 int（因为 NUMA 节点号可以是负数，-1 表示"任意节点"）。但 Rust 那边的绑定没有同步更新，导致函数签名不匹配。如果不修复，Rust 的函数指针不能正确强转为 C 的函数指针，编译时可能会报错或产生未定义行为。这就像两个人约好用同一种格式传数据，结果一边改了格式没通知另一边。Andreas Hindborg 和 Gary Guo 参与了审阅，共收到 7 条反馈。

📬 查看补丁
💡 小白科普
blk-mq（Block Multi-Queue）：Linux 内核的多队列块设备层，负责处理磁盘/SSD 等存储设备的 I/O 请求。现代 NVMe SSD 有多个硬件队列，blk-mq 让每个 CPU 核心可以独立提交请求，大幅提升性能。 📖 了解 blk-mq
NUMA（Non-Uniform Memory Access）：多处理器系统中，不同 CPU 访问不同内存区域的速度不同。numa_node 指定应该在哪个 NUMA 节点上分配内存，-1 表示"我不在乎，系统自己选"。 📖 了解 NUMA

宏、类型系统与核心 API 改进

宏、类型系统与核心 API 改进

Alexandre Courbot 提交了 bitfield 宏第四版（v4）补丁系列，共 7 个补丁。这次的一个重要修复是：宏内部使用的类型没有用完整路径限定（fully qualified），比如直接写 u32 而不是 core::primitive::u32。在大多数情况下这没问题，但如果使用者的模块中恰好定义了同名的类型（shadow），就会出错。就像你在教室里喊"张三"，大家都知道是谁；但如果班里有两个张三，你就得说"一班的张三"了。Yury Norov 和 Miguel Ojeda 参与了审阅。

📬 查看补丁：类型限定

同一个系列中还包含了 bitfield 的 KUnit 测试。KUnit 是 Linux 内核的单元测试框架，这些测试确保 bitfield 宏生成的位域操作代码行为正确。有了测试保障，未来对宏的修改就不容易引入回归问题。Yury Norov 提供了审阅反馈。

📬 查看补丁：KUnit 测试

Sami Tolvanen 将 module_param 模块中空指针警告的输出从普通 pr_warn 改为了 pr_warn_once!。为什么要改？因为模块参数可能在内核运行期间被反复读取，如果每次都打印警告，内核日志会被刷屏。用 pr_warn_once! 只会在第一次出现时打印一次，后续不再重复。Miguel Ojeda 审阅了这个补丁。

宏、类型系统与核心 API 改进

Gary Guo 提交了一个补丁，让内核的 Rust 代码改用 strict provenance API。在 Rust 中，原始指针可以通过 as 在指针和整数之间自由转换，但这会丢失指针的"来源"信息（provenance）——即这个指针最初是从哪个分配中来的。Strict provenance API（如 ptr::with_addr、ptr::addr）保留了这个信息，让编译器和各种分析工具（如 Miri）能更好地检测指针错误。Tamir Duberstein 参与了审阅。这是一个提升代码安全性的改进，虽然功能上没有变化，但让代码更加"正确"。

📬 查看补丁

Gary Guo 和 Alexandre Courbot 还合作提交了两个内联优化补丁：一个是让 pin_init 宏生成的 #ident 和 #project_ident 方法始终内联（#[inline(always)]），另一个是让一些 init 方法也始终内联。这两个补丁是 Nova GPU 驱动导出符号系列（nova-exports v2）的一部分。为什么要强制内联？因为这些方法通常很小，内联后可以避免函数调用的开销，而且更重要的是，可以避免产生不必要的导出符号（exported symbol），保持内核模块的接口干净。

📬 查看补丁：pin_init 内联 📬 查看补丁：init 方法内联

Strict Provenance：Rust 中一种更严格的指针操作方式。普通的指针-整数转换会丢失"这个指针来自哪块内存"的信息，strict provenance API 保留了这个信息，帮助工具检测内存安全问题。 📖 了解 Strict Provenance
KUnit：Linux 内核的单元测试框架，让开发者可以像写应用程序测试一样为内核代码编写测试。 📖 了解 KUnit

️ 构建系统与工具链

️ 构建系统与工具链

Mark Brown 提交的补丁说明了 KASAN + Rust 需要使用 Clang 编译器，目前已迭代到第三版。KASAN（Kernel Address Sanitizer）是内核中的内存错误检测工具，能发现越界访问、释放后使用等 bug。当 Rust 和 KASAN 同时启用时，需要 Clang 编译器（而不是 GCC），因为 Rust 本身就基于 LLVM（Clang 的后端），两者配合更好。这个补丁更新了构建系统的依赖关系，确保配置时给出正确的提示。Miguel Ojeda 参与了审阅，共收到 5 条反馈。

📬 查看补丁

Nathan Chancellor 提交了一个 modpost 工具改进，用于检测和报告 buf_printf() 输出被截断的情况，已迭代到第二版。modpost 是内核构建过程中处理模块符号导出的工具。当生成的符号信息超过缓冲区大小时，之前会静默截断，可能导致构建出的模块缺少某些符号定义。这个补丁让 modpost 在截断发生时主动报告错误，避免开发者花大量时间排查"明明定义了符号为什么找不到"的问题。这个补丁是 Nova GPU 驱动导出符号系列（nova-exports v2）的基础工作之一。Alexandre Courbot 参与了审阅。

📬 查看补丁
💡 小白科普
KASAN（Kernel Address Sanitizer）：一种内核调试工具，能在运行时检测内存错误（如数组越界、访问已释放内存等）。启用后内核会变慢，但能帮你找到隐藏很深的 bug。类似于给代码装了一个"内存监控摄像头"。 📖 了解 KASAN
modpost：内核构建系统中的一个后处理工具，负责检查模块之间的符号依赖关系，确保模块导出和导入的符号都能正确匹配。 📖 了解内核模块构建
