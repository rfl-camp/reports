驱动核心框架

驱动核心子系统向 Linus 发起合并请求
Danilo Krummrich 今天向 Linus Torvalds 发送了驱动核心（driver core）子系统的 GIT PULL 请求，目标是合入 Linux 7.2-rc1。这次提交中最引人注目的部分是 Rust 原生的设备驱动生命周期管理系列补丁，它已经通过签名标签（signed tag）与 DRM 子系统树共享。所有提交都已在 linux-next 中经过了多轮测试。

这件事为什么重要？在 Linux 内核中，「驱动核心」是所有设备驱动的底层基础设施——它管理着设备的注册、注销、电源管理等。以前这些全部用 C 写成，现在 Rust 驱动可以用原生的方式管理设备的「生命周期」（也就是设备从创建到销毁的整个过程），不再需要笨拙地包装 C 代码。这相当于给 Rust 驱动开发者铺好了一条安全的高速公路。

Miguel Ojeda 提交了 rust: faux 模块的第 20 版补丁，新增了从 faux 设备获取已绑定设备引用的功能。faux 设备是一种「假设备」，主要用于内核测试——你可以把它理解为一个「模拟器」，让开发者在没有真实硬件的情况下测试驱动代码。这次改动让测试代码可以更方便地拿到设备对象进行操作，迭代到第 20 版说明社区对 API 设计非常谨慎。

同步机制：SRCU 抽象

SRCU Rust 抽象第 10 版（5 个补丁系列）
Onur Özkan 提交了 SRCU（Sleepable Read-Copy-Update，可睡眠的读-拷贝-更新）Rust 抽象的第 10 版补丁，整个系列包含 5 个补丁。这组补丁的直接动机来自 Tyr 驱动的重置基础设施——在 GPU 等硬件需要重置时，必须确保正在进行的硬件访问已经安全完成，否则就可能出现「你正在写数据，硬件突然重启」的灾难性场景。SRCU 正是解决这类「读写协调」问题的同步机制。

这个系列拆解成了 5 个清晰的步骤：

① 重构 C 端初始化函数：让 init_srcu_struct() 统一调用 __init_srcu_struct()，不再出现两个函数互相调用的混乱情况。这和 mutex 的初始化方式保持一致，让代码更清晰。

📬 补丁 1/5

② 添加 SRCU 辅助函数：在 rust/helpers/srcu.c 中新增了供 Rust 调用的 C 辅助函数包装。因为有些 C 函数是内联函数或宏，Rust 的 FFI（外部函数接口）无法直接调用，所以需要一层薄薄的 C 包装。

📬 补丁 2/5

③ 暴露 srcu_readers_active()：将这个函数从 kernel/rcu/srcutree.c 移动到头文件 include/linux/srcutree.h 中，使得 Rust 端可以通过辅助函数调用它。这个函数的作用是检查「是否还有读者在使用」，在清理资源前必须先确认没有人在读。

📬 补丁 3/5

RCU（Read-Copy-Update）：一种高效的同步机制，允许多个「读者」同时读取数据而不加锁，只在「写者」修改数据时才需要同步。SRCU 是它的「可睡眠版本」——普通 RCU 在读的时候不能睡眠（不能做慢操作），SRCU 放宽了这个限制。了解 RCU →

️ GPU 驱动（NOVA-CORE）

️ GPU 驱动（nova-core）

移除 #[allow(non_snake_case)] 属性
NVIDIA 工程师 Alexandre Courbot 提交了一个代码清理补丁，移除了 nova-core GPU 驱动模块中的 #[allow(non_snake_case)] 属性。这个属性的作用是让编译器「闭嘴」——不要抱怨代码里不符合 Rust 命名规范的变量名（Rust 规范要求用 snake_case，比如 my_variable，而不是 myVariable）。

移除这个属性意味着代码中之前不规范的命名已经被修正了，现在可以让编译器重新检查命名规范。这看起来是一个很小的改动，但对于一个正在积极开发的驱动来说，保持代码风格统一非常重要——它降低了新贡献者阅读和理解代码的门槛。nova-core 是 NVIDIA GPU 的开源内核驱动，用 Rust 编写，是 Rust-for-Linux 最受关注的项目之一。

修复文档测试中的错误模式匹配
Gary Guo 发现了 Rust 文档测试（doctest）处理代码中的一个 bug。内核的 doctest 框架需要对 rustdoc 生成的代码做一些文本替换，其中一个模式是 -> Result<(), impl core::fmt::Debug>。之前有人不小心在 core 前面加了 ::（写成了 ::core），导致模式匹配失败——就像你在搜索框里打错了关键词，当然什么都搜不到。这个补丁修正了搜索模式，同时保持替换结果中的 :: 不变。

📬 查看补丁

修复文档测试函数名的可重现性问题
Gary Guo 还修复了另一个问题：当使用 O= 参数指定独立的构建输出目录时，rustdoc 生成的测试函数名会包含构建路径，比如 _doctest_main__home_gary_Projects_linux_rust_kernel_io_rs_824_0。这不仅导致了超长的符号名，更关键的是，不同的开发者在不同的机器上构建，会得到不同的函数名，破坏了构建的可重现性。修复方法是裁剪掉路径部分，只保留文件名和行号。这对于「可重现构建」（reproducible builds）非常重要——它保证无论谁在哪里编译，产出的二进制文件都是完全一样的。

I/O 与设备配置

I/O 与设备配置

添加动态大小的 I/O Region 类型（20 个补丁系列）
Miguel Ojeda 提交的第 4 版补丁系列是今天最大规模的一组补丁，包含多达 20 个补丁。它为 Rust 内核代码引入了一个新的 Region 类型，用于表示动态大小的 I/O 内存区域。

打个比方：当内核想要和一个硬件设备「对话」时，通常通过一块特定的内存地址来读写数据，这块地址就是「I/O 内存区域」。以前的抽象只能处理编译时确定大小的区域，而新的 Region 类型支持运行时才确定大小的区域——因为很多设备的 I/O 区域大小要等到实际探测硬件后才知道。这个改动让 Rust 驱动可以更灵活地处理各种硬件。

📬 查看补丁

configfs 属性声明过程宏（第 3 版）
Miguel Ojeda 还提交了一个过程宏（procedural macro）补丁，用于声明 configfs 属性。configfs 是 Linux 内核中的一个文件系统，允许用户空间通过文件和目录的方式来配置内核对象。你可以把它想象成一个「控制面板」——用户在文件系统里创建目录、写入文件，就能配置内核里的某个功能。这个宏让 Rust 驱动开发者可以用简洁的语法声明 configfs 属性，不用手动编写大量模板代码。

bitfield 的 Debug 实现标记为 #[inline]
Alexandre Courbot 提交了一个小补丁，给 bitfield（位域）模块的 Debug trait 实现添加了 #[inline] 属性。当你想打印一个位域值来调试时，会调用 Debug 方法。加上 #[inline] 后，编译器会把这个函数的代码直接「嵌入」到调用处，避免函数调用的开销。这在内核中尤其重要，因为调试输出可能在性能敏感的路径上。这个补丁已经收到了 3 个 review，说明社区认为即使是这么小的改动也值得仔细审查。
