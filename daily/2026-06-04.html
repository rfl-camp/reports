类型系统重构：ForLt 生命周期特征拆分

① 重命名 ForLt 为 CovariantForLt

今天最重要的一组补丁来自 Danilo Krummrich，一共 7 个补丁，核心目标是重新设计内核 Rust 代码中处理生命周期的基础设施。这就像是给一栋大楼换地基——虽然普通用户看不到，但所有上层建筑都依赖它。

背景：在 Rust 里，"生命周期"（lifetime）用来保证引用不会指向已经被释放的内存。内核里有一个叫 ForLt 的特征（trait），让类型能够"携带"一个生命周期参数。但原来的设计要求所有使用它的类型都必须是"协变的"（covariant），这意味着可以安全地把长生命周期缩短为短生命周期。问题是，像 Mutex（互斥锁）这样的类型天生是"不变的"（invariant），不能安全地做这种缩短操作。

第一步是把现有的 ForLt 重命名为 CovariantForLt，名字更精确地表达了它的语义——这个特征要求类型是协变的。原来的功能完全不变，只是换了个更准确的名字，为后续的新特征腾出命名空间。由 Gary Guo 审阅通过。

📬 查看补丁
② 引入新的 ForLt 基础特征

新的 ForLt 特征是一个"基础版"，不要求类型是协变的。它提供了一个 unsafe 的 cast_ref_unchecked() 方法，只有在调用者能证明安全性时才能使用。而 CovariantForLt 继承自 ForLt，额外提供安全的 cast_ref() 方法。这样，像 Mutex 这样的不变类型也能参与生命周期泛型编程了，只是需要更谨慎地处理。

📬 查看补丁
③ auxiliary 总线：添加 registration_data_with() 闭包 API

为了配合新的 ForLt 特征，辅助设备总线（auxiliary bus）增加了一个新方法 registration_data_with()。它接受一个 for<'a> 闭包，闭包会收到 Pin<&'a F::Of<'a>> 类型的引用。关键在于：使用闭包而不是直接返回引用，可以防止调用者"自己选择"一个具体的生命周期，从而保证了非协变类型的安全性。这是一个很巧妙的 API 设计。

④ 示例：用不变的 Mutex 类型演示 ForLt

Danilo 还提供了一个示例代码，展示如何在辅助设备驱动中使用不变的 Mutex 类型配合新的 ForLt 特征。这对其他驱动开发者来说是很好的参考——你可以看到在实际代码中怎么安全地使用这套新机制。

⑤ DevresLt：生命周期感知的设备资源管理

️ GPU / DRM 驱动

️ GPU / DRM 驱动

DRM 驱动添加 RegistrationData 关联类型

Danilo Krummrich 为 DRM 驱动框架添加了 RegistrationData 关联类型。简单来说，当一个 DRM 驱动（比如显卡驱动）注册到系统时，它可能需要保存一些"注册时才有的数据"。以前这些数据的生命周期管理比较粗糙，现在通过 ForLt 类型系统，这些数据的生命周期被精确地绑定到了父总线设备的绑定范围。Registration<'a, T> 通过 Pin<KBox<_>> 获取数据的所有权，并在 drm_dev_register 之前将指针写入 drm::Device。这就像是给显卡驱动加了一个"生命周期保险箱"，确保数据不会在驱动还在使用时就被意外释放。Gary Guo 参与了审阅。

📬 查看补丁
DRM 添加 UnbindGuard 保护机制

这个补丁解决了一个重要的安全问题：当用户程序通过 ioctl（系统调用接口）操作 DRM 设备时，设备的父总线可能已经被解绑了（比如 USB 显卡被拔掉了）。新增的 UnbindGuard 是一个守卫对象，它封装了内核中的 drm_dev_enter() / drm_dev_exit() 临界区。只要你持有这个守卫，就可以保证父设备一定还在。因为 DRM 设备的注册通过 Devres 管理，使用 drm_dev_unplug() 进行反注册，所以在守卫的生命周期内，设备绑定状态是有保证的。这就像一个"安全门"——进去之前先确认设备还在。

📬 查看补丁
Nova 驱动：Bar0 生命周期优化

NVIDIA 的开源 GPU 驱动 nova-core 有了新进展。Eliot Courtney 提交的补丁将生命周期参数移到了 Bar0 结构体上。Bar0 是 GPU 的第一个 BAR（Base Address Register），也就是 CPU 访问 GPU 寄存器的"窗口"。这个改动让 Bar0 的生命周期管理更加清晰，代码更容易理解。Danilo Krummrich 和 Alexandre Courbot（来自 NVIDIA）都参与了审阅讨论。

内存管理：RCU 新类型

内存管理：RCU 新类型

新增 RcuBox 类型

Alice Ryhl 提交了 RcuBox 类型的补丁系列（共 4 个补丁），这是 Rust 内核生态中一个重要的新原语。RCU（Read-Copy-Update）是 Linux 内核中最常用的并发机制之一，特别适合"读多写少"的场景。想象一个电话簿：很多人同时在查号码（读），偶尔有人搬家需要更新号码（写）。RCU 的做法是：更新时不锁住电话簿，而是复制一份新的、改好的版本，然后在所有人都不再看旧版本时，才把旧版本回收。

RcuBox 将这种机制封装成了一个类型安全的 Rust API。这意味着 Rust 驱动开发者可以更安全地使用 RCU，编译器会帮你检查是否正确地遵守了 RCU 的使用规则（比如在 RCU 读取端临界区内才能访问数据）。目前已有 Boqun Feng 和 Philipp Stanner 等 5 人参与审阅，讨论相当活跃。

设备驱动

串口设备总线抽象 v12

Markus Probst 提交了串口设备总线（serdev）Rust 抽象的第 12 版（共 3 个补丁）。这个补丁已经迭代了 12 轮，可见社区对代码质量的要求之高。serdev 是内核中专门处理"挂在串口上的设备"的子系统——比如一些嵌入式设备通过串口（UART）连接到主机。这个抽象的第一个用户将是群晖（Synology）NAS 设备中 MCU（微控制器）的驱动。另外，开发者 Kari Argillander 也表示想用这个抽象来写一个看门狗（watchdog）驱动。一个抽象能服务多个驱动，说明它的设计具有通用性。

📬 查看补丁
块设备：为 Request 添加 command 访问器

Andreas Hindborg 为块设备层的 Rust 绑定中的 Request 类型添加了 command getter 方法。块设备请求（Request）是内核处理磁盘 I/O 的基本单位——每次你读写文件，内核都会创建请求发给磁盘驱动。这个补丁让 Rust 驱动能够读取请求的命令类型（比如是读、写还是其他操作）。这是一个较大补丁系列（79 个补丁）的一部分，Gary Guo 参与了审阅。

configfs 属性声明宏重写

Gary Guo 和 Malte Wechter 合作，用 syn 库将 configfs_attrs! 重写为过程宏（procedural macro）。configfs 是内核提供给用户空间的一种配置接口（就像一个虚拟文件系统，你可以通过创建目录和写文件来配置内核功能）。之前的声明式宏（declarative macro）虽然能工作，但代码可读性和可维护性较差。新版本使用了 syn 这个 Rust 社区标准的语法解析库，代码更清晰。同时旧宏被删除，所有使用处都切换到了新宏。

安全加固与健全性

安全加固与健全性

Binder：限制最大线程数并防止重复 looper 注册

Alice Ryhl 和 Yunseong Kim 提交了 4 个补丁来加固 Android Binder 驱动。Binder 是 Android 系统中进程间通信（IPC）的核心机制——每次你在 Android 手机上打开一个 App、调用系统服务，背后都是 Binder 在传递消息。这次的补丁做了两件事：一是给 max_threads 设置上限，防止恶意程序申请过多线程导致资源耗尽；二是拒绝重复的 looper 线程注册，避免同一个线程被多次注册导致的潜在问题。这些都是防御性编程的典型做法。

📬 查看补丁
删除 task_euid() 函数（v4）

Alice Ryhl 提交了第 4 版补丁（共 2 个），要删除 task_euid() 函数。这个函数用来获取进程的"有效用户 ID"（effective UID），在权限检查中经常用到。删除它的原因是社区认为直接使用底层的凭据（credential）结构体会更安全、更清晰。Paul Moore（安全子系统维护者）参与了审阅，这说明该改动涉及安全相关的代码路径。

安全加固与健全性

健全性问题：Binder ProcessInner 的 death_delivered

GeorgeAndrou 在 GitHub 上报告了一个健全性问题（soundness issue，Issue #1238）。问题出在 Binder 驱动的 ProcessInner::death_delivered 字段上：它没有正确地维护链表的所有权不变量。在 Rust 的类型系统中，如果一个字段声称拥有某些数据的所有权，但实际上没有正确维护这个约束，就可能导致未定义行为（undefined behavior）。这是一个被标记为 unsound（不健全）的严重 bug。

🐛 查看 Issue
workqueue 安全注释修复

zanni098 提交了一个 PR（#1235），修复了工作队列（workqueue）中 WorkItemPointer 对 Pin<KBox> 实现的安全注释（safety comments）。在内核 Rust 代码中，每个 unsafe 块都需要附带注释说明为什么这段代码是安全的。这个 PR 更新了这些注释使其更准确地反映实际的安全论证。

构建系统与工具链

rust-analyzer 宏配置修复（v3）

Tamir Duberstein 和 Malte Wechter 修复了一个影响开发体验的问题。rust-analyzer 是 Rust 开发者最常用的 IDE 插件，它能提供代码补全、错误提示等功能。但之前生成 rust-analyzer 配置时，传给 macros crate 的编译配置（cfg）跟实际编译时用的不一样。这导致 rust-analyzer 无法正确理解条件编译的代码——比如某段代码只在特定配置下才存在，rust-analyzer 却不知道这个配置是否启用。修复后，IDE 中的代码分析将更加准确。这是第 3 版补丁。

📬 查看补丁
kbuild：Rust 1.98 编译器标志重命名

Nathan Chancellor 提交了一个构建系统补丁：从 Rust 1.98 版本开始，编译器标志 -Zdebuginfo-for-profiling 的名字变了，需要在内核构建系统（kbuild）中同步更新。这是一个很典型的"跟进上游"的工作——Rust 编译器每 6 周发布一个新版本，内核需要及时适配这些变化。Alice Ryhl 参与了审阅。虽然改动很小，但如果不及时修复，使用新版 Rust 编译器编译内核时就会报错。

📬 查看补丁
klint 发布 Rust 1.96 版本

Gary Guo 在 Zulip 上宣布 klint 已经为 Rust 1.96 打了标签。klint 是一个专门为 Linux 内核 Rust 代码设计的静态分析工具（类似于 Rust 的 clippy，但检查的是内核特有的规则）。比如它可以检查你是否在不该睡眠的上下文中调用了可能睡眠的函数。跟进最新的 Rust 版本意味着使用新版编译器的开发者也能享受到这些额外的检查。
