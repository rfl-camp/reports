️ GPU / DRM 驱动

1. Tyr GPU 驱动：把探测资源搬进注册数据

今天 GPU 驱动方向动作不少，有好几个补丁都在改进 Rust 版 DRM（Direct Rendering Manager，直接渲染管理器）驱动框架的基础设施。

Deborah Brouwer（来自 Collabora）提交了一个补丁，改动的是 drm/tyr 驱动——这是一个用 Rust 编写的 GPU 驱动。补丁的核心思路是：把驱动在"探测"（probe）阶段获取的各种资源——包括父平台设备引用、时钟、稳压器、MMIO 映射（用来和硬件通信的内存映射）、固件状态和 GPU 信息——统一搬进一个叫 TyrDrmRegistrationData 的新结构体里。

为什么要这么做？因为这些资源必须在 DRM 设备注册期间一直存活。之前它们散落在不同地方，管理起来容易出错（比如某个资源被提前释放了）。现在把它们集中放到注册数据里，由 DRM 注册机制统一管理生命周期，代码更安全也更清晰。Danilo Krummrich 已经在 review 这个补丁。

2. DRM 框架：给 drm::Driver 添加 RegistrationData（v2，7 个补丁）

同样是 Deborah Brouwer 提交的系列补丁，共 7 个。这个系列是上面 Tyr 驱动改动的"上游基础设施"——它在 Rust 版 DRM 框架层面添加了一个通用的 RegistrationData 关联类型，这样所有用 Rust 写的 DRM 驱动都可以把需要在注册期间存活的资源放进这个结构里。这是一个框架级别的改进，不只是 Tyr 一个驱动受益，未来所有 Rust DRM 驱动都能用上。目前已经迭代到 v2 版本，Danilo Krummrich 在 review。

3. DMA Fence 抽象封装（4 个补丁）

Boris Brezillon 提交了一组 4 个补丁，为内核中的 dma_fence 机制添加 Rust 安全抽象。dma_fence 是 GPU 驱动中极其重要的同步原语——当 GPU 在执行一个任务（比如渲染一帧画面）时，CPU 需要知道"GPU 什么时候干完了"。dma_fence 就是这个"完成信号"，就像你点了外卖后收到的"已送达"通知。

有了 Rust 版的 dma_fence 抽象，Rust GPU 驱动就可以安全地使用这个同步机制，不用直接调用不安全的 C 接口。Daniel Almeida 正在 review 这组补丁。这是让 Rust GPU 驱动走向成熟的关键一步。

同步原语与锁机制

同步原语与锁机制

1. GlobalGuard 和 GlobalLock::try_lock 加上 #[must_use]（已合入！）

内核是高度并发的系统——多个 CPU 核心同时运行，随时可能同时访问同一份数据。为了防止数据被搞乱，内核需要各种"锁"和同步工具。今天这方面有好几个进展。

Boqun Feng 提交、Ashutosh Desai 编写的补丁已经合入 rust-next 分支（commit 03e85788）。这个补丁给 GlobalGuard 和 GlobalLock::try_lock 加上了 #[must_use] 标注。

什么意思呢？在 Rust 里，"锁守卫"（Guard）的作用是：当你拿到一把锁后，Guard 对象代表"你正持有这把锁"。当 Guard 被丢弃（drop）时，锁自动释放。问题在于：如果你拿到了 Guard 但没有存到变量里（比如写成了 lock.try_lock(); 而不是 let _guard = lock.try_lock();），锁会立刻被释放，你以为自己锁住了，其实没有！#[must_use] 标注让编译器在这种情况下给出警告，帮你发现这类隐蔽的 bug。Miguel Ojeda 参与了 review。

2. SetOnce::reset() 补丁系列（v17，6 个补丁）

Lyude Paul 提交、Alice Ryhl review 的系列补丁，给 SetOnce 类型添加了 reset() 方法。SetOnce 是一种"只能设置一次"的容器——你把值放进去之后就不能改了。但有些场景下（比如驱动卸载后重新加载），你确实需要重置它。这个 reset() 方法就是为这种场景准备的。

这个系列已经到了 v17 版本，说明关于"何时允许重置、如何保证线程安全"这些问题经过了大量讨论和反复修改。每一次迭代都在完善安全保证。

⏰ 时钟与 PWM 驱动

1. ExclusiveClk 封装与 pwm-th1520 驱动

Maurice Hieronymus 提交了两个补丁，为 Rust 时钟（clk）子系统添加 ExclusiveClk 封装。在嵌入式系统中，时钟信号就像心跳——硬件的每一步操作都需要时钟来驱动。有时候一个时钟会被多个设备共享，但某些设备需要"独占"一个时钟，不允许别人改变它的频率。ExclusiveClk 就是把 C 内核的 clk_rate_exclusive_get 接口封装成安全的 Rust API，表示"我独占这个时钟的频率"。

这个封装被直接用到了 pwm-th1520 驱动中。TH1520 是阿里平头哥出的一款 RISC-V 芯片，这个 PWM 驱动控制芯片上的脉冲宽度调制功能（常用于控制 LED 亮度、电机转速等）。Alice Ryhl 对这两个补丁做了 review，并分别发表了反馈意见。

设备模拟与测试（faux 设备框架）

faux::Registration 支持获取已绑定设备上下文（v18，4 个补丁）

Lyude Paul（来自 Red Hat）在编写使用 faux 设备进行单元测试的 Rust 代码时发现了一个问题：faux::Registration 的 AsRef<device::Device> 实现里，没有加入 Bound（已绑定）设备上下文。

BINDER 驱动 BUG 修复

Binder 驱动 Bug 修复

rust_binder: 修复 BINDER_GET_EXTENDED_ERROR（v2）

Alice Ryhl（来自 Google）发现了 Rust 版 Binder 驱动中一个实实在在的 bug 并提交了修复。Binder 是 Android 系统中进程间通信（IPC）的核心机制——你手机上的 App 能互相发消息、调用系统服务，背后靠的就是 Binder。

这个 bug 是怎么回事呢？代码在处理 BINDER_GET_EXTENDED_ERROR 这个 ioctl 命令时，把 ExtendedError 结构体复制到了栈上的一个副本，然后修改了这个副本——但忘了把修改写回原来的地方。这就像你复印了一份文件，在复印件上改了内容，然后把原件给了别人——别人看到的还是没改过的版本！

除了修复这个 bug，Alice 还改进了 deliver_reply() 函数，让它接受一个 extended error 参数，因为"回复时产生的错误必须直接传递给远端线程"。

内核覆盖率工具 KCOV：数据流追踪新功能（热烈讨论中！）

内核覆盖率工具 kcov：数据流追踪新功能（热烈讨论中！）

这组补丁想做什么？

今天最热闹的讨论之一来自 kcov 的数据流追踪 RFC 补丁系列。这是由 Yunseong Kim 提交的 v2 版本（共 6 个补丁），引发了内核调度和性能领域大佬 Peter Zijlstra 和编译器专家 Nathan Chancellor 的密集反馈。

kcov 是内核的代码覆盖率工具，通常用于模糊测试（fuzzing）——让测试工具知道"我的测试输入跑到了内核的哪些代码路径"。这组新补丁想给 kcov 加一个新能力：数据流追踪。不只是记录"跑过了哪些代码行"，还要记录"内核函数被调用时参数是什么值、返回了什么值"。这对发现安全漏洞特别有用——如果你能知道某个安全检查函数收到了什么参数、返回了什么，就能更精准地构造测试输入。

补丁 1/6（per-task 数据流追踪）：Peter Zijlstra 关注了按任务（per-task）追踪函数参数和返回值的设计方案，提出了关于性能开销和安全性的反馈。

补丁 2/6（构建系统支持）：Nathan Chancellor 和 Peter Zijlstra 讨论了如何在内核构建系统中集成数据流检测的编译选项。这涉及到给编译器加特殊的 instrumentation flag。

补丁 3/6（CONFIG 选项）：添加 CONFIG_KCOV_DATAFLOW_INSTRUMENT_ALL 和 NO_INLINE 配置项。Peter 对是否应该全局启用 instrumentation 和禁止内联优化提出了疑虑——全局启用会严重影响内核性能。

补丁 5/6（中断上下文保护）：给 kcov_df_write() 加了中断上下文守卫。因为 kcov 是 per-task 的，在中断处理中调用可能会破坏数据，需要特别保护。

补丁 6/6（递归保护和文档）：添加递归守卫，防止 kcov 的 instrumentation 代码追踪自己，形成无限循环。Peter 对文档和实现细节给出了进一步建议。

⚙️ 工作队列（WORKQUEUE）

⚙️ 工作队列（Workqueue）

1. 工作队列与生命周期绑定（Zulip 深度讨论，24 条消息）

这是今天 Zulip 上最活跃的讨论之一！Alice Ryhl 发起了一个关于"如何把工作队列和新的生命周期模型结合起来"的讨论，Benno Lossin、Gary Guo、Onur Özkan 和 Danilo Krummrich 都参与了。

背景是这样的：在内核驱动中，"工作队列"（Workqueue）是一种把任务延迟执行的机制——比如"我现在处于中断处理中，不能做复杂的事情，先把这个活丢进工作队列，等会儿再做"。问题在于：如果工作队列引用了设备的私有数据，而设备被拔掉了，工作队列的任务还在引用已经不存在的数据——这就是经典的"使用已释放内存"（use-after-free）问题。

Alice 给出了一个 GPU 驱动私有数据的例子，展示了如何用 Rust 的生命周期系统来保证"工作队列中的任务引用的数据一定还活着"。Benno Lossin 注意到这涉及到自引用结构（self-referential struct）的问题，并讨论了 &'a Self -> &'foo Foo 这种引用转换是否应该总是被允许。这个讨论还在进行中，可能会影响 Rust 驱动框架的基础设计。
