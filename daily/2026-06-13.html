GEM SHMEM Rust 绑定 v21 — 四补丁系列

Lyude Paul（Red Hat 的图形栈开发者）发出了 GEM SHMEM 绑定第 21 版补丁集。GEM（Graphics Execution Manager）是 Linux 内核管理 GPU 显存的框架，而 SHMEM 是其中一种基于共享内存的后端——简单说就是"让 GPU 和 CPU 共享一块内存来交换图形数据"。这套补丁为这个 C 语言接口提供了安全的 Rust 封装，这样未来像 Nova（开源 NVIDIA 驱动）和 Asahi（Apple Silicon GPU 驱动）这样的 Rust GPU 驱动就能直接使用类型安全的接口来管理显存了。经过 21 轮迭代，这套 API 的设计已经非常成熟，补丁集里还包含了一个 DmaResvGuard 辅助工具和 faux 设备测试支持。

📬 查看补丁集
DmaResvGuard 辅助工具

上面补丁集中的第二个补丁引入了 DmaResvGuard（DMA 预留锁的 RAII 守卫）。在 GPU 驱动中，多个组件（CPU 端的应用程序、GPU 硬件、视频解码器等）经常需要同时访问同一块显存缓冲区，dma_resv 锁就是用来协调这些访问的。这个 Guard 封装让上锁/解锁变得更容易——获取守卫时自动加锁，守卫离开作用域时自动解锁，避免忘记解锁导致的死锁问题。Gary Guo 已经给出了审查意见。Lyude 说这是一个"临时方案"，后续会被更完善的设计取代。

📬 查看补丁
Zulip 讨论：VMap 的 Sync 实现与数据竞争

在 Zulip 的 #DRM 频道，Lyude 提出了一个值得关注的问题：当前 VMap（将内核虚拟地址映射到物理内存页面的机制）的 Sync trait 实现，配合 IoCapable trait，允许多个线程同时对同一块内存做 volatile 写入——这在 Rust 的内存模型里属于数据竞争（data race），是未定义行为（UB）。Gary Guo 回应说，虽然这在 Rust 层面确实算 UB，但在 Linux 内核内存模型（LKMM）下是合法的，可以暂时忽略。他还提到这部分代码后续会被 SysMem（I/O 投影系列补丁）替代。这个讨论反映了 Rust 严格的安全保证与内核现有实践之间的张力——内核允许的一些操作在 Rust 看来是"不安全"的，社区正在逐步找到平衡点。

vmap 函数讨论（v20 遗留）

在邮件列表上，针对 v20 版本中 GEM SHMEM 的 vmap（虚拟内存映射）函数的讨论仍在继续。Lyude 回复了来自 Linaro 内存管理特别兴趣小组（mm-sig）的反馈。vmap 允许驱动程序在内核空间"看到"并访问 GPU 显存中的数据，比如在调试时读取帧缓冲区的内容。这些跨社区的讨论有助于确保 Rust 的 API 设计与内核现有的内存管理子系统保持一致。

Nova Core：移除 #[allow(non_snake_case)]

Gary Guo 提交了一个"清理型"补丁：在 nova-core（开源 NVIDIA GPU 驱动的核心模块）中移除了 #[allow(non_snake_case)] 注解。背景是之前 pin_init! 宏内部会生成一些不符合 Rust 命名规范（蛇形命名）的标识符，触发编译器警告，所以需要手动压制这个警告。但上游已经在 pin-init 宏内部修复了这个问题（commit 5423ef9d4db8），所以现在 nova-core 可以安全地删掉这个压制注解了。Danilo Krummrich 和 Onur Özkan 参与了审查。这虽然是一个小改动，但体现了 Rust 内核代码的持续清理和代码质量提升。

内核覆盖率工具 (kcov) — 数据流追踪

RFC v2 系列：per-task 数据流追踪

Yunseong Kim 提交了一套 RFC（征求意见稿）补丁系列的第二版，目标是为 kcov（内核覆盖率工具）增加按任务的数据流追踪功能。kcov 是一个帮助测试内核代码的工具——它能告诉你"内核执行了哪些代码路径"。现在这个系列要在此基础上更进一步：不仅记录"走了哪条路"，还记录"带了什么数据"——具体来说是记录函数的参数和返回值。这对于模糊测试（fuzzing）非常有价值，因为 fuzzer 需要知道输入数据如何"流过"内核内部的函数调用链，从而更聪明地生成测试用例。Peter Zijlstra（知名内核开发者，主要负责调度器和锁机制）也参与了讨论。

📬 查看补丁系列总览
补丁 01/14：添加 per-task 数据流追踪的核心实现

这是系列的第一个实质性补丁，由 Yunseong Kim 编写，Alexander Potapenko 和 Julian Braha 参与了审查。它在 kcov 中增加了基础的数据流记录结构——每个内核"任务"（可以理解为一个线程或进程）都有自己的数据流缓冲区，记录它调用的函数参数和返回值。这样做的好处是避免不同任务的数据互相干扰，每个任务的追踪数据都是独立、干净的。审查者对代码给出了详细反馈。

📬 查看补丁 📬 查看 v2 1/6 讨论
补丁 02/14：修复 INIT_TRACK 竞态条件

Alexander Potapenko 和 Yunseong Kim 发现了一个竞态条件（race condition）：在初始化数据流追踪（INIT_TRACK）时，如果两个线程几乎同时尝试初始化同一个追踪结构，可能会导致数据损坏或崩溃。这个补丁修复了这个并发问题。竞态条件就好比两个人同时想往同一个杯子里倒水——如果没有协调，水就会溅出来。这个 bug 在审查中被发现并修复，收到了 4 条审查意见，讨论非常活跃。

内核覆盖率工具 (kcov) — 数据流追踪

补丁 03/14：为递归守卫添加内存屏障

这个补丁为 kcov_df_write 函数中的递归守卫（recursion guard）添加了内存屏障（barrier）。递归守卫是为了防止 kcov 自身在追踪过程中进入无限循环——想象你用一面镜子拍另一面镜子，会产生无穷反射。但这个守卫在多核 CPU 上需要内存屏障来保证所有 CPU 核心都能"看到"守卫状态的变化，否则某个核心可能以为守卫没有启用，从而重新进入被保护的代码。Alexander Potapenko 提出了审查意见。

📬 查看补丁
补丁 04/14：拒绝同时在多个 dataflow fd 上启用追踪

这个补丁增加了一个安全检查：如果一个任务已经在一个数据流文件描述符（fd）上启用了追踪，再尝试在另一个 fd 上启用时会被拒绝。这防止了同一任务的数据流被写入多个缓冲区造成混乱。Alexander Potapenko 对此提出了 1 条审查意见。这类边界情况的处理体现了内核代码对健壮性的高要求。

BINDER 驱动（ANDROID 进程间通信）

Binder 驱动（Android 进程间通信）

在 process cleanup 时保留 NodeDeath 在 NodeRefInfo 中

Matthew Maurer 提交了第二版补丁，修改了 rust_binder（用 Rust 重写的 Android Binder 驱动）中进程清理逻辑。Binder 是 Android 系统的"邮局"——所有 App 之间的通信都要经过它。当一个进程退出时，需要清理它持有的所有 Binder 引用。之前的实现在清理时会过早地丢弃 NodeDeath（节点死亡通知）信息，这个补丁让它在 NodeRefInfo 中保留更久，确保清理流程的正确性。审查者已经给出了反馈。

📬 查看补丁
避免 insert_or_update_handle() 中的析构函数调用

同样来自 Matthew Maurer 的第二版补丁。insert_or_update_handle() 是 Binder 中管理句柄（handle，可以理解为其他进程的"地址"）的函数。之前的实现在某些路径上会触发 Rust 的析构函数（drop），而在内核中，析构函数的调用时机和副作用需要非常小心——特别是在持有锁的时候调用析构函数可能导致死锁。这个补丁重构了代码，避免了不必要的析构函数调用，让代码更安全、更可预测。

📬 查看补丁
将 Process::node_refs 迁移到 SpinLock

Matthew Maurer 的第三个 v2 补丁，将 Process::node_refs（进程的节点引用表）的锁从之前的类型切换为 SpinLock（自旋锁）。自旋锁是一种非常轻量级的锁——当锁被占用时，等待的线程不会"睡觉"，而是原地"转圈"等待，适合锁持有时间极短的场景。这个改动可能是为了满足特定的上下文要求（比如在不允许睡眠的中断处理路径中使用），或者是为了与内核其他部分的锁策略保持一致。

Rust 内核基础设施

zerocopy 支持 v2 — 19 个补丁的大型系列

Greg Kroah-Hartman（Linux 内核稳定版维护者，也是 Rust-for-Linux 的重要支持者）发出了 zerocopy 库支持的第二版补丁集，包含 19 个补丁。zerocopy 是一个 Rust 库，允许在不进行内存拷贝的情况下，安全地将原始字节重新解释为结构化数据类型——就像你收到一封信，不用把内容抄一遍，直接按照格式去读就行。这在内核中非常重要，因为内核经常需要解析来自硬件或用户空间的原始数据（比如网络包头、USB 描述符），避免拷贝可以显著提升性能。这个系列补丁将 zerocopy 集成到内核的 Rust 工具链中，已收到 2 条审查意见。

📬 查看补丁集
工作队列：添加 cancel_sync 支持 v2

Onur Özkan 提交了第二版补丁，为内核的工作队列（workqueue） Rust 绑定添加了 cancel_sync（同步取消）支持。工作队列是内核中"稍后再做"的机制——当你需要推迟某个任务到合适的时机执行时，就把它放进工作队列。但有时候你又需要"取消"一个已经排队但还没执行的任务，而且要确保取消完成后才继续往下走（同步取消）。v2 相比 v1 引入了一个新的 SupportsCancelling trait，将 from_raw_work 函数从 WorkItemPointer 中分离出来，设计更加清晰。补丁修改了 rust/kernel/workqueue.rs，增加了约 116 行代码。

📬 查看补丁
faux 设备：允许获取 Bound 状态的 Device

Lyude Paul 发现 faux（虚拟/伪设备框架）的 Registration 结构没有实现获取"已绑定"状态设备引用的功能。在 Linux 设备模型中，一个设备从注册到和驱动绑定有多个阶段。Lyude 在编写使用 faux 设备做单元测试的 Rust 代码时，需要获取一个已绑定设备的引用，但发现 API 不支持。这个补丁（v21 系列的一部分）添加了这个缺失的实现——因为 Registration 对象本身的存在就证明了驱动已经绑定到设备上了。Gary Guo 和 Danilo Krummrich 参与了审查。

bitfield 的 Debug 实现标记为 inline

Alexandre Courbot 提交了一个小但实用的优化补丁：将 bitfield（位域）类型的 Debug trait 实现标记为 #[inline]。位域是内核中非常常见的数据结构——硬件寄存器经常用一个整数的不同位来表示不同的含义（比如第 0 位是"启用"，第 1-3 位是"模式"等）。Debug trait 让你可以用 {:?} 格式化打印这个值来调试。标记 #[inline] 告诉编译器：这个函数很小，请直接把代码"嵌入"到调用处，不要做一次函数调用——这能减少函数调用的开销。Alice Ryhl 参与了审查。

📬 查看补丁
configfs 属性的过程宏 v3

Malte Wechter 提交了第三版补丁，为内核的 configfs（配置文件系统）添加了一个 Rust 过程宏（procedural macro），用于声明 configfs 属性。configfs 是一种让用户通过文件系统接口来配置内核对象的机制——你可以通过创建目录和写入文件来配置内核功能，而不需要专门的命令行工具。这个过程宏简化了在 Rust 中定义这些可配置属性的样板代码，让驱动开发者可以用更少的代码暴露配置接口。

讨论：doctest 源码映射脚本

Gary Guo 提出了一个 RFC（征求意见稿），为 Rust 内核的 doctest（文档测试）添加源码映射脚本。Rust 有一个很棒的特性：你可以在文档注释中写代码示例，编译器会自动编译并测试它们。但在内核环境中，doctest 被提取出来后，错误信息中的行号和原始源文件对不上了，调试非常困难。这个脚本会生成一个映射表，当 doctest 编译出错时，能自动告诉你"这个错误实际上对应源文件 xxx.rs 的第 yy 行"，大大提升了开发体验。
