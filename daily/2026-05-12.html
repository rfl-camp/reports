设备驱动框架：高阶生命周期类型大改造

今天最重磅的内容来自内核 Rust 驱动框架的核心维护者 Danilo Krummrich。他提交了一个包含 25 个补丁的系列，为设备驱动框架引入了 Higher-Ranked Lifetime Types（高阶生命周期类型）。

这是什么意思呢？简单来说，当你在 Rust 中写一个设备驱动时，驱动需要从内核那里"借用"一些数据（比如设备信息）。之前的框架中，这些借用关系的生命周期管理不够灵活——就像你借了别人的书，但规定只能在教室里看，不能带回宿舍。现在通过 ForLt 这个特性，驱动可以更灵活地表达"我需要在某个范围内安全使用这些数据"，同时编译器依然能在编译时帮你检查所有安全性。

这个系列具体包含三个大方向：

📬 查看完整系列 📬 Adapter trait 补丁 📬 drvdata 泛化补丁

辅助设备（Auxiliary Device）框架改进 — Danilo 同时提交了两组补丁，改进 Rust 的辅助设备支持。第一组为辅助设备添加了"注册数据"（registration data），让设备在注册到内核时可以携带额外的配置信息。第二组补丁则用这个新的注册数据机制替换了原来的 drvdata() 方法，使得 API 更加清晰一致。辅助设备是一种让一个物理设备暴露多个逻辑功能的机制——比如一块网卡既可以做网络通信，又可以做 RDMA，每个功能就是一个辅助设备。

📬 注册数据补丁 📬 替换 drvdata 补丁

串口设备总线抽象 v7 — Markus Probst 提交了第 7 版的串口（serial）设备总线 Rust 抽象，包含 4 个补丁。串口是最基础的通信接口之一（你可能在嵌入式开发或调试时见过它），这组补丁为内核中的串口设备提供了 Rust 语言的安全封装。经过多轮审查迭代到 v7，说明社区对这个抽象的 API 设计非常认真。

内存管理与数据结构

内存管理与数据结构

Maple Tree 实现 Send 和 Sync（v3） — Joel Fernandes（来自 NVIDIA）提交了第 3 版补丁，为 Rust 版的 MapleTree 实现 Send 和 Sync 这两个 trait。

问题的背景是这样的：C 语言写的 maple_tree 结构体内部包含一个 *mut c_void（一个原始指针），而 Rust 的安全规则会自动判断"包含原始指针的类型不能安全地跨线程传递"。但实际上，maple tree 在 C 内核中一直是可以安全跨线程使用的（因为有锁保护）。这个问题会沿着调用链向上传播——从 MapleTree 影响到 MapleTreeAlloc，再到 Vmm、BarUser、Gpu，最终导致 nova-core（NVIDIA 的新 GPU 驱动）的 NovaCore 结构体无法满足 Send 要求，整个驱动编译不过。这个补丁通过手动标记这些 trait 来解决问题。

📬 查看补丁

Binder 驱动使用 lock_vma_under_rcu() — Lorenzo Stoakes 提交了一个针对 Rust 版 Android Binder 驱动的补丁。Binder 是 Android 系统中进程间通信（IPC）的核心机制——每当你的 App 调用系统服务时，底层就是通过 Binder 在传递消息。

这个补丁改进了 Binder 的 shrinker（内存回收器）部分，让它使用 lock_vma_under_rcu() 而不是之前的锁定方式来访问 VMA（虚拟内存区域）。RCU 是一种高效的并发读取机制，使用它意味着在内存压力大需要回收内存时，读取操作不需要获取重量级的锁，性能更好。

📬 查看补丁

alloc 模块代码风格清理 — Danilo Krummrich 还提交了 2 个小补丁，清理 Rust alloc（内存分配）模块的 import 语句风格。具体是把 import 语句改成 "kernel vertical" 风格——也就是每个 import 单独一行，按模块垂直排列。这种看似小事的风格统一对大型项目的可维护性很重要，同时也对 doctest（文档测试）中的 import 做了同样的清理。

构建系统与开发工具

构建系统与开发工具

ARM 架构：KASAN 启用时禁用 Rust 支持 — Nathan Chancellor 提交了一个修复补丁，解决了在 32 位 ARM 架构上同时开启 KASAN 和 Rust 时编译失败的问题。

KASAN（Kernel Address Sanitizer）是内核中一个强大的内存错误检测工具——它能在运行时帮你发现越界访问、释放后使用等 Bug。但问题是，Rust 编译器（rustc）目前在 arm-unknown-linux-gnueabi 这个目标平台上还不支持 KASAN。当使用 allmodconfig（编译所有模块的配置）时，KASAN 和 Rust 都会被开启，结果 Rust 编译就报错了。这个补丁的解决方案很直接：当 KASAN 被启用时，不再选择 HAVE_RUST，从而避免冲突。已有多位审查者给出了 review 意见。

📬 查看补丁

kbuild：使用单一可执行文件作为 rustc 链接器（v8） — 同样来自 Nathan Chancellor，这个补丁改进了内核构建系统中 Rust 编译器的链接器配置。之前通过 -C linker 选项传给 rustc 的可能是多个不同的链接器调用，现在改为使用单一可执行文件，简化了构建过程。Nicolas Schier 参与了审查。这个补丁已经迭代到 v8，说明构建系统的细节调优也需要反复打磨。

📬 查看补丁

rust-analyzer 改进：传递 cfg 给宏 crate — Andreas Hindborg 提交了一个补丁，修改 generate_rust_analyzer 脚本，使其能正确地将 cfg（条件编译配置）传递给宏 crate。在内核开发中，不同的编译配置会启用或禁用不同的代码路径，如果 rust-analyzer 不知道这些配置，它就无法正确分析宏展开后的代码，导致 IDE 里出现一堆虚假的错误提示。Tamir Duberstein 参与了审查。

同步原语与并发控制

同步原语与并发控制

SRCU 抽象（v2） — Onur Özkan 提交了 3 个补丁，为 Rust 添加 SRCU（Sleepable Read-Copy-Update）的内核抽象。

RCU 是 Linux 内核中一种非常重要的同步机制，它允许读取者不用加锁就能安全读取数据，只有写入者需要等待。这使得读操作几乎没有性能开销，非常适合"读多写少"的场景。SRCU 是 RCU 的一个变体，特别之处在于它允许读取者在临界区中"睡眠"（即让出 CPU 等待）。普通的 RCU 不允许这样做，因为它需要所有读取者尽快完成。有了这个 Rust 抽象，内核开发者就可以用 Rust 的安全方式来使用 SRCU 了。

📬 查看补丁

Zulip 讨论：Spinlock 与中断的交互 — 在 Zulip 的 General 频道，Dirk Behme、Boqun Feng 和 Boris Brezillon 讨论了自旋锁（spinlock）与中断禁用的 Rust 封装问题。

具体来说，讨论围绕一组补丁中的 #ifdef PREEMPTION 应该改为 #ifdef CONFIG_PREEMPTION 的问题展开。这看起来只是个小小的宏名拼写差异，但在内核中这很关键：CONFIG_PREEMPTION 是 Kconfig 定义的标准配置选项名，如果写错了，条件编译就会走错分支，可能导致在抢占式内核上用了非抢占的代码路径，引发死锁或性能问题。Boris 还提到 fence callback（围栏回调，GPU 同步中的概念）的用户并不多，主要集中在 drm_sched 和各种容器类型中。

️ 内核基础设施与宏

️ 内核基础设施与宏

提取 bitfield! 宏（v3） — Gary Guo 提交了 5 个补丁，将 bitfield! 宏从 register! 宏中独立出来。

在硬件编程中，一个寄存器（register）通常由多个位域（bit field）组成——比如一个 32 位的控制寄存器，其中第 0-3 位表示模式，第 4 位表示启用/禁用，第 5-7 位表示速度等。之前 bitfield! 和 register! 是耦合在一起的。现在把 bitfield! 独立出来，意味着你可以在不涉及寄存器操作的场景中也使用位域定义——比如解析网络协议包头、操作文件系统元数据等。这让代码复用性更好。

📬 查看补丁

为 Delta 类型实现 Display — Andreas Hindborg 为 rust::time::Delta 类型实现了 Display trait。Delta 表示两个时间点之间的差值，实现 Display 后就可以直接用 println! 或内核的 pr_info! 等宏来格式化输出时间差了——比如打印 "操作耗时 15ms"。Gary Guo 给出了审查意见。虽然改动不大，但这种"让类型可打印"的改进对调试和日志记录非常实用。

📬 查看补丁
💡 小白科普
位域（Bit Field）：将一个整数的各个二进制位分成不同的"字段"，每个字段代表不同含义。就像一面旗帜上不同颜色的条纹各代表不同意义。硬件寄存器大量使用这种方式。📖 学习更多
Display trait：Rust 中定义类型如何被格式化为人类可读字符串的标准方式。实现它之后就可以用 {} 格式化打印该类型。📖 学习更多

RFC v2: 添加 kconfirm 工具 — Julian Braha 提出了一个名为 kconfirm 的新工具提案（RFC，即征求意见稿），目前是第 2 版，包含 2 个补丁。

这个提案引发了社区的热烈讨论。Jan Engelhardt 和 Demi Marie Obenour 在总体讨论中提出了各自的看法，而 Jani Nikula（Intel）则对具体实现（第 1 个补丁的脚本部分）给出了审查意见。从讨论的活跃度来看（3 位审查者参与了总体讨论，2 位参与了具体补丁审查），社区对是否接受这个工具还在评估中。作为 RFC，它的主要目的是收集反馈、讨论方向，而不是立即合入。
