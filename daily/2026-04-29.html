️ GPU / DRM 驱动

Tyr 驱动：固件加载与 MCU 启动支持（v4，共 20 个补丁）

Tyr 是一个正在开发中的、完全用 Rust 编写的 ARM Mali GPU 驱动程序。今天发出的第四版补丁系列实现了 固件加载（firmware loading）和 MCU（微控制器单元）启动支持。简单来说，GPU 内部有一个小型处理器（MCU），需要先把特定的固件程序加载进去、然后启动它，GPU 才能正常工作——就像你的手机开机时需要先加载基带固件才能打电话一样。这个补丁系列还处于活跃评审中，Alice Ryhl 和 Deborah Brouwer 在参与讨论。这是 Tyr 驱动走向功能完备的关键一步。

Tyr 驱动：Kconfig 依赖配置（v4，共 20 个补丁）

同样是 Tyr 驱动系列的一部分。这个补丁确保在内核编译配置（Kconfig）中，Tyr 驱动会自动选择（select）它所依赖的其他内核模块。如果你没做过内核编译可能不太熟悉：Linux 内核是模块化的，编译前需要用配置菜单选择要编译哪些功能。这个补丁就是把 Tyr 驱动"需要哪些前置模块"写清楚，这样用户只要勾选 Tyr，依赖就自动打开了，不需要手动一个个找。Boris Brezillon 和 Deborah Brouwer 参与了这一讨论。

️ GPU / DRM 驱动

DRM 设备初始化：修复 unsound（不安全）问题

Gary Guo（Rust-for-Linux 核心贡献者）发现了 drm::Device::new 中的一个 soundness bug（内存安全隐患）。问题出在哪呢？当你创建一个 DRM 设备对象时，如果内部数据（data 字段）初始化失败了，原来的代码会调用 drm_dev_put 来清理，但这个清理过程中会创建一个对还没完全构造好的设备对象的引用——这在 Rust 的安全模型里是不允许的，因为引用了未完整初始化的内存。修复方案是：如果初始化失败，只释放底层的 C 语言分配的结构体，而不走正常的"引用释放"流程，从而避免碰到那个未初始化的字段。这是一个很好的例子，说明 Rust 的安全检查机制确实能发现 C 代码中不容易注意到的问题。

Zulip 讨论：Rust TTM 绑定 / API 设计

Eliot Courtney 在 Zulip 的 DRM 频道分享了他正在做的 TTM（Translation Table Manager）绑定的早期进展。TTM 是 Linux DRM 子系统中负责管理 GPU 显存的组件——你可以把它想象成"GPU 的内存管理员"，负责决定哪些数据放在显存里、哪些可以挪到系统内存里。Eliot 说他参考了现有的 GEM（Graphics Execution Manager）绑定的设计模式来推进工作，并且希望尽早征求社区意见以确保方向正确。这项工作对 Nova 等驱动的未来发展至关重要。

I/O 子系统（硬件寄存器访问）

I/O 子系统（硬件寄存器访问）

限制非类型化 I/O 访问，仅允许 Region 使用（v2，共 11 个补丁）

这个补丁系列由 Danilo Krummrich 主导，核心思想是：收紧对硬件 I/O 寄存器的访问权限。在设备驱动中，要和硬件"对话"就需要读写特定的内存地址（叫做 I/O 区域）。以前的 Rust 抽象允许比较自由的"无类型"（untyped）访问，就好比你可以直接往任意地址写数据。新的设计要求所有 I/O 访问都必须通过明确声明的 Region（区域）来进行，这样编译器就能帮你检查"你访问的地址确实属于你申请过的那块硬件区域"。Andreas Hindborg 和 Gary Guo 参与了评审，讨论了类型安全和 API 易用性的平衡。

📬 查看补丁
I/O 视图类型（view type）（v2，共 11 个补丁）

同一系列的一部分。这个补丁引入了一个新的"视图"（view）类型，让驱动可以获得一个 I/O 区域的"只读视图"或"部分视图"。打个比方，原来你拿到一块硬件区域就是整块拿走，现在你可以只"借用"其中一小段来操作，而且这个借用关系是编译时检查的。这样做的好处是多个驱动子模块可以安全地共享同一块 I/O 区域的不同部分，而不会互相踩到对方。

I/O 数据拷贝方法（v2，共 11 个补丁）

还是同一系列。这组补丁为 I/O 区域增加了安全的数据批量拷贝方法。在驱动开发中，经常需要一次性把一大块数据从内存搬到硬件（或反过来），比如把一帧图像数据写入显卡的帧缓冲。这些新方法在 Rust 层面保证了拷贝的源地址和目标地址都是合法的，避免了越界访问的风险。Andreas Hindborg 和 Gary Guo 继续在评审中讨论 API 设计细节。

设备驱动框架

设备驱动框架

高阶生命周期类型用于设备驱动（共 24 个补丁）

这是今天技术含量最高的一组补丁。Danilo Krummrich 提出使用 Rust 的高阶生命周期类型（Higher-Ranked Lifetime Types，简称 HRLTs）来重新设计设备驱动框架中的生命周期管理。这解决什么问题呢？在内核驱动中，设备对象的生命周期非常复杂——设备可能随时被热插拔，驱动的各个回调函数需要在不同时间点访问设备数据。以前的设计用了很多变通方法来满足 Rust 的借用检查器，代码比较绕。新设计利用 for<'a> 这种高阶生命周期语法，让编译器能更精确地理解"这个引用在整个回调执行期间都是有效的"，从而写出更简洁、更安全的驱动代码。Uwe Kleine-König（一位资深内核开发者）也参与了讨论。

📬 查看补丁
PCI 设备：为 Device<Bound> 实现 Sync（共 24 个补丁）

这个补丁为已绑定（Bound）状态的 PCI 设备实现了 Sync trait。在 Rust 中，Sync 表示一个类型可以安全地被多个线程同时通过共享引用访问。PCI 设备对象在被驱动成功绑定后，其底层状态由内核的 PCI 子系统保证是线程安全的，所以在 Rust 层面标记为 Sync 是合理的。没有这个标记，你就无法在多线程场景下共享设备引用，而现代驱动几乎都需要多线程操作。Danilo Krummrich 和 Gary Guo 讨论了安全性证明。

📬 查看补丁
ACPI：修复 PRP0001 设备的匹配数据缺失（v6）

ACPI 是现代 PC 和服务器上的硬件描述标准，内核通过读取 ACPI 表来了解有哪些硬件。PRP0001 是 ACPI 中一个特殊的设备 ID，表示"这个设备可以用设备树（Device Tree）方式的 compatible 字符串来匹配驱动"。这个补丁修复了 Rust ACPI 绑定中遗漏了 PRP0001 匹配数据的问题——相当于有些设备明明在系统里，但 Rust 驱动却"认不出"它。现在已经到第六版了，Rafael J. Wysocki（ACPI 子系统维护者）和 Danilo Krummrich 都参与了评审，说明这个修复虽然看起来小，但涉及到的 API 设计讨论很深入。

⚙️ 内核基础设施（同步、数据结构、时间）

Work::disable_sync —— 停止工作队列中的异步任务

Onur Özkan 提交了这个补丁，为内核的工作队列（workqueue）抽象增加了一个 disable_sync 方法。工作队列是内核中"延后执行任务"的机制——当你需要做某件事但不能在当前上下文做（比如在中断处理中不能做耗时操作），就把任务丢到工作队列里让它稍后执行。disable_sync 的作用是：阻止新任务入队，并且等待正在执行的任务完成。这个需求直接来源于上面提到的 Tyr GPU 驱动——在 GPU 重置（reset）过程中，需要先安全地停掉所有排队的重置任务，然后才能释放这些任务使用的资源。Gary Guo 参与了评审。

📬 查看补丁
List::remove —— 修复安全注释

Alice Ryhl（Google 的 Rust-for-Linux 开发者）提交了 2 个补丁来修复 List::remove 方法中的 SAFETY 注释。在 Rust 内核代码中，每个 unsafe 代码块旁边都必须写一段 // SAFETY: 注释，解释为什么这段不安全代码实际上是安全的。这次修复并不改变代码逻辑，而是让注释更准确地描述了安全不变量（safety invariant）——这在内核社区中被视为和修 bug 同等重要的事情，因为错误的安全注释可能会误导后续开发者写出真正不安全的代码。

📬 查看补丁
AtomicAdd 安全注释重写（v2）

Sagar Taunk 提交了对原子操作（atomic operation）中 AtomicAdd 实现的安全注释的改写。之前的注释带着一个 TODO 标记，而且存在语法错误，很难读懂。新版注释清楚地定义了安全契约：说明了 wrapping_add（溢出时回绕的加法）的含义，以及为什么参数类型 Self::Repr::Delta 在这里是安全的。原子操作是多线程编程的基础，确保注释清晰准确对于这种底层代码特别重要。

arch_timer_get_rate 时间函数封装（v4，共 20 个补丁）

Deborah Brouwer 提交了为 Rust 封装 arch_timer_get_rate 函数的第四版补丁。这个 C 函数用于获取系统架构定时器（architecture timer）的频率——简单说就是问硬件"你的时钟每秒滴答多少次"。驱动开发中经常需要精确的时间计算（比如"等待 100 微秒"），知道定时器频率是基础。这个补丁把 C 函数包装成安全的 Rust API，是 Rust 时间子系统抽象的一部分。已经到第四版说明社区对 API 设计进行了充分的讨论和打磨。

📬 查看补丁
module_kset 初始化时机修复（v4，共 4 个补丁）

Shashank Balaji 的补丁修复了内核模块参数子系统的初始化顺序问题。module_kset 是 sysfs 中表示内核模块集合的数据结构。问题是它之前初始化得太晚了——在一些内置模块的 initcalls（初始化调用）之后才初始化，导致这些模块无法在 sysfs 中正确注册。修复方法很直接：把 module_kset 的初始化提前到 do_initcalls() 之前。这对 Rust 模块尤其重要，因为 Rust 内核模块也依赖这套参数注册机制。

Hsiu Che Yu 发现 Rust 块设备层中 Request 结构体的注释有标签不一致的问题。Request 有四种所有权状态（用来追踪一个 I/O 请求的生命周期），注释中用编号 1-4 来标识它们，但有两处不小心写成了字母"B"和"C"而不是数字"2"和"3"。虽然只是注释错误，不影响代码行为，但在内核这种高度协作的项目中，注释的准确性直接影响其他人对代码的理解，所以这个修复是有价值的。Miguel Ojeda 参与了评审。

[RFC 讨论] kconfirm —— 内核配置变更确认工具

这是一个由 Julian Braha 发起的 RFC（Request for Comments，征求意见稿），提议在内核开发工具中加入一个叫 kconfirm 的新脚本。它的作用是：当你修改内核代码后，自动检查你的改动是否导致了 Kconfig 配置选项的变化（比如某个选项被新增、删除或改名了），然后在终端中提示你确认。这对新手特别有帮助，因为你可能改了一个 Makefile 或 Kconfig 文件却没意识到影响了编译配置。讨论分为两个部分：第一部分（scripts: add kconfirm）是脚本本身的实现，Jonathan Corbet（LWN.net 创始人、内核文档维护者）和 Nathan Chancellor 参与了评审，讨论了脚本的实现方式和边界情况；第二部分（Documentation: add kconfirm）是对应的开发者文档，Miguel Ojeda 和 Gary Guo 也加入了评审。社区对这个工具总体是欢迎的，但对细节（比如什么情况下应该触发提示、是否应该默认启用）还在讨论中。

用户空间内存访问（uaccess）

将 INLINE_COPY_{TO/FROM}_USER 转为 Kconfig 配置并简化条件编译

Segher Boessenkool 和 Andrew Cooper 在讨论一组关于 uaccess（用户空间访问）的 RFC 补丁。Linux 内核运行在特权模式，用户程序运行在普通模式，当内核需要读写用户程序的内存时，必须使用特殊的 copy_to_user / copy_from_user 函数（而不能直接读写，否则会有安全问题）。这个补丁系列将一些之前用 C 预处理器 #ifdef 控制的内联拷贝选项改为用 Kconfig 配置来管理，好处是代码更清晰、更容易维护，也更容易被 Rust 代码（通过 bindgen）理解。这看起来是基础设施改进，但对 Rust 内核开发有间接帮助，因为 Rust 绑定生成器处理 Kconfig 比处理复杂的 #ifdef 条件编译要容易得多。
