串口设备总线（SERDEV）与 SYNOLOGY NAS 驱动

串口设备总线（serdev）与 Synology NAS 驱动

serdev Rust 抽象 v8（5 个补丁）

serdev Rust 抽象 v8（5 个补丁）

Markus Probst 提交了串口设备总线（serdev）的第 8 版 Rust 抽象补丁系列，已经收到了 17 条审阅意见。你可以把串口设备总线理解为"内核中专门管理串口连接设备的一套框架"——比如你的 NAS 里面有个小单片机通过串口和主处理器通信，这个框架就负责管理它们之间的对话。这次的补丁系列一共包含 5 个部分，层层递进地构建了完整的抽象。

第一个补丁修改了 devres::register 函数，让它返回对已初始化数据的引用。这看起来是个小改动，但它是后续串口抽象的基础——后面的代码需要在注册设备资源后继续使用这个引用来操作设备。Danilo Krummrich 参与了审阅。

第二个补丁在内核的 serdev_device 结构体中添加了 Rust 私有数据字段。这就像给一个信封里塞了一张便条——C 语言的串口设备结构体现在可以携带 Rust 驱动需要的额外信息了。

核心的第三个补丁添加了串口设备总线的基础 Rust 抽象，让 Rust 驱动开发者可以用安全、符合 Rust 习惯的方式来编写串口驱动。

第四个补丁提供了一个示例驱动，展示了如何使用这些抽象。示例驱动支持两种设备匹配方式：通过设备/驱动名称匹配，或者通过设备树（OF）ID 表匹配。对于学习如何写 Rust 内核驱动的新手来说，这个示例非常有价值。

最后一个补丁更新了 MAINTAINERS 文件——因为原来的 serdev 维护者 Rob 表示需要找人接手，Markus 把自己加了进去。

Synology Microp 驱动 v13（2 个补丁）

Synology Microp 驱动 v13（2 个补丁）

同样来自 Markus Probst，这个补丁系列是上面 serdev 抽象的"第一个真正的用户"。Synology NAS（网络存储设备）里面有一个叫 Microp 的微控制器，它通过串口连接到主处理器，负责控制 LED 指示灯、风扇转速、蜂鸣器，还能处理按钮事件和获取设备型号信息。你可以把它想象成 NAS 里面的"管家"——主处理器通过串口告诉它"把第三个灯打开"或者"风扇调到最高速"。

第一个补丁添加了设备树绑定（devicetree bindings），这是一种描述硬件信息的标准方式，告诉内核"这里有一个 Synology Microp 设备，它的地址在哪里、有什么功能"。第二个补丁则是实际的平台驱动代码。这是一个完全用 Rust 编写的真实硬件驱动，展示了 Rust 在内核中已经可以驱动真实设备了。

LED 子系统 RUST 抽象

LED 子系统 Rust 抽象

LED classdev 抽象 v17（3 个补丁）

LED classdev 抽象 v17（3 个补丁）

Markus Probst 提交了 LED 子系统 Rust 抽象的第 17 版补丁，可见这个系列经过了非常多轮的审阅和改进。这些补丁的目标是让开发者可以用 Rust 来编写 LED 驱动——比如控制你笔记本电脑上的电源指示灯、键盘背光，或者 RGB 灯条。

第一个补丁实现了核心抽象，包含三个主要组件：led::LedOps trait 定义了 LED 驱动需要实现的操作（设置亮度、获取亮度、设置闪烁），led::DeviceBuilder 提供了构建 LED 设备的 builder 模式接口，led::Device 是对 C 语言 led_classdev 结构体的安全封装。这些设计让 Rust 开发者不需要直接和不安全的 C 指针打交道。

第二个补丁添加了 led::Mode trait，这是一个扩展点——有了它，未来可以支持不同类型的 LED 设备（比如普通单色 LED 和 RGB LED）而不需要修改核心框架。

第三个补丁就是这个扩展的第一个应用：多色 LED 支持。它实现了 led::MultiColor 模式、MultiColorSubLed（多色 LED 中的单个颜色通道）以及 led::MultiColorDevice 的安全封装。想象一下 RGB LED 灯条——一个"灯"其实包含红、绿、蓝三个独立的发光单元，这个抽象就是用来管理这种复杂结构的。

值得一提的是，这个系列最初是和一个通过 I2C 控制微控制器 LED 的驱动一起提交的，但由于 I2C 的 register! 宏还没有实现，所以被拆分出来独立提交了。

GPU / Nova 驱动

Nova-Core 固件支持：Hopper/Blackwell 架构 v11（22 个补丁）

Nova-Core 固件支持：Hopper/Blackwell 架构 v11（22 个补丁）

NVIDIA 的 John Hubbard 提交了一个大型补丁系列（共 22 个补丁！），为 Nova GPU 驱动添加对 NVIDIA Hopper 和 Blackwell 架构的固件支持。Nova 是正在开发中的、用 Rust 编写的开源 NVIDIA GPU 驱动——你可以把它理解为"NVIDIA 官方支持的、用 Rust 从头写的新一代显卡驱动"。

RCU 内存管理

RCU 内存管理

新增 RcuBox 类型（4 个补丁系列中的一部分）

新增 RcuBox 类型（4 个补丁系列中的一部分）

由 Alice Ryhl（Google）编写、Philipp Stanner 提交的补丁引入了一个新的 RcuBox 容器类型。简单来说，RcuBox 就像标准的 KBox（内核中的堆分配智能指针，类似于用户态的 Box），但在释放内存时使用 kfree_rcu 而不是普通的 kfree。

这有什么区别呢？在内核中，多个 CPU 核心可能同时在读取同一块内存。如果你直接释放这块内存，正在读取的 CPU 就会访问到无效数据（就像你正在看一本书，突然有人把书烧了）。kfree_rcu 会等到所有正在读取的 CPU 都完成读取后，才真正释放内存。RcuBox 把这个机制包装成了类型安全的 Rust 接口，让开发者不容易犯错。

补丁还引入了 ForeignOwnable 的扩展，允许其他容器依赖 RcuBox 的 RCU 属性，这为后续在驱动中使用 RCU 保护的数据结构打下了基础。Danilo Krummrich 和 Boqun Feng 参与了审阅。

适配 Rust 1.98.0 x86 目标规格变更

适配 Rust 1.98.0 x86 目标规格变更

同样来自 Miguel Ojeda 的预防性补丁。Rust 1.98.0 将不再支持 x86-softfloat 目标规格名称，需要改用简写 softfloat。如果不提前修改，升级编译器后会直接编译失败，报错"invalid rustc abi: 'x86-softfloat'"。这种看似微小的变更实际上很关键——内核构建依赖精确的目标规格配置来生成正确的机器码，尤其是浮点指令的处理方式。Alice Ryhl 参与了审阅。

修复 GenDisk 清理路径

修复 GenDisk 清理路径

Ren Wei 提交了一个修复 Rust 块设备抽象中 GenDisk（通用磁盘）清理路径的补丁。"清理路径"是指当设备被移除或出错时，内核如何正确释放已分配的资源。这就像你关闭一个程序时，系统需要回收它占用的内存和文件句柄一样。如果清理路径有 bug，可能导致内存泄漏（资源没被释放）或者更严重的"双重释放"（同一块内存被释放两次，导致系统崩溃）。Miguel Ojeda 对此进行了审阅。

PWM 驱动：使用 pin_init::zeroed() 初始化

Michal Wilczynski 改进了 Rust PWM（脉冲宽度调制）驱动中 pwm_ops 结构体的初始化方式，改用 pin_init::zeroed()。PWM 常用于控制 LED 亮度、电机转速等。原来的初始化方式可能不够安全或简洁，pin_init::zeroed() 能确保结构体的所有字段都被正确地初始化为零值，避免使用未初始化内存导致的未定义行为。Alexandre Courbot 参与了审阅。

GitHub Issue #1237：Node::add_death 中的 unsafe 不变量问题

GeorgeAndrou 报告了一个标记为 unsound（不健全）的安全问题。在 binder 驱动的 Node::add_death 函数中，unsafe 代码的安全不变量（safety invariant）仅依赖于隐式的调用约定（calling convention），而没有显式地保证。这意味着如果调用约定发生变化，这段代码可能会导致未定义行为。在 Rust 中，"unsound"是一个严重的标签——它意味着安全代码有可能触发未定义行为，这违反了 Rust 的核心安全承诺。
