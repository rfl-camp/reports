️ GPU / DRM 驱动

nova-core：驱动解绑时执行完整卸载序列（v7，共 4 个补丁）

这组补丁来自 NVIDIA 的 Alexandre Courbot，解决了一个很实际的问题：当你卸载（unbind）nova-core 驱动时，之前的代码会让 GPU 上的 GSP（GPU System Processor，GPU 内部的一个小处理器）继续运行，并且不清理 WPR2 内存区域。这带来两个麻烦：第一，下次重新加载驱动时，因为 WPR2 区域还在，必须先重置 GPU 才能重新初始化；第二，GPU 上的硬件资源（比如 falcon 引擎分配的内存）没有被释放，造成泄漏。v7 版本实现了一套完整的卸载流程——依次运行 Booter Unloader 和 FWSEC-SB 固件来安全关闭 GSP、释放 WPR2 区域和相关硬件资源。这就像你关电脑时要先关闭所有程序再关机，而不是直接拔电源。Danilo Krummrich 参与了代码审查。

硬件随机数生成器（hw_random）

为 hw_random 子系统添加 Rust 抽象（共 2 组补丁）

Manos Pitsidianakis 和 Miguel Ojeda 提交了两组补丁，为内核的硬件随机数生成器（hw_random）子系统提供 Rust 绑定。hw_random 是什么？你的电脑里可能有专门的硬件芯片来生成真正的随机数（不是软件算出来的伪随机数），比如 Intel 的 RDRAND 指令、或者虚拟机里的 virtio-rng 设备。hw_random 子系统就是内核中统一管理这些硬件随机源的框架。

Onur Özkan 也参与了其中一组补丁的开发。值得注意的是，这个 Rust 抽象中注册过程用了一个原子布尔值来保护，因为目前 Rust 内核代码还不支持"关中断自旋锁"（IRQ disabling spinlock）。开发者在补丁中标注了 TODO，等将来支持后会切换到更正规的锁机制。另外，基于这些绑定的 virtio-rng Rust 驱动将作为独立系列提交（因为它还依赖 virtio 抽象系列）。

s390 大型机架构：启用 Rust 支持（v4，共 6 个补丁）

来自 IBM 的 Jan Polensky 提交了第 4 版补丁，让 s390 架构（IBM 大型机使用的 CPU 架构）支持 Rust。你可能没听说过 s390，但它在银行、航空公司、政府机构等需要超高可靠性的地方非常常见。这组补丁包含 6 个子补丁，主要做了以下事情：把 s390 注册为"可用 Rust 的 64 位架构"；添加了 Rust 代码所需的汇编接口，比如 WARN/BUG 报告机制（内核遇到严重错误时用来记录和报告问题的基础设施）和静态分支（static branch，一种运行时几乎零开销的条件跳转优化）。Miguel Ojeda 参与了审查。这意味着继 x86、ARM64 之后，Rust 正在向更多 CPU 架构扩展。

BINDER 驱动（ANDROID IPC）

Binder 驱动（Android IPC）

修复 32 位内核上偏移数组遍历的步长错误

这是一个由 kernel test robot 发现、Hyunwoo Kim 报告的 bug 修复。问题出在 Rust 版 Binder 驱动的 Allocation::Drop 实现中：当释放一个 Binder 分配对象时，代码需要遍历一个"偏移数组"来清理其中引用的对象。这个数组的每个元素是 binder_size_t，也就是 u64（8 字节），但原来的代码错误地使用了 usize 作为步长。在 64 位内核上 usize 就是 8 字节，所以没问题；但在 32 位内核上，usize 只有 4 字节，这意味着代码会每 4 字节读一次，而不是每 8 字节——相当于每读完一个元素后，下一个元素会从中间位置开始读，导致数据完全错乱，可能引发内存越界访问。修复方法很简单：把步长从 usize 改成 u64。Alice Ryhl 参与了审查。

内存与资源管理

内存与资源管理

Page::nid 函数标记为 inline

Nakamura Shuta 提交了一个小但有意义的优化补丁。在内核中，Page::nid 是一个获取内存页所属 NUMA 节点 ID 的函数，它只是简单地调用了 C 函数 page_to_nid。但由于没有标记为 inline，编译器可能会为这个"中转站"函数生成一次独立的函数调用——每次调用都要入栈、跳转、出栈，对于这么简单的操作来说完全是浪费。加上 #[inline] 后，编译器会把函数体直接"嵌入"到调用处，消除这个不必要的中间层。通过 nm vmlinux 可以验证，修改后这个符号不再出现在内核二进制中。Alice Ryhl 和 Gary Guo 做了审查。

📬 查看补丁

Devres<T> 添加 'static 生命周期约束

Danilo Krummrich 为 Devres<T> 类型添加了 'static 生命周期限定。Devres 是内核中"设备资源管理"的 Rust 抽象——当一个设备被移除时，所有通过 devres 注册的资源会自动释放（就像你退房时酒店自动帮你归还所有借的东西）。添加 'static 约束意味着 Devres 管理的类型不能包含任何非静态引用，这样可以确保资源不会在其引用的数据被销毁后仍然存活，防止悬垂引用。

ZEROCOPY 库讨论

zerocopy 库讨论

新频道成立 & field_container_of() 讨论

Miguel Ojeda 在 Zulip 上为内核中集成的 zerocopy 库创建了专门的 #zerocopy 讨论频道。zerocopy 是一个用于安全地在字节序列和结构化类型之间转换的 Rust 库，内核将其作为"vendor"（内嵌供应商库）使用。

在这个新频道中，Boqun Feng 发起了一个技术讨论：他在研究 zerocopy 的 Ptr 类型时发现了 project() 方法可以做从类型到字段的投影，于是向 zerocopy 的作者 Joshua Liebow-Feeser 询问是否有反向操作——即 field_container_of()，也就是"已知一个字段的指针，怎么找到包含它的结构体的指针"。这在内核中极其常见（C 代码中的 container_of 宏几乎无处不在），能否在 zerocopy 中安全地实现它是一个很有价值的讨论。

zerocopy 在驱动环形缓冲区中的应用探讨

Manos Pitsidianakis 在频道中提出了一个有趣的应用场景：能否用 zerocopy 来处理 virtio 驱动中的环形缓冲区？在 virtio 架构中，宿主设备后端会把特定布局的结构体（使用小端字节序）放进共享的环形缓冲区中。如果 zerocopy 能安全地处理这种"从原始字节到结构体"的转换，就不需要手动做内存拷贝了，可以显著提升性能。这个方向值得关注。

kbuild：清理 Rust 编译器生成的长类型名文件

Joel Kamminga 提交了一个 kbuild（内核构建系统）补丁，让 make clean 时自动清理 *.long-type-*.txt 文件。这些文件是怎么来的？当 Rust 编译器遇到一个类型名太长、一行放不下的错误信息时（在内核中这种超长泛型类型相当常见），它会把完整的类型信息写到一个 .long-type-xxx.txt 文件中。这些文件纯粹是编译器的临时产物，不应该留在源码树里。这个补丁把它们加入了 clean 的清理列表。同时，GitHub 上也创建了对应的 issue #1236，并标记为 good first issue——如果你想给 Rust-for-Linux 做贡献，这是一个很好的入门机会！

module_param：修复 pr_warn 缺少换行符
