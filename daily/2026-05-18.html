️ 驱动框架：高阶生命周期类型重构（27 补丁系列）

核心问题是什么？

这是今天最重量级的活动。Danilo Krummrich 发出了 v3 版本的补丁系列，一共 27 个补丁，目标是彻底改造 Rust 设备驱动访问硬件资源的方式。

在 Linux 内核中，当一个驱动程序被加载并"绑定"到某个硬件设备时，它需要访问各种设备资源（比如 PCI 设备的内存映射区域）。目前 Rust 驱动使用 Devres<T> 这个包装器来安全地访问这些资源——每次访问都需要传入一个 &Device<Bound> 引用来"证明"设备还在工作。

问题在于：这种方式要求驱动数据必须是 'static（也就是"活得和程序一样久"），这导致驱动不能直接存储对设备的引用，用起来很不方便。新的方案引入了一个 'bound 生命周期参数，让驱动的私有数据可以直接通过引用来持有设备资源，不再需要 Devres 的运行时检查开销。

① 移除 ForeignOwnable 的 'static 限制（作者：Gary Guo）
ForeignOwnable 是一个 trait，用于标记哪些类型可以安全地"交给 C 代码持有"。之前要求必须是 'static，现在通过给 GAT（泛型关联类型）加上 Self: 'a 约束来放宽这个限制，为后续改动打基础。

📬 查看补丁

② 将 'static 约束移到构造器（作者：Gary Guo）
配合上面的改动，把 'static 限制从驱动数据方法和总线适配器实现中移除，只保留在 Registration（驱动注册）的构造器中。这样驱动内部代码就可以使用非 'static 的类型了。

📬 查看补丁

③ 将驱动私有数据与驱动类型解耦
给所有总线驱动 trait 添加了 type Data<'bound> 关联类型，把驱动的"私有数据类型"从驱动结构体本身分离出来。这是让每个驱动可以自定义"绑定期间存什么数据"的关键一步。

📬 查看补丁

④ 在 devres 释放之前先丢弃 drvdata
修改了 device_unbind_cleanup() 的执行顺序：先执行 post_unbind_rust 回调（丢弃驱动私有数据），再调用 devres_release_all() 释放设备资源。这保证了驱动数据在引用的资源被释放之前先被清理——这就像"先放下手里拿着的东西，再关掉保险柜"。

📬 查看补丁

⑤ 为各总线的 Device<Bound> 实现 Sync
分别为 PCI、Platform、Auxiliary、USB 以及通用 Device 的 Device<Bound> 类型实现了 Sync trait。Bound 只是一个零大小的类型状态标记，不影响线程安全性。实现 Sync 后，驱动可以在多线程环境中安全地共享对设备的引用——这对存储 &'bound Device<Bound> 的场景是必须的。

⑥ 让各总线 Driver trait 支持生命周期参数
分别为 PCI、Platform、Auxiliary、USB、I2C 总线的 Driver trait 添加了 'bound 生命周期，将 type Data 改为 type Data<'bound>。这样 probe() 和 unbind() 回调就能直接接收带生命周期的设备引用，驱动可以在自己的私有数据中直接存储设备引用，而不需要再包一层 Devres。

⑦ 添加 ForLt trait 支持高阶生命周期
新增了一个叫 ForLt 的 trait，用来在类型系统层面表达"对于任意生命周期 'a，这个类型都是合法的"。这是让整个 GAT + 高阶类型方案能正常工作的类型系统基础设施。

⚡ 电源管理：RUNTIME PM 的 RUST 支持

⚡ 电源管理：Runtime PM 的 Rust 支持

Onur Özkan 提交了一个 RFC（征求意见稿）补丁，为 Linux 内核添加 Runtime PM（运行时电源管理）的 Rust 绑定。Danilo Krummrich 参与了讨论并提供了反馈。

这是什么意思？ 想象你的笔记本电脑 WiFi 网卡在不传输数据时自动进入低功耗模式，有数据来了又立刻"醒来"——这就是 Runtime PM 在做的事。目前内核中这个功能是用 C 实现的，这个补丁的目标是让 Rust 驱动也能方便地使用这套机制。

由于是 RFC 阶段，这意味着作者还在征求社区意见，API 设计可能会有比较大的变化。讨论中 Danilo 提出了一些关于接口设计的建议。这对于编写功耗敏感的 Rust 驱动（比如移动设备上的驱动）来说非常重要。

构建系统：KCONFIRM 验证脚本

构建系统：kconfirm 验证脚本

Demi Marie Obenour 提交了 kconfirm 脚本的 RFC v3 版本，Nathan Chancellor 和 Miguel Ojeda 参与了讨论，目前已收到 10 条 review 评论，讨论非常活跃。

kconfirm 是什么？ 这是一个新的辅助脚本，计划放在内核源码的 scripts/ 目录下。它的作用是帮助开发者在编译内核前验证 Kconfig 配置是否正确——就像你在安装软件前先检查系统要求是否满足一样。这对于确保 Rust-for-Linux 相关的内核配置选项被正确启用特别有用。

第二个补丁（2/3）添加了相应的文档说明，让开发者知道怎么使用这个新工具。讨论中大家对脚本的具体行为、错误提示方式等细节提出了不少建议。Nathan Chancellor（LLVM/Clang 内核构建的主要维护者）和 Miguel Ojeda（Rust-for-Linux 项目的领导者）的参与表明这个工具受到了核心开发者的重视。

️ GPU/DRM 驱动：NOVA 项目新手参与指南

️ GPU/DRM 驱动：Nova 项目新手参与指南

在 Zulip 的 #Nova 频道中，一位叫 Nanonej 的新贡献者询问如何开始参与 Nova 驱动的开发。Alexandre Courbot（Nova 驱动的主要维护者之一）给出了详细的指导。

Nova 是什么？ 它是一个用 Rust 编写的 NVIDIA GPU 驱动，目标是替代现有的 nouveau 开源驱动。这是 Rust-for-Linux 生态中最引人注目的"真实世界"驱动项目之一。

讨论要点： Alexandre 解释了 Nova 的代码审查流程——所有可见的代码都是通过邮件列表发送补丁的方式提交的。你发出 v1，收到反馈，然后修改后发 v2、v3……直到代码被接受。Nanonej 表示已经理解了补丁邮件的流程，并询问是否需要 fork 项目做备份或多机协作——Alexandre 确认了这是合适的做法。

这段对话对新手很有参考价值：它展示了内核社区的协作方式和 Nova 项目的参与门槛其实不高——只要你会用 git send-email 发补丁就能开始。
