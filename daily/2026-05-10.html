内核版本发布：Rust fixes for 7.1

Miguel Ojeda（Rust-for-Linux 项目的核心维护者）今天向 Linus Torvalds 发出了一个 Git Pull 请求，标题是「Rust fixes for 7.1」。这意味着他请求 Linus 把一批 Rust 相关的修复合并进 Linux 7.1 版本。

这些修复已经在 linux-next（一个专门用来测试即将合并代码的分支）里待了一整周，确认没有引起冲突或问题。Miguel 还提到，在这个开发周期内他可能还会再发一次修复 PR。这个基线是从 7.1-rc1（2026 年 4 月 27 日发布的第一个候选版本）开始的。

为什么这件事重要？每次 Rust 代码被成功合并进主线内核，都意味着 Rust 在 Linux 内核中的地位更加稳固。这就好比一个新员工一次又一次地顺利通过试用期考核，逐渐成为团队不可或缺的一员。

💡 小白科普：Git Pull Request 是子系统维护者请求上游（这里是 Linus 本人）合并代码的正式方式。Linux 内核采用层级式的维护者结构，每个子系统的维护者收集、审核补丁，然后统一提交给 Linus。linux-next 是一个集成测试分支，所有即将合并的代码会先在这里汇合，确保彼此不冲突。📖 了解内核开发流程

⏱️ 时间子系统：FSLEEP() 增加调试断言

⏱️ 时间子系统：fsleep() 增加调试断言

Onur Özkan 提交了一个补丁，给 Rust 的 fsleep() 函数增加了调试断言（debug assertions），用来检测超出合理范围的输入参数。这个补丁得到了 Andreas Hindborg 和 Gary Guo 等 6 位开发者的审阅，可以说受到了相当多的关注。

fsleep() 是内核中一个「灵活睡眠」函数——它会根据你需要睡眠的时间长短，自动选择最合适的底层实现（微秒级用 udelay，毫秒级用 msleep 等）。问题是，如果传入了一个超出预期范围的值（比如负数或者极大的数），之前的代码不会给出任何提示，可能导致难以发现的 Bug。

加了 debug assertion 之后，在开发和测试阶段（debug 模式），如果参数不合理就会立即触发警告，帮助开发者尽早发现问题。这就像是在厨房秤上加了一个警报——如果你不小心放了太多盐，秤会马上叫起来，而不是等到菜做完才发现太咸了。

📬 查看补丁
💡 小白科普：Debug Assertion（调试断言）是一种只在调试版本中生效的检查机制。它不影响正式发布版本的性能，但能在开发过程中帮你抓住不合理的输入值。Rust 中用 debug_assert!() 宏来实现。📖 Rust debug_assert 文档

初始化框架 (PIN-INIT)

初始化框架 (pin-init)

今天有两个与 pin-init 相关的补丁活动：

1. 用 loop {} 代替原来的方式来生成 Never 类型值

Onur Özkan 提交了一个补丁，修改了 pin_init 模块的内部实现：将之前生成「永不返回值」（never value）的方式改为使用 loop {} 无限循环。Gary Guo 参与了审阅。

这听起来可能很奇怪——为什么要写一个无限循环？在 Rust 的类型系统中，loop {} 表达式的类型是 !（never type），意思是「这段代码永远不会执行到这里」。这是 Rust 类型系统中一个优雅的技巧，用来在编译期告诉编译器某些分支是不可达的。相比之前的实现，loop {} 是一种更惯用、更清晰的写法。

📬 查看补丁

2. MAINTAINERS 文件中 pin-init 的维护者配置修正

这是 Mauro Carvalho Chehab 大型文档改进系列（共 13 个补丁）中的一个。他发现 pin-init 在 MAINTAINERS 文件中的维护者配置条目（"P" 字段）既不是一个有效的 ReST 文档路径，也不是一个 URL，导致 Sphinx 文档构建工具无法为它生成超链接。这个补丁将其改为指向一个已格式化的 URL，修复了这个问题。Gary Guo 也参与了审阅。

📬 查看补丁
💡 小白科普：pin-init 是 Rust-for-Linux 中一个非常重要的初始化框架。在内核中，很多数据结构一旦被创建就不能移动位置（因为其他地方可能有指向它的指针），这叫做 "pinned"。pin-init 提供了一种安全的方式来初始化这类数据结构，避免了 C 代码中常见的「先创建后初始化」导致的未初始化内存访问问题。Never type (!) 是 Rust 的一个特殊类型，表示一个值永远不可能存在，常用于标记不可达代码路径。📖 了解 Never 类型

中断管理与自旋锁：SPINLOCKIRQ 来了

中断管理与自旋锁：SpinLockIrq 来了

来自 IBM 的 Heiko Carstens 提交了一组包含 11 个补丁的系列（Part 1），为 Rust 引入了带引用计数的中断禁用（Refcounted interrupt disable）和 SpinLockIrq 支持。Boqun Feng 参与了审阅讨论。

这到底在说什么？让我们用一个比喻来理解：想象你在一个繁忙的厨房里做一道精细的菜。为了不被打断，你可以让别人暂时不要叫你（= 禁用中断）。但问题是，如果厨房里有好几个人都说了「别叫我」，那只有等所有人都说「好了可以叫我了」之后，叫人才应该恢复。这就是「引用计数的中断禁用」——用一个计数器记录有多少人要求安静，只有计数归零才真正恢复中断。

SpinLockIrq 则是在获取自旋锁的同时禁用中断的一种锁机制。在内核中，如果一个中断处理程序和普通代码都要访问同一个数据，只用普通的自旋锁是不够的——你还必须禁用中断，否则可能在持有锁的时候被中断打断，而中断处理程序也想获取同一把锁，就会死锁。SpinLockIrq 把这两个操作打包在一起，用 Rust 的类型系统来保证你不会忘记禁用中断。

这是一组非常基础且重要的补丁，对于未来用 Rust 编写内核驱动来说至关重要。这只是 Part 1，后续应该还会有更多。

📬 查看补丁系列
💡 小白科普：中断（Interrupt）是硬件通知 CPU「有事要处理」的信号，比如键盘按键、网络数据到达等。CPU 会暂停当前工作去处理中断。自旋锁（Spinlock）是一种忙等待的锁——如果锁被别人持有，当前 CPU 会一直循环检查直到锁被释放，而不是去睡觉等通知。它适用于持有时间非常短的场景。📖 内核自旋锁文档

构建系统与工具链

构建系统与工具链

1. 修复 ccache 与 rustc 链接器选项的兼容问题

Mohamad Alsadhan 提交了第 8 版补丁，解决了一个实际使用中常遇到的问题：当 HOSTCC 环境变量包含一个包装器命令时（比如 "ccache gcc"），rustc 的 -C linker= 选项会把它当成多个单词来解析。Shell 会把 "ccache gcc" 拆成两个词，rustc 把第二个词当成了输入文件名，于是报错：error: multiple input filenames provided。

这个补丁的解决方案是让 kbuild 系统使用单个可执行文件路径来传递给 rustc -C linker=。这已经是第 8 版了，说明这个问题虽然看起来简单，但要在各种构建场景下都正确处理还是有不少细节要考虑的。

如果你曾经在用 ccache 加速内核编译时遇到 Rust 编译报错，这个补丁就是来解决你的问题的！

📬 查看补丁

2. 修复 rust-analyzer 对原始类型的 IDE 支持

Jesung Yang 提交了第 7 版补丁（包含 2 个子补丁），修复了 generate_rust_analyzer.py 脚本，改善了 IDE（集成开发环境）对 Rust 原始类型（primitive types，如 i32、bool 等）的支持。

在内核开发中，rust-analyzer 是开发者最常用的 IDE 工具——它提供代码补全、跳转到定义、错误提示等功能。但由于内核的构建系统比较特殊，rust-analyzer 需要一个专门生成的配置文件才能正确理解代码结构。这个补丁修复了配置生成脚本中的问题，让 rust-analyzer 能正确识别和处理原始类型。

GPU/DRM 驱动：ASAHI GEM SHMEM 变更

GPU/DRM 驱动：Asahi GEM SHMEM 变更

在 Zulip 的 DRM 频道中，Gary Guo 分享了一个链接，指向 Linux 7.1-rc1 中新加入的 call_once.h 头文件，讨论的背景是 Asahi GPU 驱动中 GEM SHMEM 相关的变更。

Asahi 是 Apple Silicon（M1/M2 芯片）的开源 GPU 驱动项目，很大一部分是用 Rust 编写的，是 Rust-for-Linux 最重要的真实用例之一。GEM（Graphics Execution Manager）是 Linux DRM（Direct Rendering Manager）子系统中的内存管理框架，而 SHMEM 是 GEM 的一个后端，使用共享内存来分配显存对象。

Gary 提到的 call_once.h 是一个确保某段初始化代码只执行一次的机制（类似于 Rust 的 std::sync::Once）。这暗示 Asahi 驱动的 GEM 内存管理部分正在进行一些底层的初始化机制调整。讨论还比较初步，后续值得持续关注。

💬 查看 Zulip 讨论
💡 小白科普：DRM（Direct Rendering Manager）是 Linux 内核中管理 GPU 的子系统，负责显存分配、命令提交等底层图形操作。GEM（Graphics Execution Manager）是 DRM 中的一套显存对象管理 API。你在屏幕上看到的每一帧画面，背后都有 DRM/GEM 在工作。📖 了解 DRM

️ IDE 与开发者体验

️ IDE 与开发者体验

1. rust-analyzer 对 container_of! 宏的理解出了问题

Alexandre Courbot 在 Zulip 的 Help 频道报告了一个问题：rust-analyzer 突然无法正确理解 container_of! 宏的类型。他提到之前 pin_init! 宏也出现过类似的问题——rust-analyzer 有时候会出现这种「间歇性抽风」的行为，让开发者很头疼。

Miguel Ojeda 看到后立刻抄送了 Tamir Duberstein 和 Jesung Yang（后者正在做上面提到的 rust-analyzer 配置修复工作），说明这些问题可能是相互关联的。

container_of! 是内核中非常常用的一个宏——给定一个结构体成员的指针，它能反推出整个结构体的起始地址。这是 Linux 内核链表等数据结构实现的核心技巧。如果 IDE 不能正确理解这个宏，开发者在写代码时就会看到一堆误报的错误，严重影响开发体验。
