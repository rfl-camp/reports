️ 架构支持：s390 大型机迎来 Rust

s390 架构 Rust 支持补丁 v6（共 6 个补丁）

s390 架构 Rust 支持补丁 v6（共 6 个补丁）

s390 是 IBM 大型机（mainframe）使用的处理器架构，常见于银行、航空等需要极高可靠性的场景。这组补丁由 Jan Polensky 提交，Gary Guo、Alexander Gordeev、Heiko Carstens 等人参与审查，已经迭代到第 6 版，说明社区对质量要求很高。

具体来说，这组补丁做了以下几件事：
① 把 s390 注册为一个"Rust 可用"的 64 位架构，让内核构建系统知道可以在 s390 上编译 Rust 代码；
② 添加了 Rust 代码在 s390 上报告 WARN/BUG（内核警告和错误）时所需的汇编接口；
③ 提供了静态分支（static branch）的支持——这是内核中一种性能优化技术，可以在运行时几乎零开销地开关某些代码路径；
④ 设置了正确的编译器标志和 bindgen 目标，确保 Rust 代码能正确调用 C 代码。

这很重要，因为 Rust 目前在内核中只支持少数几个架构（x86_64、ARM64、RISC-V 等），每增加一个架构都意味着 Rust 在内核中的"地盘"更大了。对于 IBM 大型机用户来说，未来也可以享受 Rust 带来的内存安全保障。

nova-core：用 zerocopy 安全解析 GPU 固件（19 个补丁，v2）

nova-core：用 zerocopy 安全解析 GPU 固件（19 个补丁，v2）

nova-core 是正在开发中的 NVIDIA GPU 开源内核驱动。GPU 驱动需要读取固件（firmware）中的数据结构，比如 FalconUCodeDescV2——这是 NVIDIA GPU 内部一个叫 Falcon 的微控制器所使用的代码描述信息。以前，要把一段原始字节解读为这种结构体，需要写 unsafe impl FromBytes——也就是程序员自己保证"我知道这段内存的布局是对的"，编译器不会帮你检查。

现在，内核引入了 zerocopy 这个 Rust 库，可以通过 #[derive(FromBytes)] 安全地自动派生这个能力，再调用 read_from_prefix 方法从字节流中读取结构体。这样做的好处是：编译器会在编译时验证结构体的每一个字段都可以安全地从任意字节初始化，大大降低了出错的可能性。Miguel Ojeda 提交，Gary Guo 和 Danilo Krummrich 参与审查。

DRM GEM SHMEM：DmaResvGuard 锁辅助工具（v19，共 4 个补丁）

DRM GEM SHMEM：DmaResvGuard 锁辅助工具（v19，共 4 个补丁）

Lyude Paul（来自 Red Hat）提交了 DRM 子系统中 GEM（Graphics Execution Manager）共享内存部分的 Rust 绑定更新。这次引入了一个 DmaResvGuard 辅助结构体，用来简化 DMA 预留锁（dma_resv lock）的加锁和解锁操作。DMA 预留锁是 GPU 驱动中非常重要的同步机制——当 CPU 和 GPU 同时要访问一块内存时，需要用这个锁来协调，防止数据冲突。有了这个 Guard，获取锁后会自动在作用域结束时释放，不容易忘记解锁，就像 Rust 中的 MutexGuard 一样。

DRM GEM SHMEM：引入 sg_table() 接口（v19）

DRM GEM SHMEM：引入 sg_table() 接口（v19）

同一系列中，Lyude 还添加了 shmem::Object::sg_table() 方法。Scatter-gather table（散列表）描述了一块物理上不连续的内存在各个地方的分布情况，GPU 驱动需要它来建立 DMA 映射。这个接口的设计特别注意了安全性：它在 shmem::Object 中引入了一个 Devres（设备资源）资源，确保在驱动卸载（unbind）时，所有从 scatter-gather table 创建的映射都会被正确释放，不会留下悬空引用。

UniqueArc::as_ptr 已合入 rust-next ✅

UniqueArc::as_ptr 已合入 rust-next ✅

Andreas Hindborg 提交的补丁为 UniqueArc 添加了 as_ptr() 方法，并已经合入了 rust-next 分支（commit 4fedd763）。UniqueArc 是内核中一种特殊的引用计数智能指针——它保证在某一时刻只有一个拥有者，这样你就可以安全地修改里面的数据。新增的 as_ptr() 方法让你能从 UniqueArc 中获取一个原始指针，这在需要与 C 代码交互时非常有用（C 代码不认识 Rust 的智能指针，只认原始指针）。实现上，它直接委托给了底层 Arc 的实现。补丁经过了 Alice Ryhl 和 Miguel Ojeda 的审查。

导出 lock::do_unlocked（v2）

导出 lock::do_unlocked（v2）

Andreas Hindborg 的另一个补丁将 lock::do_unlocked 函数导出为公开 API。这个函数的作用是：在持有锁的情况下，临时释放锁去执行某些操作，完成后再重新获取锁。这在内核中有时是必须的——比如你持有一个自旋锁，但需要调用一个可能睡眠的函数，就必须先放锁。导出这个函数意味着其他 Rust 模块（比如驱动）也可以使用这个功能了。Alice Ryhl 和 Miguel Ojeda 参与了审查。

CPU 与 NUMA 拓扑工具函数

添加 num_possible_cpus 和 nr_online_nodes 的 Rust 封装（各 v2）

添加 num_possible_cpus 和 nr_online_nodes 的 Rust 封装（各 v2）

这两组补丁分别为 C 函数 num_possible_cpus() 和 nr_online_nodes() 提供了 Rust 安全封装。num_possible_cpus() 返回系统中可能存在的 CPU 核心数量——注意是"可能"而不是"当前在线"，因为在支持热插拔的服务器上，CPU 可以动态增减。nr_online_nodes() 返回当前在线的 NUMA 节点数——在大型服务器中，内存并不是"一碗水端平"的，不同 CPU 访问不同位置的内存速度不同，NUMA 节点就是用来描述这种"远近亲疏"关系的。

这些封装看起来很简单，但它们是构建更复杂功能（比如 per-CPU 数据结构、NUMA 感知的内存分配）的基础砖块。Gary Guo 和 Alice Ryhl 参与了审查。

Miguel Ojeda 提交了一组构建系统相关的补丁，为引入新的过程宏库（zerocopy-derive）做准备。过程宏是 Rust 的一种编译时代码生成机制——你在代码里写 #[derive(FromBytes)]，编译器会在编译时运行过程宏来自动生成实现代码。内核中已经有了 macros 这个过程宏 crate，现在要加入 zerocopy-derive，所以需要让构建系统能更通用地处理多个过程宏。Nicolas Schier 参与了审查。

这组补丁中的关键改动包括：
① 定义 procmacro-extension 变量：过程宏编译后会生成一个动态库文件（.so 或 .dylib），但不同平台的扩展名不同。以前用的是专门针对 libmacros 的变量名，现在改成了通用的名字，这样所有过程宏都能共享这个逻辑。
② 定义 procmacro-name 函数：一个 Makefile 函数，用来从 crate 名称生成对应的库文件名。
③ 支持 per-target 环境变量：允许为每个编译目标设置独立的环境变量，这在编译多个过程宏时很有用。
④ 修复 quiet_cmd_rustc_procmacrolibrary 显示：让构建日志中显示正确的命令信息，方便调试。
⑤ 删除未使用的变量：清理代码。

时钟子系统：引入 ExclusiveClk 并用于 PWM 驱动（v2）

时钟子系统：引入 ExclusiveClk 并用于 PWM 驱动（v2）

Maurice Hieronymus 和 Daniel Almeida 提交了为内核时钟子系统添加 ExclusiveClk（独占时钟）抽象的补丁。在嵌入式系统中，硬件外设（如 PWM 控制器、串口等）需要时钟信号才能工作。有些时钟可以被多个设备共享，但有些情况下某个设备需要独占一个时钟——比如它需要调整时钟频率，这会影响到共享的其他设备。ExclusiveClk 就是为这种场景设计的，确保一个设备独占某个时钟资源。这个补丁还把它实际用在了 pwm-th1520 驱动中——这是一个用于 T-Head TH1520 芯片的 PWM（脉宽调制）驱动，PWM 常用于控制 LED 亮度、电机转速等。

IoCapable trait：完善对齐要求的安全契约

IoCapable trait：完善对齐要求的安全契约

Alexandre Courbot（来自 NVIDIA）发现 IoCapable trait 的安全契约（safety contract）中存在遗漏。IoCapable 定义了设备 I/O 内存读写的接口，它的 io_read 和 io_write 方法要求传入的地址必须正确对齐——比如读 32 位值时地址必须是 4 的倍数。但之前的安全契约文档只要求了地址在有效范围内，没有提到对齐要求。这个补丁把对齐要求明确写进了安全契约。虽然现有的调用者都已经通过 io_addr() 或 io_addr_assert() 获取对齐好的地址，但明确文档化很重要——这就是 Rust 中 unsafe 代码的哲学：所有的前提条件都要白纸黑字写清楚。

Lyude 在 #Help 频道分享了她在 KMS 补丁系列中尝试理解 ForLt trait 的困惑。ForLt 是一种高阶类型（Higher-Ranked Types, HRT）的编程模式，用来表达"对于任意生命周期都成立"的类型约束。她想用它来去除 KMS 绑定中对引用计数的依赖，但发现相关文档非常缺乏。这反映了 Rust-for-Linux 项目在使用 Rust 高级特性时面临的一个普遍挑战：这些特性即使在普通 Rust 生态中文档也不完善，在内核场景下更是少有参考。

Rust 工具链 bug 的分类和处理

Miguel Ojeda 在 #Help 频道讨论了关于 Rust 工具链 bug 分类（triage）的话题。当内核开发者在使用 rustc 编译器、bindgen 等工具时遇到 bug，需要有人帮忙判断这是工具链的问题还是内核代码的问题，并向上游（Rust 编译器团队）报告。这种"桥梁"角色对于 Rust-for-Linux 项目的健康发展非常重要。
