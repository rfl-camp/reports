GPU / DRM 驱动

Nova 驱动：让 nova-drm 能调用 nova-core（v4，共 6 个补丁）

Nova 是社区正在开发的 NVIDIA GPU 开源驱动。它分成两部分：nova-core（核心层，管理 GPU 硬件）和 nova-drm（DRM 层，负责接收用户空间的命令）。目前的问题是，nova-drm 即将需要接收用户空间的 IOCTL 请求，然后转发给 nova-core 去执行真正的工作，但现有的 Rust 构建系统不支持跨模块调用。这组补丁的第四版解决了这个问题——它让 nova-core 能导出 Rust 元数据（metadata），使得 nova-drm 可以正确地链接和调用 nova-core 的函数。同时，补丁还顺便内联（inline）了一些初始化方法，以减少函数调用开销。

Tyr 驱动：把探测资源移入注册数据（v2）

Tyr 是一个 GPU 驱动（基于 DRM 框架）。当一个驱动"探测"（probe）到硬件设备时，它需要获取各种资源——比如时钟、电压调节器、MMIO 内存映射、固件状态和 GPU 信息。这个补丁引入了一个新的结构体 TyrDrmRegistrationData，把这些资源统一管理起来。这样做的好处是：这些资源的生命周期被绑定到了 DRM 设备的注册期间，也就是说只要设备还在工作，这些资源就不会被意外释放。这是一种更安全、更清晰的资源管理方式，就像把散落在桌上的文件整理到一个文件夹里一样。

DMA Fence Rust 抽象（共 4 个补丁）

DMA fence（DMA 栅栏）是 GPU 驱动中非常重要的同步机制。想象一下：GPU 在执行渲染任务时，CPU 需要知道"GPU 什么时候把这个任务做完了"，DMA fence 就是 GPU 用来告诉 CPU "我做完了"的信号。这组补丁为 DMA fence 添加了 Rust 语言的抽象层，让 Rust 驱动开发者可以用安全的 Rust 代码来使用 DMA fence，而不需要直接操作不安全的 C API。这是 GPU 驱动 Rust 化的重要基础设施。作者 Philipp Stanner 和 Daniel Almeida 已经收到了 4 条审阅意见。

RCU 内存管理

RCU 内存管理

新增 RcuBox 类型（共 3 个补丁）

Boqun Feng 提交了由 Alice Ryhl 编写的 RcuBox 补丁。RcuBox 是一个类似于 Rust 标准库中 Box 的智能指针，但有一个关键区别：当你释放（drop）一个 RcuBox 时，它不会立即释放内存，而是等待一个 RCU 宽限期（grace period）之后才释放。为什么要这样做？因为在多核 CPU 系统中，可能有其他 CPU 核心正在读取这块内存，如果立即释放就会导致"读到已释放内存"的严重 bug。RcuBox 通过 call_rcu() 或 kvfree_call_rcu() 来确保安全释放。此外，补丁还扩展了 ForeignOwnable trait，让容器类型能依赖 RcuBox 的 RCU 属性。

📬 查看补丁
[RFC 讨论] RcuFreeBox——更细粒度的 RCU 释放

Alice Ryhl 和 Boqun Feng 正在讨论一个新的类型 RcuFreeBox。现有的 RcuBox 在 RCU 宽限期之后会同时做两件事：①调用对象的析构函数（drop）②释放内存。但某些场景下，我们需要更细粒度的控制——比如只需要保证"内存不会被立即释放"（用于 SLAB_TYPESAFE_BY_RCU），但析构函数可以提前调用。RcuFreeBox 就是为这种场景设计的：它在 drop 时立即调用析构函数，但推迟内存释放到宽限期之后。这个 RFC（征求意见稿）正在 Danilo 的请求下开发，目前社区有 4 条审阅意见。

FerroLens 发现的安全漏洞（Soundness Bug）

Bug 1：GenDisk 的 Send 实现不健全

今天一个叫 FerroLens 的新工具引起了社区的关注。这是加州大学河滨分校（UCR）的 Yuan Tan 等人开发的工具，专门用来检测 Linux 内核 Rust 代码中的"不健全"（unsound）行为。"不健全"是 Rust 术语，意思是代码虽然能编译通过，但在某些条件下可能违反 Rust 的安全保证。今天 FerroLens 一口气报告了三个 bug：

GenDisk 是块设备（比如硬盘）驱动中的一个核心类型。它被标记为 Send（意味着"可以安全地在线程间传递"），但问题是它内部包含的某些字段（特别是 Queue 类型的参数）可能并不满足 Send 的要求。这就像一个快递箱被标记为"可以空运"，但里面装了不能空运的液体。补丁的修复方案是让 GenDisk 的 Send 实现正确地考虑其内部类型的约束。

Bug 2：Revocable 模块中的竞态条件

Revocable（可撤销）是内核中的一种机制：有些资源在某个时刻需要被"撤销"（变成不可用）。FerroLens 发现 revoke_internal/no_sync（撤销操作）和 try_access（尝试访问操作）之间存在竞态条件——也就是说，一个线程正在撤销资源的同时，另一个线程可能正好在尝试访问它，导致不安全的并发访问。这就像一个人正在关门，另一个人同时在推门，可能导致门夹到人。

锁机制与调试（Lockdep / 中断管理）

XArray 修复 lockdep 误报（v2）

Alice Ryhl 提交的补丁修复了 XArray（一种可扩展数组数据结构）的 lockdep 误报问题。问题的根因很有趣：xa_init_flags() 是一个 C 的 static inline 函数，它内部调用了 spin_lock_init()，这个宏会为每个编译单元生成一个静态的 lock_class_key。当通过 Rust 绑定调用时，所有 Rust 中创建的 XArray 实例最终共享同一个 key。这导致 lockdep（内核的死锁检测工具）误以为这些不同的 XArray 在互相竞争同一把锁，从而发出假警报。修复方法是为每个 Rust XArray 实例分配独立的 lockdep key。

📬 查看补丁
块设备：为 open_mutex 分配独立的 lockdep 类（v3）

Andreas Hindborg 提交的补丁解决了一个类似的问题，但针对的是块设备驱动。每个磁盘（disk）都有一个 open_mutex（打开互斥锁），用来保护磁盘的打开/关闭操作。lockdep 工具需要区分不同磁盘的锁，但由于它们使用相同的 lockdep class，lockdep 会报告假阳性（false positive）的死锁警告。这个补丁让每个调用者可以指定自己的 lockdep class，从而消除误报。这个补丁已经到了第三版，收到了 7 条审阅意见，讨论相当充分。

中断计数与自旋锁改进（v3，共 13 个补丁）

Boqun Feng 提交了一组大补丁（13 个），对内核的中断禁用/启用机制做了重要改进。

问题是什么？现有的 _irqsave() / _irqrestore() API 有一个隐患：它们通过保存和恢复标志位（flags）来管理中断状态，但如果使用不当（比如恢复了错误的 flags），就可能意外地启用或禁用中断。这在嵌套锁的场景中尤其容易出错。

解决方案：补丁引入了"计数式中断禁用"——用一个计数器来跟踪中断被禁用了多少次。每次禁用计数器 +1，每次启用计数器 -1，当计数器归零时才真正启用中断。这比传统的 flags 方式更安全、更不容易出错。同时还引入了 __preempt_count_{add,sub}_return() 原语，用于在修改抢占计数后返回新值，为中断计数提供底层支持。

指针 API 改进（INDEX PROJECTION 语法）

指针 API 改进（Index Projection 语法）

改了什么？

Gary Guo 今天在 rust-next 分支合并了一系列关于索引投影（Index Projection）的改进提交。索引投影是 Rust-for-Linux 中一个自定义的机制，用于在编译时安全地访问数组/切片元素。

1. 重命名：把 ProjectIndex::index 方法重命名为 build_index，因为 Rust 标准库中 SliceIndex trait 的 index 方法表示"可能 panic 的索引"，为了避免语义冲突，内核版本改名为 build_index，表示"编译时检查的索引"。

2. 用 match 替代 unwrap_or_else：在 build_index 的实现中，用 match 语句替代了 unwrap_or_else，避免了潜在的内联问题。编译器有时不能正确内联 unwrap_or_else 的闭包，导致不必要的函数调用开销。

3. 新增 panic 变体：有些情况下，程序员知道索引一定在范围内，但编译器无法证明（而且这还可能因编译器版本不同而变化）。新增的 panic 变体在运行时检查索引，如果越界就 panic，而不是编译时报错。

4. 关键字语法：所有使用者都已转换为关键字索引投影语法（keyworded index projection syntax），通过关键字明确表达意图：是编译时检查（build）还是运行时检查。最后，旧的隐式语法被移除。

固件与设备驱动

固件加载：为零大小固件返回空切片

这是一个看似简单但很关键的修复。Firmware::data() 方法使用 core::slice::from_raw_parts() 来构建一个 Rust 切片（slice）。在 C 语言中，空指针 + 长度为 0 是一种常见的"什么都没有"的表示方式。但 Rust 不一样——from_raw_parts() 要求指针永远不能是 NULL，即使长度为 0 也不行！Linux 的固件加载器在表示"空固件"时，确实会设置 size = 0 且 data = NULL。如果直接把这个 NULL 指针传给 Rust，就会触发未定义行为。修复方案很简单：检测到空固件时，直接返回一个空的 Rust 切片（&[]），而不是去调用 from_raw_parts()。这个补丁收到了 6 条审阅意见，讨论很充分。

Mark Brown 提交了一个巧妙的补丁来解决一个长期困扰社区的问题。Randstruct 是一个内核安全加固功能，它会随机化结构体字段的排列顺序，让攻击者更难通过内存偏移来利用漏洞。但问题是：Rust 目前不支持 randstruct，内核配置中有一个 !RANDSTRUCT 的依赖项。在 allmodconfig（"尽可能多地启用模块"的标准覆盖测试配置）下，randstruct 默认开启，这就导致 Rust 被自动禁用了。补丁的解决方案是：当启用了 Rust 时，默认关闭 randstruct。这样 allmodconfig 就能同时编译 Rust 代码了，大大提高了测试覆盖率。
