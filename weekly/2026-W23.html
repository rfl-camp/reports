串口设备总线抽象（v11）

串口设备总线抽象（v11）

由 Markus Probst 和 Onur Özkan 等人推进的串口（serial）设备总线 Rust 抽象补丁已经迭代到了第 11 版，收到了来自 Danilo Krummrich 等人的 9 条审阅意见。这组补丁为 Linux 内核的串口子系统提供了基础的 Rust 绑定，让开发者以后可以用 Rust 来编写串口设备驱动。串口是最古老也最基本的通信接口之一（比如你连接开发板或路由器的调试口，用的往往就是串口），为它提供安全的 Rust 抽象，意味着这类底层驱动也能享受到 Rust 的内存安全保障。经过 11 轮迭代，说明社区对这组抽象的 API 设计非常谨慎，力求在易用性和内核惯例之间找到最佳平衡。

LED 多色类设备抽象（v18）

LED 多色类设备抽象（v18）

Onur Özkan 提交的 LED 多色类设备（multicolor classdev）抽象已经迭代到了令人印象深刻的第 18 版。这组补丁为内核的 LED 子系统添加 Rust 支持，特别针对可以显示多种颜色的 LED 设备（比如 RGB LED 灯）。v18 这个版本号本身就说明了一个事实：内核社区对新抽象层的审阅标准极其严格，每一轮都可能有 API 设计、安全性、性能等方面的修改建议。不过这也是好事——经过如此多轮打磨的代码，一旦合入主线，质量将非常可靠。

I2C 适配器引用计数修复（v3）

I2C 适配器引用计数修复（v3）

Nicolás Antinori 发现并修复了 I2C 适配器 Rust 绑定中的一个引用计数双重递增的 bug。问题出在 I2cAdapter::get 方法上：当调用 C 侧的 i2c_get_adapter() 时，引用计数已经加了 1；但随后将裸指针转换为 Rust 的 ARef 智能指针时，From trait 的实现又把引用计数加了 1。这意味着每次获取适配器引用，计数都会多加一次，最终会导致设备资源永远无法被正确释放（内存泄漏）。这是 Rust 和 C 交互时非常典型的陷阱——两边各有自己的资源管理逻辑，必须小心协调才能避免重复计数。

小白科普
引用计数（Reference Counting）：一种资源管理方式，每当有人"借用"一个资源，计数加 1；归还时减 1；计数归零时资源被释放。就像图书馆的借阅系统——借书+1，还书-1，没人借了书就回到书架。如果计数出错（比如借一次记成借两次），书就永远不会"回到书架"了。 📖 了解 Rust 中的引用计数
I2C 总线：一种常见的低速通信总线，用于连接温度传感器、触摸屏控制器等各种小型芯片，只需两根线即可通信。 📖 内核 I2C 文档

SRCU 抽象（v7）

SRCU 抽象（v7）

Onur Özkan 提交的 SRCU（Sleepable RCU）Rust 抽象补丁已迭代到 v7，收到了来自 RCU 维护者 Paul E. McKenney 和 Rust-for-Linux 维护者 Miguel Ojeda 的 4 条审阅意见。SRCU 是 Linux 内核中一种重要的同步原语——简单来说，它允许多个"读者"同时访问共享数据而几乎不需要等待，只有"写者"修改数据时才需要协调。与普通的 RCU 不同，SRCU 允许读者在持有锁的期间进入睡眠状态（比如等待磁盘 I/O 完成），这使它在更多场景下可以使用。为 SRCU 提供 Rust 绑定意味着 Rust 驱动开发者可以安全地使用这一高性能同步机制，而不需要手动管理复杂的读侧临界区。能够同时得到 RCU 专家和 Rust 专家的审阅，是这类关键基础设施补丁质量的有力保障。

RCU（Read-Copy-Update）：内核中一种"读多写少"场景的高效同步机制。想象一个公告板：所有人可以随时来看（读），但管理员更新内容（写）时，不是直接擦掉旧的，而是先写好一份新的、等所有正在看旧公告的人看完了，再把旧公告撤下来。SRCU 就是"可以在看公告时打个盹"的版本。 📖 什么是 RCU

支持 Rust 1.98.0 目标规格（x86）

支持 Rust 1.98.0 目标规格（x86）

Miguel Ojeda 提交了一个补丁，让内核的构建系统能够兼容 Rust 1.98.0 及以上版本的新目标规格（target spec）。Rust 编译器需要知道"我在给什么平台编译代码"，这就是目标规格的作用。当 Rust 上游修改了 x86 平台的目标规格格式时，内核这边也需要及时跟进，否则新版本的 Rust 编译器就无法正常编译内核代码。这类补丁虽然看起来不起眼，却是保持 Rust-for-Linux 与上游 Rust 工具链同步的必要工作，确保开发者可以使用最新的编译器来构建内核。

kbuild: 清理长类型名文件（v3）

kbuild: 清理长类型名文件（v3）

Miguel Ojeda 提交的构建系统补丁（v3）将 *.long-type-*.txt 文件纳入了 make clean 的清理目标。这些文件是 Rust 编译器在遇到过长的类型名时自动生成的诊断文件——Rust 的类型系统非常强大，有时候泛型嵌套会产生极长的类型名（想象一层套一层的俄罗斯套娃），编译器会把完整的类型名写入文件以供调试。现在执行 make clean 时这些临时文件也会被自动清理，保持构建目录的整洁。

GitHub: Rust 不稳定特性跟踪

GitHub: Rust 不稳定特性跟踪

GitHub 上由维护者 ojeda 维护的 Issue #2 本周仍在活跃更新。这个议题持续跟踪内核所依赖的 Rust 不稳定特性（unstable features）。由于内核使用了一些尚未在 Rust 稳定版中发布的语言功能，社区需要密切关注这些特性在上游 Rust 中的稳定化进度。每当一个特性被稳定化，内核就可以减少对 nightly 编译器的依赖，这是 Rust-for-Linux 走向广泛采用的关键里程碑之一。

目标规格（Target Spec）：告诉编译器"你要为什么样的硬件和操作系统生成代码"的配置文件。就像你出国旅行前要知道目的地用什么电压和插头一样，编译器也需要知道目标平台的"规格"才能生成正确的机器码。

Binder 驱动：修复 32 位架构上的偏移数组步长问题（v2）

Binder 驱动：修复 32 位架构上的偏移数组步长问题（v2）

Hyunwoo Kim 发现 Rust 版 Binder 驱动在清理 offsets 数组时存在一个与平台相关的 bug。Binder 是 Android 系统中进程间通信（IPC）的核心机制，偏移数组中的每个条目都是 binder_size_t（即 u64，固定 8 字节），但代码中使用了 usize 来计算步长和读取每个条目。在 64 位系统上 usize 恰好是 8 字节，所以问题不会暴露；但在 32 位系统上 usize 只有 4 字节，步长变成了一半，导致遍历错位——就像翻书时每次翻一页变成了翻半页，后面读到的内容全是错的。这种"在主流平台上正常、在特定平台上出错"的 bug 很隐蔽，这次修复体现了社区对跨平台正确性的重视。

宏改进：用 const expect 替代 match + panic

宏改进：用 const expect 替代 match + panic

Daniel del Castillo 提交了一个改进内核 Rust 宏代码质量的补丁。在之前的代码中，编译期常量上下文（const context）里使用了 match + panic! 的组合来处理错误情况。这次改用了更简洁的 const expect 写法——效果一样（编译时如果条件不满足就报错），但代码更易读、意图更明确。这类改进虽然不影响运行时行为，但让代码库更加清晰，降低了后来维护者的理解成本。

小白科普
Binder：Android 系统的进程间通信（IPC）机制。不同的应用（进程）之间要互相传数据，就需要一个"中间人"——Binder 就充当这个角色。它是 Android 能够运行的基石之一。 📖 Android Binder 介绍
usize vs u64：usize 的大小取决于平台（32 位系统上是 4 字节，64 位上是 8 字节），而 u64 固定是 8 字节。当数据格式要求固定宽度时，必须用 u64 而不是 usize，否则跨平台就会出错。
