⚡ PowerPC 架构的 Rust 支持（V14）

这是本周体量最大、意义最深远的补丁系列：一共 7 个补丁，由 IBM 的 Mukesh Kumar Chaurasiya 和社区贡献者 Link Mauve 联合提交，已经迭代到第 14 版。它的目标是让 Linux 内核中的 Rust 代码能够在 ppc64le（64 位 PowerPC 小端，如 IBM Power11 服务器） 和 ppc32be（32 位 PowerPC 大端，如任天堂 Wii、GameCube） 上正确编译和运行。

补丁 1：修复 "multiple candidates for rmeta dependency core" 错误

补丁 1：修复 "multiple candidates for rmeta dependency core" 错误
当使用 LLVM 工具链并行度为 1（-j1）编译 ppc64le 时，rustc 会同时看到"系统自带的标准库 core"和"内核自己定制的 core"，产生歧义报错。这个补丁通过调整构建逻辑，确保 rustc 只看到内核版本的 core，消除了歧义。

📬 查看补丁
补丁 2：修复 CONFIG_DMA_SHARED_BUFFER 未启用时的链接错误

补丁 2：修复 CONFIG_DMA_SHARED_BUFFER 未启用时的链接错误
在 PowerPC 等平台上，如果没有开启 CONFIG_DMA_SHARED_BUFFER（一个用于 GPU/显示等设备共享内存的内核选项），链接器会报找不到 dma_resv_reset_max_fences 符号的错误。补丁修复了 helpers.c 中的条件编译，避免在不需要的情况下引用该符号。

补丁 3：让 __udivdi3() 和 __umoddi3() 触发 panic

补丁 3：让 __udivdi3() 和 __umoddi3() 触发 panic
在 32 位系统上，C 编译器有时会把 64 位除法悄悄转换为调用 __udivdi3/__umoddi3 这两个软件实现的除法函数。问题在于：内核的 Rust 代码不应该依赖这些来自用户态 C 库的实现。补丁将这两个函数改为一旦被调用就 panic，从而在开发阶段暴露不正确的使用方式，而不是静默地产生错误行为。

补丁 4：调整 powerpc jump_label 内联汇编，添加 ARCH_STATIC_BRANCH_ASM 宏
为了让 C 和 Rust 共用同一套跳转标签（jump_label）的内联汇编逻辑，而不是各自复制一份，补丁引入了新的宏 ARCH_STATIC_BRANCH_ASM，与其他架构（如 x86、ARM）的做法保持一致。

补丁 5 & 6：设置 PowerPC 最低 rustc 版本要求 + 正式添加 PowerPC Rust 支持
PowerPC 至少需要 rustc 1.95，因为 稳定版内联汇编（stable inline asm） 正是在这个版本才进入稳定通道。最终补丁由 Link Mauve 编写，在 Nintendo Wii 上完成了实测验证，ppc64le 则在 IBM pseries Power11 服务器上通过了 dmesg 确认。

generate_rust_analyzer.py 新增版本管理基础设施（V4）

generate_rust_analyzer.py 新增版本管理基础设施（V4）
rust-analyzer 是 Rust 开发者最常用的 IDE 插件/语言服务器，能提供代码补全、跳转到定义、错误提示等功能。但在 Linux 内核这样的复杂项目里，让 rust-analyzer 正确理解内核代码一直是个难题。generate_rust_analyzer.py 是专门为内核生成 rust-analyzer 配置文件的脚本。这次 V4 补丁（2 个补丁）为该脚本添加了版本管理基础设施，让工具能够追踪配置格式的版本变化，为未来的功能扩展铺路。该系列已有 2 条审核意见。

工作队列子系统：SAFETY 注释修正

工作队列子系统：SAFETY 注释修正

Rust 中有一个重要约定：凡是绕过编译器安全检查的代码（用 unsafe 块包裹），必须附上 // SAFETY: 注释来解释"为什么这里是安全的"。内核工作队列（workqueue，一种让驱动把任务交给后台线程异步执行的机制）的 Rust 封装中，Pin<KBox<T>> 的 WorkItemPointer 实现里存在错误的 SAFETY 注释——注释里写的是 Arc::into_raw，但实际用的是 KBox::into_raw。

这个 V2 补丁由 Sagar Taunk 提交，将注释更正为 KBox::into_raw。虽然这不影响实际运行行为（SAFETY 注释只是给人看的文档），但错误的注释会误导阅读代码的人，让他们误以为这里使用了引用计数（Arc），从而在理解内存所有权模型时产生混淆。已有 3 条审核意见，维护者 Miguel Ojeda 参与了审核。

📬 查看补丁
🔰 小白科普
workqueue（工作队列）：内核提供的一种机制，驱动可以把"稍后再做"的任务放进队列，由专门的内核线程在合适时机执行，避免在中断处理等时间敏感的上下文里做耗时操作。就像餐厅的传菜窗口：厨师（驱动）把菜放上去，服务员（工作线程）再端出去。
SAFETY 注释：Rust for Linux 的代码规范要求，每个 unsafe 代码块旁必须用注释解释安全性依据，是内核 Rust 代码质量的重要保证。

#1080：Rust CI 需要的特性与 Bug 修复
这是一个"元议题"（meta issue），汇总了 Rust for Linux 持续集成（CI）系统目前缺少的功能和已知问题，标签为 misc 和 meta。CI 系统相当于内核的"自动质检流水线"，如果 CI 不完善，新提交的代码可能引入隐患而不被及时发现。有意参与 CI 基础设施改进的开发者可以在此议题中提交反馈。

#2：内核所需的 Rust 不稳定特性

#2：内核所需的 Rust 不稳定特性
这是项目中最古老的开放议题之一（编号 #2），追踪了内核 Rust 代码当前依赖的所有 Rust 不稳定特性（unstable features）。不稳定特性意味着这些语言功能还没有被正式纳入 Rust 稳定版，未来可能发生变化。内核团队的目标是尽量减少对不稳定特性的依赖，每消灭一个依赖就意味着内核 Rust 代码的长期可维护性又提升了一步。这个议题是了解 Rust 语言标准化进展如何影响内核开发的好入口。

🔗 查看议题 #2
🔰 小白科普
Rust 不稳定特性（unstable features）：Rust 的新功能在正式"稳定"前，需要用 #![feature(...)] 显式开启，且只能在 nightly 版编译器上使用。内核代码追求稳定性，因此社区积极推动将关键特性纳入稳定版。
CI（持续集成）：每次提交代码后自动运行编译、测试的流水线，相当于代码的"体检"，在合并前发现问题。
