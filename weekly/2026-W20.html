构建系统：工具链缺失时不再"假装成功"

构建系统：工具链缺失时不再"假装成功"

发生了什么：Sasha Finkelstein 提交了一个补丁，要求当内核配置开启了 RUST=y（即启用 Rust 支持）但 Rust 工具链实际不可用时（RUST_IS_AVAILABLE=n），构建直接失败而不是静默地跳过所有 Rust 驱动。

为什么重要：之前的行为非常令人困惑——用户明明在配置里打开了 Rust 驱动（比如 Apple GPU 驱动），编译也"成功"了，但重启后发现驱动根本没有被编译进去。这就像你在购物车里加了商品但结账时系统悄悄把它们移除了，你毫不知情。补丁收到了 4 位评审者的反馈，包括 Janne Grunau 和项目维护者 Miguel Ojeda，说明社区对此方案高度关注。

📬 查看补丁
💡 小白科普
RUST_IS_AVAILABLE：内核构建系统中的一个自动检测变量，用于判断当前系统是否安装了合适版本的 Rust 编译器（rustc）和绑定生成工具（bindgen）。如果检测不通过，这个变量为 n。

⚙️ 工作队列：新增 CANCEL_SYNC 支持

⚙️ 工作队列：新增 cancel_sync 支持

发生了什么：Onur Özkan 提交了一个补丁，为 Rust 的工作队列（workqueue）模块添加 cancel_sync 功能。Alice Ryhl（Google 的 Rust-for-Linux 核心贡献者）参与了评审。

为什么重要：当一个驱动程序要被卸载（teardown）时，它可能还有一些"待办事项"在工作队列里排队等着执行。cancel_sync 的作用就像你在离开办公室前把所有待处理的工单取消，并且等待正在处理中的工单完成——这样才能安全地释放相关资源，不会出现"资源已经被释放但还有代码在使用它"的内存安全问题。

值得注意的是，这个功能没有为 Pin<KBox<T>> 类型实现，因为将一个装箱的工作项排入队列会转移所有权——此时取消操作的语义会更加复杂。

📬 查看补丁
💡 小白科普
Workqueue（工作队列）：内核中延迟执行任务的机制。想象成一个"待办事项清单"——驱动把不紧急的任务丢进去，内核会在合适的时候（比如不在中断上下文时）去执行它们。这避免了在时间敏感的代码路径中做耗时操作。

PIN-INIT 库：V7.2 上游同步启动

pin-init 库：v7.2 上游同步启动

发生了什么：Gary Guo 提交了一个包含 10 个补丁的系列，将 pin-init 库的上游更新同步回内核树（第一轮）。同时还有一个独立补丁修复了 Clippy 的 useless_borrows_in_formatting 警告。

为什么重要：pin-init 是 Rust-for-Linux 中极为核心的基础设施——它解决了一个 Rust 和内核交互时的根本难题：内核中许多数据结构初始化后不能被移动（比如包含自引用指针的结构），而 Rust 默认允许值被移动。pin-init 提供了一套安全的 API，让你可以"就地初始化"这些结构。每次上游同步都意味着更多的 bug 修复和 API 改进被引入内核。

📬 查看同步补丁系列 📬 查看 Clippy 修复
💡 小白科普
Pin（固定）：Rust 中防止值被移动的机制。类比：你把一张便签钉在了软木板上——它就不能再被挪走了。内核中很多结构体（如互斥锁、链表节点）内部包含指向自身的指针，一旦移动，这些指针就失效了，所以必须"钉住"。

辅助设备框架：V2 迭代

辅助设备框架：v2 迭代

发生了什么：Danilo Krummrich（内核 Rust 设备模型的主要开发者）提交了辅助设备（auxiliary device）系列的第二版，这次为辅助设备添加了注册数据的支持。该系列共 3 个补丁，已收到 1 条评审意见。

为什么重要：辅助设备是 Linux 中一种让单个物理设备暴露多种功能的机制。例如一块网卡可能同时提供网络功能和 RDMA 功能——它可以注册多个"辅助设备"，每个对应一种功能并绑定不同的驱动。为这个框架提供 Rust 支持，让 Rust 驱动可以充分利用现代硬件的多功能特性。从 v1 到 v2 的迭代说明社区正在积极完善这一基础抽象。

📬 查看补丁
💡 小白科普
Auxiliary Device（辅助设备）：内核中的一种设备抽象模式。想象一把瑞士军刀——物理上是一把刀，但逻辑上可以拆分成刀片、开瓶器、剪刀等多个"辅助工具"，每个都可以有自己独立的驱动程序来管理。

Miguel Ojeda 和 Jan Engelhardt 围绕 kconfirm 工具展开了讨论（共 2 条消息）。这是一个 RFC（征求意见稿）的第二版，涉及为内核添加某种确认机制。目前讨论仍在早期阶段，细节有待社区进一步展开。

📬 查看讨论
rust-analyzer 无法识别 container_of! 类型

在 Zulip 的 Help 频道中，有开发者报告 rust-analyzer（Rust 的 IDE 支持工具）突然无法理解 container_of! 宏的返回类型。Jesung Yang 指出这可能与原始指针类型上的固有方法调用（如 byte_sub、cast）有关，并表示这个问题应该已经有修复方案。

这类工具链问题对日常开发体验影响很大——如果 IDE 无法正确推断类型，开发者在写 Rust 内核代码时就失去了自动补全和类型检查的帮助。

📬 查看 Zulip 讨论
💡 小白科普
container_of!：内核中一个极为常用的宏。假设你有一个结构体里面包含了一个链表节点，你只有这个节点的指针——container_of! 能帮你"反推"出包含它的外层结构体的指针。就像知道了心脏的位置，推算出整个人的位置。
rust-analyzer：Rust 语言的智能 IDE 引擎，提供代码补全、跳转定义、类型推断等功能，类似于 C/C++ 的 clangd。
