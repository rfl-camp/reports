块设备（BLOCK DEVICE）子系统

块设备（Block Device）子系统

修复 GenDiskBuilder 构建失败时的资源泄漏

补丁作者：Haoze Xie (Ren Wei)

这个补丁修复了一个隐蔽的资源泄漏问题。当 GenDiskBuilder::build() 在调用内核 C 函数 __blk_mq_alloc_disk() 之后发生失败时，已经分配好的 gendisk（通用磁盘结构）不会被释放，而是一直留在内存中，直到调用者释放最后一个 tagset 引用才会被回收。打个比方：这就像你在组装一台电脑时，主板已经装好了但发现显卡不兼容，结果主板既没有被退回仓库，也没有被安装使用，就一直占着桌面空间。补丁的解决方案是在失败路径上主动释放这个临时创建的 gendisk 对象，确保资源不会泄漏。这类"错误路径"的清理工作虽然不起眼，但对内核的长期稳定性至关重要。

📬 查看补丁
小白科普
gendisk（通用磁盘）：Linux 内核用来表示一个磁盘设备（如硬盘、SSD）的核心数据结构，类似于磁盘设备的"身份证"，记录了磁盘的名字、大小、分区等信息。
错误路径（failure path）：代码中处理"如果操作失败了该怎么办"的分支。好的代码需要在每个可能出错的地方都做好清理工作，否则就会造成资源泄漏。

I2C 子系统

I2C 子系统

修复 I2cAdapter 引用计数重复递增

补丁作者：Nicolás Antinori

这是一个典型的"引用计数"bug 修复。当调用 I2cAdapter::get 时，底层 C 函数 i2c_get_adapter() 已经将设备和模块的引用计数加了一次。然而，在将返回的裸指针转换为 Rust 的 ARef（自动引用计数智能指针）时，From trait 的实现又额外增加了一次引用计数。这导致引用计数被多加了一次，最终设备永远不会被真正释放——就像借了两本图书馆的书，但登记簿上写成了四本，你还了两本后系统还以为你没还完，那两本书就永远"在借"状态了。这个修复确保引用计数只增加一次，避免了资源的永久占用。

为 I2cClient 实现 Io trait（RFC v3 系列的一部分）

补丁作者：Muchamad Coirul Anwar

这个补丁是 AS5600 传感器驱动系列的一部分，为 I2cClient 实现了 kernel::io::Io trait，提供了 try_read8() 和 try_read16() 方法。这意味着未来所有通过 I2C 总线进行寄存器读写的 Rust 驱动都可以使用统一的接口，而不需要每个驱动自己处理底层通信细节。这遵循了社区之前讨论达成的共识方向，是 I2C Rust 抽象层的重要基础设施。

📬 查看补丁
小白科普
I2C（Inter-Integrated Circuit）：一种简单、低速的通信总线协议，常用于连接传感器、显示屏等外围设备到主处理器。你可以把它想象成一条"共享电话线"，多个设备轮流用它和 CPU 说话。
引用计数（Reference Counting）：一种内存管理技术，每个对象维护一个计数器，记录有多少地方在使用它。当计数归零时，对象就可以被安全释放。Rust 的 Arc 和内核的 ARef 都使用这种机制。

IIO 子系统与传感器驱动

IIO 子系统与传感器驱动

Patch 0/4：系列总览

本周最值得关注的系列补丁来自 Muchamad Coirul Anwar，他提交了 AS5600 磁旋转位置传感器 Rust 驱动的第三轮 RFC（v3），共包含 4 个补丁。这个系列不仅仅是一个传感器驱动，更重要的是它同时引入了 IIO 子系统的最小化 Rust 抽象层——这是将整个工业传感器生态引入 Rust 内核的关键一步。

v3 在 v2 的基础上继续迭代，v2 已经引入了最小化的 IIO 抽象并通过 sysfs 暴露了 in_angl_raw（原始角度值）和 in_angl_scale（缩放因子）两个属性。这意味着用户空间程序可以通过简单地读取文件来获取传感器的角度数据——这正是 Linux 驱动的标准做法。

📬 查看系列总览
Patch 2/4：最小化 IIO 子系统 Rust 抽象

这是整个系列的核心。它为 Linux IIO 子系统提供了安全的 Rust 封装，包括：使用 typestate 模式的 Device<T, State>（设备在"未注册"和"已注册"之间有编译期状态检查）、IioDriver trait 定义驱动接口等。Typestate 模式是 Rust 的一大特色——它让编译器帮你检查"这个设备还没注册呢，你不能读数据"这类逻辑错误，而在 C 语言中这类错误只能靠程序员自己小心。这是 Rust 在内核驱动中展现安全优势的一个优秀案例。

小白科普
IIO（Industrial I/O）子系统：Linux 内核中专门管理各类传感器（加速度计、温度计、光传感器等）的框架。它提供了统一的接口让用户空间程序读取传感器数据，就像一个"传感器通用翻译官"。

编译与性能优化

编译与性能优化

OPP 模块方法标记为 inline

补丁作者：Nicolás Antinori

使用 LLVM 19.1.7 + Rust 1.85.0 工具链编译内核时，Nicolás 发现 OPP（Operating Performance Points，工作性能点）模块的几个方法（如 OPP::freq）被编译器生成为独立的符号，出现在了 vmlinux 的符号表中。这意味着这些本应很小的函数没有被内联展开，而是被当作了独立函数来编译，产生了不必要的函数调用开销。补丁通过为这些方法添加 #[inline] 标记来提示编译器将它们内联展开。这类优化虽然单个影响很小，但积少成多，对内核整体性能有帮助。同时这也反映出 Rust 编译器在内核场景下的内联策略可能与 C 编译器有差异，需要开发者额外关注。

📬 查看补丁
小白科普
内联（inline）：一种编译器优化技术。正常的函数调用需要"跳转"到函数代码的位置再"跳回来"，有一定开销。内联是把函数的代码直接"复制粘贴"到调用的地方，省去了跳转开销，但会增加代码体积。对于很短的函数，内联几乎总是划算的。
OPP（Operating Performance Points）：内核中用于管理设备频率和电压组合的框架。比如你的 CPU 可以在 1GHz/0.9V 或 2GHz/1.1V 下运行，每一组搭配就是一个 OPP。
