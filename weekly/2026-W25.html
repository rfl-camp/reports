RUST FOR LINUX 7.2 合并请求

Rust for Linux 7.2 合并请求

Miguel Ojeda（Rust-for-Linux 项目的主要维护者）本周向 Linus Torvalds 发出了 [GIT PULL] Rust for v7.2 的合并请求。这是 Rust 代码进入 Linux 主线的常规流程：每个内核开发周期，Rust 子系统维护者会将积攒的改动打包，请求合入上游。

本次合并的亮点是 zerocopy 库的 vendoring（内核内部供应）。zerocopy 是一个帮助安全地在字节数组和结构体之间做零拷贝转换的 Rust 库。在内核环境中，这类转换非常常见——例如从硬件寄存器或网络数据包中解析结构化数据。此前内核中有一些手工的实现，而引入 zerocopy 后可以用更安全、更标准化的方式完成同样的工作。由于内核不能直接使用 crates.io 上的外部依赖，所以需要将库的源码复制进内核源码树——这就是所谓的"vendoring"。正因为要把一整个库搬进来，这次合并请求的体积比较大。

💡 小白科普
GIT PULL 请求：Linux 内核开发中，子系统维护者把准备好的改动放在自己的 Git 仓库分支里，然后给 Linus 发一封邮件说"请从这个分支拉取代码"。Linus 审查后决定是否合入主线。这是内核代码进入正式版本的最后一道关卡。
Vendoring：把一个外部库的源代码直接复制到自己的项目中，不再依赖外部包管理器。内核不连接互联网下载依赖，所以必须这样做。

EDU PCI 驱动示例：RUST 内核驱动的"全功能教科书"

EDU PCI 驱动示例：Rust 内核驱动的"全功能教科书"

本周最引人注目的补丁系列来自 Maurice Hieronymus，他提交了一组共 4 个补丁，为内核添加了一个完整的 QEMU EDU 设备 Rust 驱动示例。这个示例的特别之处在于：它在一个驱动里同时展示了 MMIO（内存映射 I/O）、中断处理（IRQ）和 DMA（直接内存访问）三大核心能力。

在此之前，内核源码树中已有的 Rust 示例驱动是"各管一摊"的——rust_driver_pci 只演示 MMIO，rust_dma 只演示 DMA，没有一个把所有能力组合在一起的完整例子。对于想学习 Rust 内核驱动开发的人来说，缺少这样一个"全栈"示例是个痛点。EDU 设备是 QEMU 虚拟机自带的一个教学用 PCI 设备，非常适合作为学习目标——你不需要真实硬件，只要启动一个 QEMU 虚拟机就能测试。

为了让这个示例能够工作，Maurice 还提交了配套的基础设施补丁：

① 封面信：EDU PCI 驱动示例系列

① 封面信：EDU PCI 驱动示例系列

这是整个补丁系列的总览。Maurice 说明了现有示例的不足——各个 PCI 功能分散在不同示例中，没有一个综合性的范例——并解释了为什么选择 QEMU EDU 设备作为目标。整个系列由 4 个补丁组成，逐步构建出完整的驱动。

📬 查看封面信
② 让 Vendor::from_raw() 变为公开 API

② 让 Vendor::from_raw() 变为公开 API

这个补丁解决了一个实际问题：之前 Vendor::from_raw() 是 pub(super)（只在模块内部可见），意味着驱动只能匹配那些在 <linux/pci_ids.h> 中有符号名的 PCI 厂商 ID。但 EDU 设备的厂商 ID（0x1234）并没有被定义在这个头文件里，所以驱动无法构造对应的 Vendor 来匹配设备。把 from_raw() 改为公开后，驱动就可以用原始数字来匹配任何厂商 ID 了。Gary Guo 参与了代码审查。

③ 添加托管式 Device::enable_device()

③ 添加托管式 Device::enable_device()

这个补丁为 PCI 子系统添加了 pcim_enable_device() 的 Rust 封装。和已有的 enable_device_mem()（只启用内存空间）不同，enable_device() 会同时启用 I/O 空间和内存空间。更重要的是，它是"托管式"的（managed）——当驱动与设备解绑时，设备会自动被禁用，不需要手动清理。这就像 Rust 的 RAII（资源获取即初始化）思想：获取资源时注册清理逻辑，离开作用域时自动释放，避免了忘记释放资源的 bug。

④ 为 Completion 添加 complete() 方法

④ 为 Completion 添加 complete() 方法

之前 Rust 的 Completion（完成量）抽象只提供了 complete_all() 和 wait_for_completion()。complete_all() 会把完成量标记为"永久完成"，之后无法重置——这意味着同一个 Completion 对象不能被反复用来通知事件。新增的 complete() 方法只唤醒一个等待者，并且之后完成量回到未完成状态，可以被再次使用。这就像一个"按一下响一声"的门铃，而 complete_all() 则是"按一下门铃就一直响"。在 EDU 驱动中，中断处理程序需要反复通知主线程"数据已准备好"，所以需要这个可重复触发的机制。Gary Guo 参与了审查。

⑤ EDU PCI 驱动示例本体

⑤ EDU PCI 驱动示例本体

最终的示例驱动本身！它通过新的 SAMPLE_RUST_DRIVER_EDU Kconfig 选项接入内核构建系统，可以作为内核模块编译和加载。这个驱动完整演示了：探测并启用 PCI 设备、映射设备内存区域进行寄存器读写、注册中断处理程序、设置 DMA 传输——是学习 Rust 内核驱动开发的绝佳起点。

💡 小白科普
PCI：一种连接硬件设备（显卡、网卡、硬盘控制器等）到 CPU 的总线标准。可以把它想象成主板上的"插槽"和"通信协议"。每个 PCI 设备都有一个厂商 ID 和设备 ID，驱动通过这些 ID 来认领自己该管理的设备。
MMIO / IRQ / DMA：设备驱动与硬件交互的三种基本方式。MMIO 是把设备寄存器映射到内存地址来读写；IRQ 是设备通过中断通知 CPU"我有事要汇报"；DMA 是设备直接读写内存而不经过 CPU，用于高速大量数据传输。
QEMU EDU 设备：QEMU 虚拟机自带的一个教学用虚拟 PCI 设备，专门用于学习驱动开发，不需要任何真实硬件。

Doctest 函数名裁剪，提升可复现性

Doctest 函数名裁剪，提升可复现性

Gary Guo 提交了一个补丁，修复了 Rust 文档测试（doctest）的一个可复现性问题。内核中的 Rust doctest 在编译时会生成包含函数名的标识符，而函数名可能包含文件路径等环境相关信息，导致在不同构建环境下产生不同的输出。这个补丁通过裁剪（trim）函数名来消除这种差异，确保 doctest 的行为在任何机器上都是一致的。David Gow 参与了审查。

这看起来是个小改动，但可复现构建（reproducible build）在内核开发中非常重要——它能让你确认"我编译出来的内核和别人编译出来的完全一样"，这对安全审计和问题排查都至关重要。

💡 小白科普
Doctest（文档测试）：写在代码注释 / 文档中的小段示例代码，编译器会自动提取并运行它们来验证文档中的例子是正确的。既是文档又是测试，一举两得。
可复现构建：指的是同样的源代码在任何机器上编译都能产生完全相同的二进制文件。如果编译结果因环境不同而不同，就很难确认软件没有被篡改。

cargo-nok：用纯 Cargo 构建树外内核模块的新提案

cargo-nok：用纯 Cargo 构建树外内核模块的新提案

Zulip 的 Modules 频道中，Tiago Dinis 提出了一个名为 cargo-nok 的工具概念。目前要编写一个树外（out-of-tree）Rust 内核模块，你仍然需要使用内核的构建系统 Kbuild（基于 Makefile），对 Rust 开发者来说不太友好。cargo-nok 的目标是让开发者可以用纯粹的 cargo build 工作流来构建内核模块，不需要和 Makefile 打交道。

不过 Tiago 也坦诚指出了挑战：Linux 内核使用的并不是标准的 core、alloc、compiler_builtins 等基础库，而是定制版本，所以并非所有普通的 Rust crate 都能直接在内核中使用。这意味着 cargo-nok 需要处理好这些差异，才能真正让开发体验丝滑。

目前这还处于早期概念阶段（PITCH），但它反映了社区对改善 Rust 内核模块开发者体验的期待。

💡 小白科普
树外模块（out-of-tree module）：不在 Linux 内核源码树中的内核模块。比如你自己写的一个驱动，代码放在自己的目录里。与之相对的是"树内模块"，直接在内核源码中维护。树外模块的好处是不用改动内核源码，但构建和维护会更麻烦。
Cargo：Rust 语言的官方包管理器和构建工具，相当于 Node.js 的 npm 或 Python 的 pip + setuptools。用 cargo build 一条命令就能编译整个项目。
